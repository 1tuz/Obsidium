# Индексация и переключение хранилищ Aquilum

Продолжение: [[search-indexing-workspaces-part-2]]

## Связанные документы

Ревизия индекса — общая причина для нескольких, на первый взгляд несвязанных, мест интерфейса:

- [[graph-view]] — снимок графа строится из этого индекса, ревизия решает, когда его перечитывать.
- [[tab-switching]] — раньше та же ревизия пересобирала все расширения CodeMirror прямо во время набора текста.
- [[mcp-and-doc-sync]] — сохранение документа и внешние правки — то, что поднимает ревизию.
- [[render-performance-pass]] — разбор, почему ревизию нельзя ставить в зависимости пересборки.

## 1. Короткий вывод

Markdown-файлы пользователя являются источником истины. Поиск и анализ графа не хранят отдельную копию заметок как первичные данные: они строят производные кэши. Для каждого хранилища создается отдельный каталог индекса, поэтому переход из хранилища A в B не очищает A и не смешивает записи A с B.

Активным в памяти одновременно является только один `ActiveIndex`: корень хранилища, Tantivy-индекс, SQLite-файл метаданных, прогресс и worker-наблюдатель. Старые дисковые кэши остаются для повторного быстрого открытия.

```text
Markdown files
    |
    +--> Tantivy index: full-text search
    +--> documents.sqlite3: fingerprints + wiki graph
    +--> ui-state.sqlite3: tabs, document IDs, cursor and scroll state
```

## 3. Где лежат данные

Tauri берет `app_data_dir()` и создает:

```text
<app-data>/ui-state.sqlite3
<app-data>/search-v2/<blake3(canonical-workspace-path)>/
    index-v3/          # Tantivy
    documents.sqlite3  # fingerprints, wiki graph и поля frontmatter
```

`ui-state.sqlite3` не является поисковым индексом. Он хранит workspace identity, UUID документов, вкладки, порядок вкладок, курсор и scroll position. В нем нет тела Markdown.

`documents.sqlite3` также не является источником текста. Он хранит минимальные данные, необходимые для инкрементальной синхронизации и связей. Тело заметки читается с диска при индексации.

Ключ к каталогу поиска вычисляется после канонизации пути. Поэтому разные workspace не делят один cache. Старый cache не удаляется автоматически.

## 4. Переключение A -> B -> A

Frontend передает `workspacePath` в `prepare_search_index`. Backend:

1. Берет `prepare_lock`, чтобы два переключения не открывали active state одновременно.
2. Канонизирует путь и проверяет, что это директория.
3. Если путь уже активен, возвращает текущий status.
4. Вычисляет отдельный cache directory по BLAKE3.
5. Открывает Tantivy и `documents.sqlite3` этого пути.
6. Сбрасывает in-memory graph cache.
7. Запускает worker с root, Tantivy, SQLite и progress.
8. Заменяет активный `ActiveIndex`.
9. Устанавливает cancellation у старого worker и дожидается его `join`.

На диске происходит не `delete(A)`, а выбор другого cache:

```text
A active -> B active: cache(A) остается, worker(A) остановлен, worker(B) сканирует B
B active -> A active: cache(A) переоткрывается, старый cache используется как база и проверяется
```

Это означает, что A не очищается при переходе в B. Актуальные результаты всегда должны проверяться через `same_workspace`: запрос с путем A к активному B получает `InvalidWorkspace`, а status для неактивного пути возвращает `idle`, а не чужой status.

### Защита от устаревших Windows-путей

Windows может вернуть `\\?\D:\Vault`, а frontend хранить `D:\Vault`. Search path normalization убирает extended prefix. Frontend `relativePath` тоже принимает обе формы. Без этого файл физически открывался, но UI-state не мог выдать `documentId`; редактор оставался на «Загрузка редактора CodeMirror».

### Кто и когда запускает подготовку

`prepare_search_index` вызывается из двух мест, и у каждого своя причина. `useLinkIndex` просит подготовку в момент простоя главного потока (`modules/idle.ts`), чтобы построение индекса не конкурировало с открытием первой заметки: пока страница разбирает бандл и монтирует редактор, простоя нет, поэтому индексация начинается после. `useKnowledgeSearch` просит её **только когда диалог поиска открыт** — раньше он делал это при запуске приложения, и подготовка уходила в бэкенд дважды подряд, хотя диалог мог никогда не открыться.

Ленивость безопасна: разрешение вики-ссылок в редакторе само дожидается `ensureReady`, а панель бэклинков узнаёт о готовности из события `links-changed`.


## 5. Полная индексация

Worker сначала запускает `full_scan`:

```text
begin_scan
  -> load fingerprints from SQLite
  -> WalkDir(root), hidden directories excluded
  -> only regular *.md files
  -> compare fingerprint
  -> update Tantivy + wiki tables
  -> commit batches
  -> remove stale files
  -> completed(indexed_count)
```

Обычный ход скана в журнал не пишется: старт, прогресс каждые 500 файлов, отмена и итог раньше шли в `eprintln!` на каждое открытие базы и каждое переключение — шум без пользы. В журнале остаются только ошибки (например, неудачное удаление индекса старой версии). Прогресс для интерфейса по-прежнему отдаёт `IndexProgress`.

Fingerprint использует гибридную проверку: сначала проверяется modification time в наносекундах и размер файла (`mtime` + `size`). Если они совпадают, файл пропускается мгновенно (без чтения с диска). Если `mtime` или размер изменились (например, при touch файла), но содержимое могло остаться прежним, вычисляется BLAKE3-хеш контента. Если хеш совпадает, обновление Tantivy и графа пропускается, обновляются только метаданные. Если количество SQLite records не совпадает с количеством документов Tantivy, включается `force_reindex`.

Одна заметка обновляется так:

1. Читается UTF-8 содержимое.
2. Старый Tantivy document удаляется по `id=absolute_path`.
3. Новый document добавляется с `id`, relative `path`, `title`, `body`.
4. В SQLite обновляется `documents`.
5. В `wiki_documents` обновляется имя и relative key.
6. Старые `wiki_links` этой заметки удаляются и извлекаются заново.

Полный scan коммитит пачками до 10 000 обработанных Markdown-файлов (`COMMIT_BATCH_SIZE`); после аварии скан продолжается с того же места, потому что версия анализатора хранится у каждого файла отдельно. Изменённые файлы читаются и хэшируются параллельно пачками по 64 (`PREPARE_BATCH_SIZE`), а в индекс их пишет один писатель. Tantivy commit и SQLite transaction связаны логикой worker, но не одной физической транзакцией. Это рабочая схема для локального приложения, но при аварийном завершении между двумя commit возможна короткая рассинхронизация; следующий scan должен ее исправить.

### Писатель индекса живёт, только пока есть что писать

`IndexSynchronizer` держит писателя tantivy в `Option` и создаёт его в момент первой записи:
новой или изменённой заметки, удаления устаревшей. Если при открытии базы ничего не изменилось,
писатель не создаётся вовсе. После записи воркер держит его ещё `WRITER_IDLE` (5 с) простоя и
отпускает через штатный `IndexWriter::wait_merging_threads`, который дожидается слияния сегментов.
Ожидание встроено в такт цикла воркера (`recv_timeout` 300 мс), отдельного потока нет.

Почему так. Писатель tantivy — это до 8 потоков индексации плюс пулы обновления и слияния
сегментов, 13 потоков на индекс, и все они спали всё время жизни индекса, хотя после первого скана
писатель нужен только на секунды вокруг сохранения. Пять секунд простоя выбраны так, чтобы серия
автосохранений во время набора текста шла одним писателем и не пересоздавала его на каждое
сохранение.

Цифры (`search/benches/indexing.rs`, 1000 заметок, release): сохранение одной заметки 48,9–50,2 мс
при живом писателе, как и до правки (49,6–52,5), и 52–62 мс после простоя, когда писателя нужно
создать. Потоки живого приложения: 54–56 без гостевой базы и 67–72 с гостевой → 38 в обоих случаях.

Бюджет писателя — 256 МБ на все его потоки (`INDEX_MEMORY_BUDGET`). Каждому потоку индексации нужно
не меньше 15 МБ, и бюджет в 50 МБ однажды оставил пул почти без рабочих. Это верхняя граница арен,
а не выделение при старте: память занимается, только пока идёт запись.

Побочный выигрыш — блокировка индекса (`.tantivy-writer.lock`) держится только пока жив писатель.
Все переходы индекса между слотами ([[mcp-guest-workspace]]) и так сериализованы `prepare_lock`,
но короткая блокировка убирает целый класс гонок за неё.

Что сломается, если вернуть вечного писателя: ничего функционально, но каждая открытая база снова
будет держать 13 спящих потоков и арены памяти. Что сломается, если отпускать писателя сразу после
каждого коммита: каждое автосохранение будет заново поднимать 13 потоков и ждать слияний.

#### Из чего складываются 50 мс сохранения и почему их не трогаем

Разбивка одной записи (`benchmark_save_breakdown`, release, медиана из семи): разбор и запись в
индекс 8,4–8,8 мс, **коммит tantivy 35–38 мс**, перечитывание индекса 3–5 мс, коммит SQLite 1 мс,
`maintain` (вакуум и чекпоинт WAL) 2 мс.

Проверенные и отвергнутые гипотезы про коммит tantivy:

- *Перезапуск потоков индексации.* `prepare_commit` действительно останавливает и заново поднимает
  все потоки писателя, но пустой коммит с тем же перезапуском стоит 2,7–3,5 мс.
- *Хэш-таблица потока, размер которой зависит от бюджета памяти.* Коммит одной заметки стоит
  35–42 мс при любом числе потоков (1, 2, 8) и любом бюджете (15–256 МБ). Зато меньшее число потоков
  замедляет полную индексацию: 1000 заметок — 343 мс на 8 потоках против 751–787 мс на одном.
  Нынешние настройки писателя верны.
- *Запись на диск.* Подтверждено: тот же коммит в индексе в памяти (`Index::create_in_ram`) стоит
  2,9 мс. Остальные ~33 мс — создание файлов сегмента с `fsync` каждого, атомарная запись
  метаданных и уборка старых файлов. Для сравнения, создание и синхронизация 9 небольших файлов на
  этом диске — 11,4 мс.

Выключать `fsync` для индекса не стали, хотя индекс — кэш, который можно перестроить из `.md`.
После сбоя питания он мог бы открыться битым, и понадобился бы код обнаружения и перестройки: это
сложность и риск ради 30 мс в фоновом потоке. Коммитить реже тоже незачем: автосохранение и так
раз в секунду, воркер склеивает события за 80 мс, а цена задержки — поиск позже видит правку. Эти
50 мс не блокируют ни ввод, ни интерфейс.

#### Воркер просыпается раз в 300 мс, и это оставлено

Цикл воркера ждёт сообщения с таймаутом 300 мс и в простое просыпается три раза в секунду. Замер
процессорного времени по потокам за 30 секунд простоя: воркеры индекса — 0 мс, ниже разрешения
системного таймера (15,6 мс). Переход на блокирующее ожидание потребовал бы будить воркер при
остановке: иначе `stop()` навсегда ждал бы поток в `recv`, а закрытие гостевой базы идёт под
`prepare_lock`. Плюс гонка «потерянного пробуждения» при переполнении очереди. Выигрыша не видно
даже в замере, а риск зависания реальный.

Читатель индекса создаётся с `ReloadPolicy::Manual`: единственный коммит в коде (`sync::commit`) сам
перечитывает индекс сразу после записи. Любой новый коммит обязан делать то же самое, иначе поиск
не увидит записанного.

## 6. Изменение, создание и переименование файла

Изменение из редактора сохраняется через `DocumentFileWriter` с debounce примерно 1 секунду. После успешной atomic write вызывается `notify_content_path`. Индексация идет не на каждый символ, а после сохранения файла.

Создание файла вызывает `notify_paths`. Переименование вызывает preflight link rewrite, физическое rename, затем уведомляет старый путь, новый путь и переписанные файлы. Внешние изменения ловит `notify` watcher.

Worker объединяет события за 80 ms. Обычное сохранение — `apply_paths` только по затронутым `.md` (не обход vault). Полный scan — при старте, dirty (переполнение очереди) или rescan директории. Temp atomic-write больше не триггерит full scan.

После индексирования worker эмитит `links-changed`. Frontend увеличивает revision, и sidebar заново запрашивает backlinks/outgoing/analysis. Пока запись только набирается в editor и еще не записана на диск, search и graph ее не видят. Это корректно: индексируется persisted состояние.

## 7. Индексный status

Надежный признак завершения первичного полного scan:

```text
state === "ready" && updating === false
```

`indexedDocuments` показывает число документов в Tantivy, `scannedDocuments` - сколько файлов просмотрено текущим scan. При открытии уже существующего cache status может быть `ready + updating=true`: старые результаты временно доступны, но идет проверка диска.

Важная текущая граница: `updating` описывает прежде всего полный scan. Небольшое incremental-применение события не переводит progress в отдельное состояние pending; frontend узнает о нем по событию `links-changed`, которое теперь содержит точные `workspacePath`, `generation` и `revision`. Для абсолютно точного UI используется именно счетчик `revision`.

## 8. SQLite-схема поискового cache

`documents`:

```sql
path TEXT PRIMARY KEY,
modified_ns INTEGER NOT NULL,
size INTEGER NOT NULL,
content_hash BLOB NOT NULL,
analyzer_version INTEGER NOT NULL DEFAULT 0,
created_ns INTEGER NOT NULL DEFAULT 0,
created_source INTEGER NOT NULL DEFAULT 0
```

`analyzer_version` хранится для каждой строки отдельно, а не одним значением на базу: если миграция анализатора прервана аварийным завершением, уже перенесённые файлы не переносятся повторно, и следующий запуск продолжает с места остановки.

`created_ns` и `created_source` — дата создания заметки и источник, из которого она получена. Их назначение, лестница источников и правило разрешения конфликтов описаны в [[graph-view]].

Версия схемы `documents` — `user_version = 12`. Ниже девятой версии база пересобирается с нуля, потому что старые формы `fingerprint` несовместимы; с девятой и выше применяются `ALTER TABLE`, и накопленные строки сохраняются. Это важно именно для `created_ns`: полная пересборка возвращает дату к выводу из файловой системы, а инкрементальная миграция сохраняет уже накопленное значение.

Каждый шаг лестницы миграций закрыт своей проверкой `if version < N`. Это не украшение: `ADD_CREATED_COLUMNS` когда-то выполнялся без такой проверки, и первый же подъём `SCHEMA_VERSION` выше 11 уронил бы открытие индекса повторным `ALTER TABLE`. Подробности и переиндексация ради полей frontmatter — в [[frontmatter-field-index]].

`probe` для каждого файла возвращает либо описание работы, либо признак пропуска. Пропуск означает одно из двух: файл не изменился при текущей версии анализатора, либо его метаданные не читаются. В обоих случаях строка в `documents` остаётся нетронутой.

`note_fields` — типизированные поля frontmatter, по одной строке на поле:

```sql
path TEXT NOT NULL,
ordinal INTEGER NOT NULL,
key TEXT NOT NULL,
key_lower TEXT NOT NULL,
kind INTEGER NOT NULL,
text TEXT NOT NULL,
text_lower TEXT NOT NULL,
items TEXT,
PRIMARY KEY(path, ordinal)
```

Ключ и значение дублируются в приведённом к нижнему регистру виде, потому что `lower()` в SQLite не знает кириллицы, а искать по `Путь к файлу` надо в любом написании. Модель значения, миграция и запасные дороги описаны в [[frontmatter-field-index]].

`wiki_documents`:

```sql
path TEXT PRIMARY KEY,
relative_key TEXT NOT NULL,
title_key TEXT NOT NULL
```

`wiki_links`:

```sql
source_path TEXT NOT NULL,
target_key TEXT NOT NULL,
target_kind TEXT NOT NULL,
byte_offset INTEGER NOT NULL,
offset_utf16 INTEGER NOT NULL,
PRIMARY KEY(source_path, byte_offset)
```

SQLite используется потому, что здесь нужны durable metadata, индексы по title/target, транзакционная замена ссылок одной заметки, быстрые backlinks и WAL для чтения во время записи. Полнотекстовый ranking выполняет Tantivy; SQL не конкурирует с ним и не нужен для BM25.

SQLite включается в WAL, `synchronous=NORMAL`, `busy_timeout=3000`, incremental vacuum и passive checkpoint.

## 9. Текущие corner cases

Уже закрыты: 
- deadlock read/write graph cache
- смешивание status разных workspace
- Windows `\\?\` path mismatch
- stale worker без join
- рассинхрон количества Tantivy/SQLite
- бесконечный editor loading после результата analysis
- graph cache теперь привязан к `(workspace, generation, revision)`
