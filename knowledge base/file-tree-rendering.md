# Перерисовка дерева файлов в сайдбаре

Статус: актуально на 2026-08-19.

Документ объясняет, почему переключение вкладки перерисовывало весь файловый список, и какой
инвариант теперь удерживает перерисовку в границах реально изменившихся строк. Ход всей работы по
скорости отрисовки, включая правки редактора и графа, записан в
[[render-performance-pass]].

## Связанные документы

- [[render-performance-pass]] — ход всей работы по скорости отрисовки.
- [[tab-switching]] — переключение вкладки было тем действием, на котором это вылезло.
- [[graph-view]] — та же причина в графе: он пересоздавался при уходе на другую вкладку.
- [[file-tree-live-updates]] — как дерево узнаёт об изменениях на диске и какие папки перечитывает.

## 1. Что показал профиль

Профилирование пяти переключений вкладки в dev-сборке дало INP 1357 мс и задачи по 941–2016 мс на
клик. В Bottom-up сверху стояли не функции приложения, а `createTask` (247 мс self),
`Run console task` (269 мс self) и `run` (272 мс self) — вместе больше половины кадра. Это
инструментация React 19 в dev-режиме: `jsxDEV` на каждый созданный элемент вызывает
`console.createTask()`, а компонент затем выполняется внутри `task.run(...)`, чтобы DevTools мог
показать асинхронный стек. В Event log это выглядело как тысячи записей `run` по 0–0.4 мс с
плотностью около двенадцати штук на миллисекунду.

Отсюда два вывода. Первый: в релизной сборке используется обычный `jsx`-runtime, поэтому этих
обёрток нет вообще — dev-профиль завышает абсолютные цифры, и часть их создаёт сам факт записи
профиля. Второй, важный: количество `run` — это количество отрендеренных компонентов, и оно
реально, в любой сборке. Тысячи рендеров на один клик по вкладке означали, что перерисовывается
всё дерево файлов, хотя измениться должны две строки: та, что перестала быть активной, и новая.

Полосой ниже в том же профиле висел `FileTreeRow` с 24 % общего времени, что подтверждало
адресата.

## 2. Пять причин, по которым `memo` не работал

`FileTreeRow` был обёрнут в `memo` с самого начала, но `memo` сравнивает пропсы по ссылке, и любой
нестабильный проп сводит его к нулю. На переключении вкладки таких пропсов было пять, независимых
друг от друга — поэтому починка любой одной ничего бы не изменила:

1. `buildVisibleFileRows` принимал `activeFile` и записывал в каждую строку поле `active`. Смена
   активного файла пересобирала весь массив строк.
2. Строка получала `guideLines: number[]` — массив направляющих линий. Даже при одинаковом
   содержимом каждая пересборка давала новый объект.
3. `Sidebar` сбрасывал выделение эффектом на смену `activeFile` через `setSelectedFiles(new Set())`
   безусловно. Новый пустой `Set` — это новое состояние, то есть второй проход рендера и новые
   идентичности всех колбэков, зависящих от выделения.
4. Три пропса передавались инлайн-стрелками прямо в JSX (`onCommitRename`, `onDeleteFile`,
   `onDuplicateFile`), то есть создавались заново на каждый рендер сайдбара.
5. `App` передавал `onFileSelect={(path) => openNote(path)}` — тоже новая функция на каждый рендер
   приложения, а `handleFileSelectWithMulti` в сайдбаре зависел ещё и от `rows`.

Дополнительно каждая строка держала смонтированный `Menu`, который в закрытом состоянии
возвращает `null`. Семьсот файлов давали семьсот бесполезных компонентов с `useId` и эффектом.

## 3. Как устроено теперь

Модель строк не знает про активный файл. `buildVisibleFileRows(roots, directories,
expandedFolders, loadingDirectories)` пересобирается только при структурном изменении дерева:
загрузка каталога, раскрытие или сворачивание папки, переименование, удаление.

Активность вычисляет `FileTree`: он приводит `activeFile` к сравнимому виду один раз и сверяет с
полем `comparableId` каждой строки. Так смена активного файла меняет проп `active` ровно у двух
строк.

Направляющие линии переехали из массива в примитив: `guideDepths: string` — список глубин через
запятую (`''`, `'0'`, `'0,1'`). Примитив сравнивается по значению, поэтому пересборка массива
строк больше не ломает `memo` у строк, чьё содержимое не изменилось. Разбирает строку
`parseGuideDepths` в момент отрисовки направляющих.

Сброс выделения возвращает прежний `Set`, если выделение уже пусто, — лишний проход рендера
исчез. `selectedCount` теперь равен размеру выделения только для строк, реально попавших в
мультивыделение, и единице для остальных; побочно это исправило подпись перетаскивания, которая
показывала «3 заметок» при волочении невыделенного файла.

`Menu` монтируется только открытым (`canRowActions && menu.open`), а его пункты собираются в тот
же момент.

Все колбэки, доходящие до строки, стабильны по ссылке. Для этого добавлен
`hooks/useStableCallback.ts`: он держит последнюю версию функции в ref, обновляет её в
`useInsertionEffect` и возвращает навсегда неизменную обёртку. Это единый механизм для такой
задачи в проекте — отдельных «ref-руками» решений заводить не нужно.

Логика сайдбара разъехалась по ответственностям, чтобы `Sidebar.tsx` вернулся к ориентиру проекта:

| Файл | Ответственность |
|---|---|
| `Layout/Sidebar.tsx` | композиция панели |
| `Layout/useFileSelection.ts` | выделение: одиночное, `Ctrl`, `Shift`-диапазон, якорь |
| `Layout/useFileTreeActions.ts` | переименование, дублирование, удаление с подтверждением — одинаково для файла и папки |
| `Layout/SidebarFooter.tsx` | подвал с базой знаний и настройками |
| `Layout/fileTreeModel.ts` | плоский список видимых строк и контракт действий |
| `Layout/FileTree.tsx` | активная строка и раскладка строк |
| `Layout/FileTreeRow.tsx` | строка: иконка, перетаскивание, контекстное меню |
| `Layout/FileTreeRename.tsx` | поле ввода нового имени |

Десять колбэков строки не протягиваются по одному через два компонента: они собраны в один объект
`FileTreeActions` (описан в `fileTreeModel.ts`). Каждый хук отдаёт свою часть уже мемоизированной
(`selectionActions`, `fileActions`), а `Sidebar` сливает их с операциями над папками в один
`treeActions`. Объект стабилен по ссылке, поэтому `memo` строки сравнивает один проп вместо
двадцати. Обратная сторона: если этот объект когда-нибудь начнут пересоздавать на каждый рендер,
перерисовываться будут сразу все строки — именно это и ловит тест из следующего раздела.

Сравнение пути активного файла не выполняется для каждой строки заново: `comparablePath` считается
один раз при построении строки и лежит в поле `comparableId`.

Со стороны `App` инлайн-стрелки заменены на стабильные обработчики: состояние модальных окон
живёт в `hooks/useOverlay.ts` (`open`/`show`/`hide`/`toggle`), а `onFileSelect` получает `openNote`
напрямую. Благодаря этому `Sidebar` обёрнут в `memo` и полностью пропускает рендер, когда
приложение перерисовывается по не касающимся его причинам — например, при росте ревизии индекса
ссылок после сохранения заметки.

## 4. Инвариант и его тест

Правило, которое нужно удерживать при любых правках сайдбара: **пропсы `FileTreeRow` меняются
только тогда, когда изменилась сама строка.** Практически это значит — никаких объектов и массивов
в пропсах строки, никаких колбэков, пересоздаваемых на рендер, и никакой зависимости модели строк
от того, какой документ открыт.

Инвариант закреплён тестом `Layout/FileTree.test.tsx`. Он мокает `parseGuideDepths` и считает
вызовы: функция выполняется один раз на рендер строки, поэтому число вызовов — это счётчик
перерисовок. Тест монтирует сорок строк, меняет активный файл и требует ровно два дополнительных
рендера. Если очередная правка вернёт нестабильный проп, тест покажет сорок вместо двух.

## 5. Действия над строкой: файл и папка

Контекстное меню одно и то же для заметки и для папки: «Переименовать», «Дублировать», «Удалить».
Открывается оно, когда строка — папка или markdown-файл (`canRowActions` в `FileTreeRow`); прочие
файлы меню не получают, потому что приложение ими не управляет.

Различие файла и папки нигде не хранится отдельным флагом: его всюду решает `isMarkdownPath`.

**Удаление** дерево только запускает: `trashFile` уводит заметку или папку в корзину базы
([[trash]]). Всё остальное — закрыть вкладки и документы удалённых заметок, стереть их реплики и
записи синхронизации — делает один обработчик события `notes-relocated`, которое шлёт шлюз
изменений ([[notes-gate]]). Заметки внутри удалённой папки шлюз перечисляет сам, до удаления.

**Переименование.** Заметка идёт через `renameWorkspaceFile` с переписыванием вики-ссылок; папка —
через `renameFolder`, который ссылок не трогает, потому что ссылки в базе адресуют заметку по имени,
а не по пути. Вкладки и открытые документы заметок едут на новые пути по тому же событию
`notes-relocated`, что и при перетаскивании и переименовании через MCP.

**Перетаскивание.** Слушатели висят на контейнере дерева, а не на каждой строке: строка опознаётся
по `data-file-id` всплывшего события, подсветка цели ставится атрибутом прямо в DOM. Можно ли
бросить, решает одна функция `canMove`: папку нельзя перенести в саму себя или внутрь себя, а файл —
туда, где он уже лежит. Сам перенос — `moveIntoFolder`: пробует прежнее имя и при `already_exists`
берёт следующее `имя (1)`, `имя (2)` — тем же способом, что `createUniqueFile`. Раньше свободное имя
подбиралось заранее по одному запросу существования, проверялось только исходное имя, и если
`имя (1)` уже было, перенос падал. Перебор по ошибке конфликта ещё и атомарен: между проверкой и
переносом место никто не займёт.

Перебор живёт в одном месте — `claimNumberedPath` в `modules/paths.ts`: он строит `имя (N).ext`,
пробует «занять» кандидата переданной операцией и идёт дальше только по ошибке конфликта; любая
другая ошибка выходит наружу сразу. Перебор ограничен тысячей попыток и после них бросает ошибку —
бесконечный цикл на сломанной файловой системе (например, конфликт, который возвращается на любое
имя) больше невозможен.

**Раскрытость едет вместе с папкой.** Раскрытые папки хранятся списком путей
(`useExpandedFolders`). Переименование и перенос папки меняют её путь, и без поправки папка
сворачивалась, а под старым путём оставалась мёртвая отметка. Оба пути — `commitRename` и
перетаскивание — вызывают `followFolder(from, to)`, который переносит отметки самой папки и всех
вложенных (`rebasedPath` из `modules/paths`). Для заметки вызов ничего не меняет, поэтому ветвления
«папка или файл» нет. Отметка удалённой папки намеренно остаётся: по ней папка, возвращённая из
корзины, снова открывается раскрытой ([[file-tree-live-updates]]).

**Дублирование.** Копия получает имя по той же схеме, что перенос: `Заметка (1).md`, `Заметка (2).md`,
папка — `Папка (1)`, через тот же `claimNumberedPath`, начиная с номера 1. Раньше у дублирования была
своя схема `Заметка 1.md` без скобок и свой неограниченный цикл: две операции дерева называли
конфликтующие копии по-разному. Папка копируется рекурсивно на стороне Rust. Удаление без открытой
базы ничего не делает: проверка `workspacePath` стоит до цикла, а не внутри каждой итерации.

Со стороны Rust папку понимают три места: `rename_file_impl` переименовывает каталог через
`fs::rename` вместо жёсткой ссылки (ею каталог связать нельзя), `copy_file_impl` уходит в
`copy_directory_impl`, а `rename_with_links` для каталога сразу переименовывает и возвращает пустой
результат — у каталога нет ни текста, ни снимка. Перенос папки в корзину со всем содержимым закреплён
тестом `a_folder_moves_to_the_trash_with_everything_inside`.

## 6. Пустое дерево

База открыта, а заметок в ней нет — самый частый первый шаг нового пользователя. `FileTree` просто перебирает строки, поэтому ноль строк давал пустую панель без единого слова. Теперь на этом месте стоит `EmptyState` с кнопкой создания заметки.

Создаёт заметку та же `createNewFile` из `useTabs`, что и пустая вкладка с горячей клавишей: второго пути создания в сайдбаре не появилось. Надпись кнопки тоже общая — `editor.createNote`.

Состояние показывается только при `treeReady`, то есть после того как корень базы уже прочитан. Иначе «пока ни одной заметки» мигало бы на каждом открытии базы, пока читается папка.

## 7. Чего здесь нет

Виртуализации списка нет — **это не реализовано, а описано как направление.** Сейчас `FileTree`
создаёт React-элемент для каждой видимой строки дерева, то есть для всех файлов раскрытых папок,
даже если в окно попадает сорок строк. После описанных правок сами компоненты при переключении
вкладки не рендерятся, но элементы создаются, и стоимость по-прежнему пропорциональна размеру
базы знаний, а не высоте окна.

Правильным следующим шагом будет отрисовка только видимого окна строк с запасом сверху и снизу.
При этом придётся учесть места, которые сейчас опираются на присутствие всех строк в DOM:
прокрутка к активному файлу в `Sidebar` ищет элемент по `[data-file-active="true"]`, а
перетаскивание слушает события на элементах строк.

## 8. Значки и цвета файлов

Iconize хранит назначение значка и цвета в `settings.json` внутри настроек встроенных функций,
с отдельной картой для каждого рабочего пространства. Это общее состояние приложения и должно
переживать переключение между dev и установленной сборкой; `localStorage` не является источником
этих данных.

При переименовании или переносе файла либо папки `rebaseFileIcons` переносит соответствующие
записи вместе с путём. При отключённой функции назначения остаются сохранены, но дерево их не
показывает. Сброс назначения удаляет запись, а не сохраняет фиктивное значение по умолчанию.
