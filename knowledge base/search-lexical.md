# Лексический поиск: что реально работает

Статус: актуально на 2026-10-22. Документ отвечает за глобальный поиск и за то, что из него
следует для похожих заметок и дублей. Устройство индекса и переключение хранилищ —
[[search-indexing-workspaces-part-1]], Adamic-Adar и BM25F-анализ — [[search-indexing-workspaces-part-2]].

## 1. Никаких моделей

Поиск не использует эмбеддинги. Модули `search/semantic.rs` (fastembed + quantized MiniLM) и
`search/hybrid.rs` (reciprocal rank fusion) удалены 22.10.2026: их никто не вызывал,
`SearchService::search` шёл напрямую в Tantivy. Вместе с ними ушли зависимость `fastembed` и её
дерево (`ort`, `tokenizers`, `hf-hub`), 1417 строк `Cargo.lock` и обещание скачать модель при первом
запросе.

Практические следствия: поиск работает офлайн с первого запуска, не занимает диск каталогом модели,
не тратит RAM на векторы и не имеет «первого медленного запроса». Взамен нет синонимии «по смыслу»:
синонимы появляются только из пользовательского словаря (раздел 5).

## 2. Что лежит в индексе

Схема Tantivy (`core/src/search/schema.rs`): `id` (абсолютный путь, `STRING|STORED`), `path`
(относительный путь через `/`), `title` (имя файла без расширения), `body` (текст заметки). Поля
`path`, `title`, `body` индексируются с частотами, `title` и `body` хранятся для сниппетов.

Токенайзер один и тот же для индексации и для запроса (`analyzer/pipeline.rs`,
`ANALYZER_VERSION = 12`): санитайз (срезает URL, оставляет подписи ссылок), `RemoveLongFilter(120)`,
`LowerCaser`, `AsciiFoldingFilter`, собственный `StemFilter` (Snowball RU или EN по письменности
слова, только слова от 4 символов и только в одном алфавите), затем фильтр мусорных терминов.
Версия анализатора входит и в имя каталога индекса, и в `documents.sqlite3`: смена токенайзера
сама по себе выбрасывает старый индекс и запускает однократную переиндексацию.

Теги, задачи, ссылки и поля frontmatter лежат **не в Tantivy, а в `documents.sqlite3`**
(`fields/`, `tasks/`, `wiki/`). Отсюда важное ограничение: полнотекстовый ранжировщик их не видит,
пока запрос не соединит оба источника.

## 3. Как строится запрос (`core/src/search/query.rs`)

1. Запрос проходит тот же анализатор, что и документы, поэтому «машины» ищутся по основам.
2. Каждый терм становится `Should`-ветвью по трём полям: `title` с бустом 5, `path` с бустом 2,
   `body` с бустом 1.
3. Термы объединены через `BooleanQuery::with_minimum_required_clauses(..., 1)`, то есть по «ИЛИ»:
   шесть слов в запросе не обнуляют выдачу. Это осознанно — ранжирование разбирается с частичным
   совпадением (`[[Улучшения на будущее 28.08.2026]]`, пункт 1).
4. Для термов от 2 символов добавляется `FuzzyTermQuery::new_prefix` (исправление опечаток и
   префиксный поиск); расстояние Левенштейна включается только с 5 символов. Поверх идёт набор
   точных совпадений с двойным бустом — он и решает исход.
5. Tantivy отдаёт до `limit` (по умолчанию 50, максимум 100) документов по score.

Результат (`SearchResult`) содержит `snippet`, `heading` (заголовок раздела, в котором найдено
первое совпадение), `matchOffset`, `matchCount` и `matchedTerms` — то есть у интерфейса уже есть
материал для объяснения совпадения, даже если карточка показывает не всё.

## 4. Что ищется помимо текста

- **Структурные выборки** — язык `dataview` в Rust: `FROM` (папка, `#тег`, `[[заметка]]`,
  `outgoing`) + `WHERE`/`SORT`/`GROUP BY`/`FLATTEN`/`LIMIT`, формы `TABLE`/`LIST`/`TASK`
  ([[dataview-queries]]).
- **Поля frontmatter** — таблица `note_fields` в SQLite, индексируется по значению и по спискам
  (`fields/query.rs`), там же `paths_with_tag`.
- **Ссылки** — `wiki_links` + разрешение целей (`wiki/`), отсюда backlinks, outgoing, граф.
- **Задачи** — `note_tasks`, отсюда `TASK`-запросы и отметка выполнения в исходной заметке.

## 5. Синонимы и пользовательский словарь (план P0-3)

Статус: не реализовано. Ниже — договорённость о том, как это будет устроено.

`SearchIndexSettings` в `core/src/settings/models.rs` получит `synonymGroups: string[][]` —
список групп, внутри группы слова равноправны. Группа разворачивается в запросе: вместо термина
подставляется `Should`-ветка из всех её членов с тем же бустом. Словарь живёт в `settings.json`
(не в индексе), поэтому его правка не требует переиндексации и действует сразу.

Ограничение: словарь — это ручное сопоставление, а не вывод «по смыслу». Автоматического вывода
синонимов из корпуса нет; если он появится, это будет отдельный механизм с сохранением
предложений, а не скрытая подмена лексики.

## 6. Фильтры в одном интерфейсе (план P0-4)

Статус: не реализовано.

Поле поиска будет принимать префиксные фильтры до текста запроса: `tag:книги`, `folder:Проекты`,
`ext:md`, `title:план`. Фильтр сужает кандидатов, остальное — обычный лексический запрос. Разбор
фильтров живёт в `core/src/search/query.rs`, поэтому одинаково работает в приложении, в MCP и в
CLI. Неизвестный префикс считается частью текста запроса, а не ошибкой.

## 7. Похожие заметки, дубли и непривязанные упоминания (план P0-6)

Статус: похожие (BM25F) и структурно близкие (Adamic-Adar) работают; дубли и непривязанные
упоминания — нет.

- **Похожие** — BM25F-анализ (`analysis/bm25f`): 64 самых информативных терма исходной заметки,
  пул 256 кандидатов, академический BM25F по `title`/`body`. Плюс Adamic-Adar по графу ссылок.
- **Дубли** — тот же пул кандидатов, но с порогом по «почти одинаковости»: пересечение шинглов
  (нормализованные термы) и близкая длина. Никакой второй индекс не строится.
- **Непривязанные упоминания** — заметки, в тексте которых встречается заголовок (или алиас)
  текущей заметки, но ссылки `[[...]]` на неё нет.

Все три живут на том же индексе и вызываются по запросу пользователя, а не фоном: постоянных
вычислений в приложении нет.
