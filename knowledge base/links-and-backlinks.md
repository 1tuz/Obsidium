# Ссылки и обратные ссылки в Aquilum

## Назначение

Aquilum поддерживает внутренние ссылки между Markdown-заметками в формате Obsidian:

```md
[[Заметка]]
[[Заметка|видимый текст]]
```

Markdown-файл остается источником истины. В файл записывается исходный текст со скобками, а скрытие синтаксиса, цвет и состояние ссылки существуют только как декорации CodeMirror.

Внутренние ссылки на заголовки и блоки пока не поддерживаются. Конструкции `[[Заметка#Раздел]]` и `[[Заметка^блок]]` не имеют специальной семантики.

## Синтаксис

`[[Заметка]]` содержит имя целевой заметки. В live preview отображается `Заметка`, а обе пары скобок скрываются, когда курсор находится вне ссылки.

`[[Заметка|видимый текст]]` содержит цель слева от `|` и alias справа. В live preview отображается **только** `видимый текст`. Цель, разделитель и скобки скрываются через `Decoration.replace` в `collectCollapseRanges` (`livePreviewPlugin.ts`). Каретка внутри ссылки раскрывает полный `[[цель|alias]]`.

Инвариант alias (регрессия: `livePreviewCollapse.test.ts`):

| Каретка | Видимо в редакторе |
| --- | --- |
| вне `[[…\ | …]]` |
| внутри `[[…\ | …]]` |
<!--q-table:{"merges":[],"cols":[202,311]}-->

Нельзя оставлять `WikiLinkTarget` видимым при наличии alias — иначе получается склеенный текст вроде `совестьсовести` (типичный баг при правках collapse-механизма).

Пустая цель не считается ссылкой. Ссылка не может продолжаться через перевод строки. Незакрытая конструкция не мешает распознаванию следующих корректных ссылок.

Wikilink внутри inline-кода, блока кода или HTML не индексируется как связь между заметками.

## Live preview

Wikilink добавлен в Lezer Markdown как отдельные узлы:

```text
WikiLink
WikiLinkMark
WikiLinkTarget
WikiLinkAliasMark
WikiLinkAlias
```

Скрытие обычного Markdown и wikilink выполняет один [livePreviewPlugin.ts](../obsidium-app/src/components/Editor/extensions/livePreviewPlugin.ts). Видимое синтаксическое дерево обходится один раз на изменение документа, selection или viewport.

Плагин одновременно:

- скрывает служебные маркеры Markdown;
- применяет правило `isMarkdownSyntaxActive`;
- собирает уникальные цели wikilink только из видимого диапазона;
- добавляет оформление отсутствующим целям после пакетного разрешения.

Отдельного второго preview-плагина для ссылок нет. Preview списков остается в `outline/preview.ts`, поскольку он владеет другими диапазонами и заменяет маркеры списков виджетами.

Декорации не изменяют `EditorState.doc`, Yjs или Markdown-файл.

## Навигация

Для исходящей wikilink действуют правила:

| Действие | Результат |
|---|---|
| обычный клик | заметка открывается в текущей вкладке |
| `Ctrl` + клик | заметка открывается в новой вкладке |
| `Cmd` + клик на macOS | заметка открывается в новой вкладке |

Нажатие перехватывается на `mousedown`, до стандартной обработки CodeMirror. Поэтому модифицированный клик не переносит курсор внутрь ссылки перед навигацией.

Если целевой документ уже открыт, менеджер вкладок активирует существующую вкладку вместо создания дубликата.

Обратные ссылки используют ту же модель: обычный клик открывает источник в текущей вкладке, `Ctrl/Cmd` + клик открывает его в новой. После открытия редактор переходит к позиции соответствующей ссылки.

Обычные web-ссылки Markdown вида `[текст](https://example.com)` не участвуют во внутреннем графе. Их существующее поведение остается отдельным от wikilink.

## Разрешение цели

Перед поиском цели Aquilum:

1. Убирает пробелы по краям.
2. Заменяет `\` на `/`.
3. Убирает расширение `.md` без учета регистра.
4. Сравнивает ключи без учета регистра.

Цель без `/` сопоставляется с именем файла без расширения. Цель с `/` сопоставляется с путем относительно корня хранилища.

Примеры:

```text
[[План]]            -> файл с именем План.md
[[План.md]]         -> файл с именем План.md
[[Проекты/План]]    -> <workspace>/Проекты/План.md
```

Если заметок с одинаковым именем несколько, выбор выполняется последовательно:

1. Файл в той же папке, что и исходная заметка.
2. Файл с наименьшей глубиной относительно корня хранилища.
3. Лексикографически первый полный путь для стабильного результата.

Для предсказуемого графа рекомендуется использовать уникальные имена или явно указывать относительный путь от корня.

## Отсутствующие цели

После завершения индексации неразрешенная wikilink остается синей, но отображается с opacity `0.6`.

Клик по такой ссылке создает пустой Markdown-файл:

- обычный клик создает файл и открывает его в текущей вкладке;
- `Ctrl/Cmd` + клик создает файл и открывает его в новой вкладке.

Имя создается без числового суффикса. Если файл появился между разрешением ссылки и созданием, ошибка `already_exists` трактуется как успешная гонка, и существующий файл открывается.

Создание выполняется только тогда, когда цель можно преобразовать в точный безопасный путь без изменения имени. Запрещенные символы, зарезервированные Windows-имена, пустые сегменты и `..` не преобразуются в другое имя, поскольку после такого преобразования исходная ссылка осталась бы неразрешенной.

Простая цель создается в корне хранилища. Цель с путем создается по указанному пути, если родительская папка уже существует. Автоматическое создание отсутствующих папок пока не выполняется.

Во время первичной индексации отсутствие строки в частично заполненном кэше не считается доказательством отсутствия файла. Такая ссылка временно не получает полупрозрачный стиль и не создает заметку. После завершения сканирования событие ревизии повторно разрешает видимые цели. Это предотвращает создание дубликатов в больших хранилищах.

## Обратные ссылки

Обратная ссылка является записью о том, что одна заметка содержит wikilink на текущую заметку.

Панель показывает:

- имя исходного документа;
- строку текста, в которой находится ссылка;
- переход к позиции ссылки;
- не более 200 результатов;
- счетчик `200+`, если существуют дополнительные результаты.

Для неоднозначных коротких имен панель применяет те же правила выбора цели, что и исходящая ссылка. Совпадение текста `[[Имя]]` само по себе недостаточно: ссылка должна фактически разрешаться в открытый документ.

SQL-результаты читаются страницами по 256 строк, пока не найдено 201 действительное совпадение или пока выборка не закончится. Это не дает неоднозначным одноименным ссылкам преждевременно заполнить лимит.

Тексты источников читаются по одному в порядке пути. В памяти хранится тело только текущего файла, а не до 200 полных Markdown-документов одновременно.

В БД хранятся два смещения:

- byte offset используется для получения строки контекста из UTF-8 Markdown;
- UTF-16 offset используется для установки позиции CodeMirror.

В `useDocumentLinks` (как и в `useDocumentAnalysis`: оба — тонкие обёртки над общим `hooks/useDocumentQuery.ts`) ревизия индекса входит в ключ запроса, но не в ключ кэша: смена `indexRevision` перезапрашивает связи, а показанный список остаётся на экране до ответа, потому что результат сверяется только по `cacheKey` (режим, база, заметка). Будь ревизия частью идентичности кэша, каждая переиндексация давала бы промах, и панель мигала бы пустым состоянием.

## Переименование заметки

Переименование через inline-заголовок документа запускает одну файловую операцию, которая включает обновление входящих wikilink.

Для `Old.md -> New.md`:

```md
[[Old]]          -> [[New]]
[[Old|текст]]    -> [[New|текст]]
[[Folder/Old]]   -> [[Folder/New]]
![[Folder/Old#Section]] -> ![[Folder/New#Section]]
[text](../Folder/Old.md#section) -> [text](../Folder/New.md#section)
```

Alias и heading/URL fragments сохраняются. Markdown destinations пересчитываются относительно папки
источника и сохраняют `.md`; ссылки в YAML, fenced code и plugin markup не переписываются. CRLF
источника сохраняется после обновления ссылок.

Когда индекс завершен, кандидаты на изменение берутся из обратного индекса. Поэтому переименование не сканирует все хранилище.

Если первичная индексация еще идет, Aquilum один раз перечисляет Markdown-файлы и отдельно вычисляет все одноименные кандидаты из файловой системы. Частично заполненная БД не используется для разрешения неоднозначного имени. Это исключает ошибочное обновление ссылок при переименовании в большом хранилище.

Перед изменением проверяются BLAKE3-хеши всех файлов-кандидатов. Если любой файл изменился после подготовки плана, переименование отменяется до изменения имени заметки.

Последовательность операции:

```text
построить план
-> проверить хеши всех источников
-> переименовать целевой файл
-> атомарно переписать ссылки
-> при ошибке откатить переписанные файлы
-> вернуть исходное имя целевой заметке
```

Yjs/IndexedDB-кэш очищается только для документов, которые действительно были переписаны во время rename. Открытые вкладки получают новый путь через общий обработчик rename.

### Переименование, отличающееся только регистром

Само переименование файла (`rename_file_impl` в `files/document.rs`) идет через `hard_link` плюс удаление источника, а не через `rename`: так целевой файл нельзя перезаписать молча, а занятое имя честно возвращает `already_exists`.

На регистре это ломалось. Файловая система Windows и macOS нечувствительна к регистру, поэтому `hard_link("note.md", "Note.md")` считает, что цель уже существует, и возвращает ту же ошибку `already_exists`, что и настоящий конфликт имен. Дальше по цепочке `isRenameConflict` в UI откатывал имя обратно, а до переписывания ссылок дело не доходило вовсе: заглавная буква не сохранялась, в бэклинках тоже ничего не менялось.

Поэтому для случая, когда старый и новый путь различаются только регистром, вызывается прямой `fs::rename` — на нечувствительной ФС это поддерживаемая операция смены регистра. Ветка включена на Windows и macOS. На Linux, где `Note.md` может быть отдельным реальным файлом, поведение прежнее, иначе `rename` затер бы чужой файл.

Планировщик ссылок при этом менять не пришлось: `same_path` (`search/paths.rs`, см. [[paths-and-file-names]]) сравнивает пути без учета регистра, поэтому план переписывания строился правильно и раньше — он просто не выполнялся.

## Изменение и удаление текста

При сохранении измененной заметки индексирование источника выполняется транзакционно:

```text
обновить запись документа
-> удалить все старые исходящие связи этого источника
-> извлечь актуальные wikilink
-> вставить актуальные связи
-> commit
```

Поэтому удаленная из текста ссылка исчезает из обратных ссылок после обработки файлового события. Старые позиции и фрагменты не накапливаются.

При удалении файла удаляется запись `wiki_documents`. Внешний ключ с `ON DELETE CASCADE` удаляет все исходящие связи удаленного источника.

Входящие ссылки из других документов сохраняются. Их цель становится отсутствующей, отображается полупрозрачной и может заново создать заметку по клику. Это соответствует тому, что исходный Markdown других заметок не изменяется при удалении цели.

Полное сканирование дополнительно удаляет записи документов, которых больше нет на диске. Удаление папки или переполнение очереди watcher запускает безопасное полное согласование.

## Зачем используется SQLite

SQLite не является хранилищем заметок и не заменяет Markdown. Это удаляемый локальный reverse-index cache.

Без обратного индекса открытие панели backlinks или переименование заметки требовало бы читать и разбирать до 100 000 файлов при каждом действии. SQLite позволяет получить кандидатов по двум индексированным ключам и затем проверить только релевантные документы.

Основные таблицы:

| Таблица | Назначение |
|---|---|
| `documents` | fingerprint файла: путь, время изменения и размер |
| `wiki_documents` | нормализованный путь и имя заметки |
| `wiki_links` | источник, нормализованная цель и смещения |

Исходный текст цели в `wiki_links` не дублируется. Таблица использует составной первичный ключ `(source_path, byte_offset)` и `WITHOUT ROWID`. Отдельный индекс по источнику не нужен, поскольку удаление связей использует префикс первичного ключа.

Индекс `(target_kind, target_key)` обслуживает backlinks и поиск кандидатов для rename.

## Жизненный цикл индекса

После открытия хранилища индекс запускается в отдельном Rust-потоке. UI и редактор не ждут завершения полного сканирования.

Первичное сканирование:

1. Рекурсивно перечисляет видимые Markdown-файлы без перехода по symlink.
2. Сравнивает `modified_ns` и размер с сохраненным fingerprint.
3. Не читает неизмененные файлы повторно.
4. Для измененного файла один раз читает Markdown, обновляет поисковый индекс и извлекает wikilink.
5. Делает commit каждые 2000 документов.
6. Удаляет устаревшие записи.

Watcher объединяет события в окно 80 мс. Очередь ограничена 2048 сообщениями. При переполнении ставится флаг dirty и выполняется полное согласование вместо потери изменений.

Frontend получает событие `links-changed`. Номер ревизии пересоздает локальный кэш разрешения видимых ссылок и обновляет backlinks. Отдельных слушателей для редактора и панели нет.

## Разрешение видимых ссылок

Live preview не делает IPC-вызов для каждой ссылки.

За один проход он собирает `Set` уникальных целей в текущем viewport и отправляет один пакетный вызов Rust. Rust открывает одно read-соединение SQLite и повторно использует два prepared statement: по имени и по относительному пути.

Результаты кэшируются внутри текущего экземпляра редактора. Изменение selection перестраивает декорации, но не повторяет SQL для уже известных целей. Смена ревизии индекса создает новый кэш.

Стоимость оформления зависит от видимого диапазона, а не от общего размера открытого документа или хранилища.

## Обслуживание и размер БД

Текущая версия схемы кэша: `6`.

Настройки SQLite:

```text
journal_mode = WAL
synchronous = NORMAL
foreign_keys = ON
auto_vacuum = INCREMENTAL
wal_autocheckpoint = 1000
journal_size_limit = 32 MiB
busy_timeout = 3000 ms
```

После изменяющих транзакций выполняется пассивный WAL checkpoint. Свободные страницы возвращаются порциями `incremental_vacuum(256)`, поэтому обычное редактирование не вызывает долгий полный `VACUUM`.

Миграция на новую схему удаляет только индексные таблицы, очищает fingerprints, выполняет одноразовый `VACUUM` и запускает повторную индексацию. Markdown-файлы не затрагиваются.

БД можно удалить при закрытом приложении. При следующем открытии она будет создана заново из Markdown. Это допустимый способ восстановления кэша, но не способ восстановления самих заметок.

## Ограничения текущей версии

- Нет ссылок на заголовки и блоки.
- `![[Заметка]]` и `![[Заметка#Заголовок]]` отображаются read-only вложением; вложенные embeds не раскрываются. Подробности — [[note-transclusion]].
- Папки для отсутствующей path-ссылки автоматически не создаются.
- Переименование или удаление файла вне Aquilum отражается индексом, но внешнее переименование не переписывает Markdown-ссылки автоматически.
- Внутренними навигационными ссылками считаются только wikilink; Markdown URL обслуживаются отдельным механизмом.
