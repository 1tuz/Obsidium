# Синхронизация страницы книги, виджетов и ссылок

## Контуры консистентности

### Открытая страница книги → `[!book]`

`useEditorBookPage` публикует валидный frontmatter в `bookPageRuntime`. Runtime хранит ограниченный LRU-кеш на 64 книги и уведомляет только подписанные смонтированные widgets.

Мгновенно, без файлового чтения и поискового индекса обновляются:

- название страницы из имени файла;
- автор;
- страницы и прогресс;
- обложка книги;
- путь к файлу книги и доступность кнопки чтения.

Прогресс сначала публикуется в memory bus, затем coalesced-очередь `persistBookReaderMeta` сохраняет последнее состояние. Параллельные записи одной книги не запускаются: новые поля объединяются в `latest`, а `drain` дописывает только актуальный snapshot.

Закрытый widget ничего не слушает. При следующем монтировании данные берутся из runtime cache.

### Данные связанных книг собираются до отрисовки

Строка `[!book]` со вики-ссылкой не знает ни автора, ни обложки: они лежат во frontmatter связанной
страницы. Раньше каждая строка добывала их сама — `IntersectionObserver` на строку, затем разрешение
ссылки и чтение данных, — поэтому виджет успевал нарисоваться дважды: сперва с пустой обложкой, потом
с настоящей. На двадцати книгах это сорок круговых вызовов, каждый со своим кадром перерисовки.

Теперь данные собирает один проход на документ (`bookCallout/prefetch.ts`): все вики-цели уходят
одним `resolve_wiki_links`, все пути — одним `get_note_fields`, после чего обложки прогреваются
через `new Image()`, и только затем эффект `bookCalloutDataReady` пересобирает декорации. Оба
бэкенд-метода принимают списки, поэтому цена не зависит от числа книг на странице: два круга вместо
двух на строку.

Строка, данных для которой ещё нет, рисуется пустой заготовкой
`.q-md-book-callout--pending` в высоту готовой строки. Это сознательный выбор: заготовка держит
раскладку и не показывает ничего неверного, тогда как строка с пустой обложкой показывает
неправильное состояние, которое затем меняется на глазах.

Файл связанной заметки при этом не открывается вовсе — данные идут из индекса полей, см.
[[frontmatter-field-index]].

Проход запускается на создание редактора, на правку документа и на новую ревизию индекса
(`links-changed`). Последнее обязательно: без него правка книги в другой вкладке или внешним
редактором никогда не доехала бы до виджета, потому что разрешённая книга берётся из кеша. Проход по
ревизии перечитывает все строки, но пересобирает декорации только если данные действительно стали
другими — сравнивается подпись из названия, автора, обложки, пути к файлу и пути страницы.

Заводила самого прохода — общий с блоком запроса: `extensions/prefetchScheduler.ts` держит подписку
на ревизию, дебаунс, очередь прогонов и уборку, а книжная строка добавляет к этому только прогрев
обложек. Раньше это было написано дважды и успело разойтись; причина сведения — в
[[dataview-queries]].

Прогрев обложек ограничен таймаутом `COVER_WARMUP_TIMEOUT_MS` = 1500 мс: ждать дольше значит держать все строки заготовками из-за одного нечитаемого файла. Обложка, уже лежащая в кеше браузера, рисуется в том же кадре, что и остальная строка. Окно дебаунса длиннее кадра печати, поэтому пачка правок даёт один запрос. Неразрешённая вики-ссылка кешируется без `bookPagePath` и пробуется заново на каждом проходе: заметка могла появиться только что. Если индекс ещё не готов, строки остаются заготовками до следующего прохода.

## Подпись решает, перерисовывать ли строку

Та же подпись — из названия, автора, обложки, пути к файлу и пути страницы — служит и виджету:
`BookCalloutGroupWidget.eq` сравнивает подписи своих строк. До этого он сравнивал **общий на
приложение счётчик поколений**, и любое изменение данных любой книжной строки документа делало
неравными все группы сразу — CodeMirror сносил и строил заново DOM каждой из них, включая загрузку
обложек. Тот же дефект в блоке запроса стоил рывков прокрутки, разобранных в [[dataview-queries]];
здесь он дешевле лишь потому, что книжные строки не пересчитывают себя по таймеру.

Что строки группы покажут, считается одной функцией `groupViewData` — и для подписи в конструкторе,
и для отрисовки в `toDOM`. Два отдельных прохода по элементам разошлись бы молча: подпись говорила
бы «не изменилось», а нарисовалось бы другое.

Позиции `from` и `to` из сравнения убирать нельзя, в отличие от блока запроса. Клик по строке ставит
каретку по `row.dataset.sourceFrom` — абсолютной позиции, записанной в момент отрисовки. Корректной
её держит именно то, что сдвиг позиций делает виджет неравным и заставляет перерисоваться.

### Файл с сырым нулевым байтом невидим для поиска

В `linkedCache.ts` разделителем подписи лежал **настоящий байт `0x00`** внутри строкового литерала,
а не escape-последовательность. Из-за этого `file` считал файл двоичным, а `grep` и `ripgrep` молча
его пропускали — поиск по проекту показывал, что символа нет нигде, хотя он был. Разделитель заменён
на `'\0'`: поведение то же, файл снова текстовый и находится поиском. Если такое повторится,
искать так: `python -c "print(b'\0' in open(path,'rb').read())"`.

### Переименование → wiki-ссылки → backlinks

Backend сначала строит план замен, проверяет hash всех источников, переименовывает target и атомарно переписывает wiki-targets. При любой ошибке применённые изменения откатываются.

После успешного rename:

1. открытые переписанные документы принимают disk snapshot в свой Yjs и новый writer hash;
2. для закрытых документов очищается IndexedDB snapshot;
3. search worker получает только изменённые пути;
4. после завершения batch публикуется новая revision;
5. backlinks/outgoing hooks отменяют устаревший запрос и загружают данные новой revision.

Backlinks поэтому имеют eventual consistency: UI обновляется после фонового индексирования, а не в той же транзакции rename. Worker обрабатывает точечный набор путей; полного обхода workspace при обычном rename нет.

## Границы

- Wiki alias сохраняется: `[[Old|видимый текст]]` становится `[[New|видимый текст]]`.
- Обычные Markdown-ссылки не являются wiki-backlinks и этим rename-процессом не переписываются.
- Runtime bus действует внутри текущего процесса приложения. Изменение frontmatter внешним редактором доезжает до виджета проходом по новой ревизии индекса, а не через memory bus.
- Гидратация связанной страницы читает индекс, а тот отстаёт от диска на проход воркера. Заметку, которой в индексе ещё нет, спасает запасная дорога — чтение первых 8 КБ файла на стороне Rust.
- Кеш гидратации не вытесняется по объёму, только обновляется по ревизии — см. TD-2 в [[tech-debt]].
- Название widget берётся из имени связанной страницы. Inline title в самом `[!book]` остаётся локальным fallback до разрешения ссылки.

## Производительность

- сбор данных книжных строк: два круговых вызова на документ независимо от числа книг;
- публикация runtime metadata: `O(число widgets этой книги)`;
- memory cache: максимум 64 entries, entries с активными listeners не вытесняются;
- прогресс записи: одна последовательная coalesced-очередь на книгу;
- rename index: `apply_paths` для изменённых файлов;
- backlinks: один запрос активного режима панели на новую revision, устаревший результат игнорируется.
