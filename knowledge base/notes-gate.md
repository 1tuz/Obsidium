# Шлюз изменений заметок

Любое изменение заметок на диске — запись, создание, копирование, переименование со ссылками,
перенос между базами, удаление в корзину, возврат из корзины, очистка корзины — проходит через один
модуль `files::gate`. Команды Tauri (`files::commands`) и инструменты MCP — тонкие обёртки над ним.
Шлюз выполняет операцию и сам делает всё, что обязано следовать за ней.

## Связанные документы

- [[trash]] — корзина, её структура и возврат.
- [[mcp-and-doc-sync]] — синхронизация документа с диском и запись через MCP.
- [[file-tree-rendering]] — удаление и переименование из дерева файлов.
- [[note-history]] — история заметки: версии пишутся в этом же шлюзе.
- [[links-and-backlinks]] — переписывание ссылок при переименовании.

## Зачем

До шлюза одни и те же побочные действия были продублированы вручную в семи командах Tauri и восьми
местах MCP: уведомить поиск о пути, уведомить дерево файлов, для переименования в MCP — отдельное
событие фронтенду, и только для базы на экране. Перенос между базами шёл голым `rename_file_impl`.
Копии расходились, и у каждого пути была своя дыра:

| Путь | Вкладка | Запись синхронизации | Реплика старого пути |
|---|---|---|---|
| переименование папки | ехала | не переносилась | оставалась сиротой |
| перетаскивание | **закрывалась** | не переносилась | оставалась |
| переименование через MCP | ехала только для базы на экране | не переносилась | оставалась |
| удаление через MCP | закрывалась через «файл пропал» | оставалась | оставалась |

Перетаскивание открытой заметки закрывало её вкладку: редактор продолжал писать по старому пути,
файла там уже не было, и заметка считалась пропавшей.

## Что делает шлюз

| Операция | История заметки | После операции |
|---|---|---|
| `write` | версия по правилам вехи | поиск: изменилось содержимое пути |
| `create` (заметка) | версия по правилам вехи | поиск и дерево: появился путь |
| `create_binary`, `copy` | — | поиск и дерево: появился путь |
| `rename` (со ссылками), `move_across` (между базами) | папка истории едет за заметкой; переписанные ссылки — версии `links` | поиск и дерево; событие `notes-relocated` с переносами |
| `trash` | открытая веха записана, папка истории — в корзину, к файлу заметки | поиск и дерево; событие `notes-relocated` с удалёнными заметками |
| `restore` | папка истории возвращается к заметке | поиск и дерево |
| `empty_trash` | удаляется вместе с заметками | ничего: корзина скрыта от поиска и дерева |

`write` и `create` принимают источник правки (`history::Source`): `Me` из команд Tauri, `Agent` из
MCP, — и необязательное название версии: версия, которую создаёт запись, сразу закрепляется с этим
именем (MCP `versionName`). `name_version` называет существующую версию или текущее состояние и
шлёт то же событие. Если запись породила версию или изменила незакрытую веху (`saved` вернул `true`), шлюз шлёт
`note-history-changed` с путём заметки — открытый список истории перечитывает себя (см.
[[note-history]], «Этап 2»). Запись прогресса чтения приходит в `write` с источником `Reading`, восстановленная версия — с
`Restore(время исходной версии)`: команда `write_file_atomic` принимает источник параметром
`source` (`edit`, `readingProgress`, `restore { fromMs }`). Источник знает вызывающий, а не служба. Перед записью шлюз спрашивает у службы текст на диске
(`disk_before`): служба читает файл, только если заметка ей незнакома или хэш на диске не совпал с
последней записью приложения, то есть на обычном сохранении из редактора диск не читается. Ошибка
истории пишется в журнал `[aquilum:history]` и никогда не срывает запись заметки. Место удалённой
заметки в корзине шлюз берёт из отчёта самой операции (`Relocated.files`, [[trash]]), а не
вычисляет.

Событие `notes-relocated` — `{ moves: [{from, to}], removed: [path] }` — перечисляет **отдельные
заметки**: перенос или удаление папки шлюз сам разворачивает в список `.md` внутри неё (`notes_under`,
до операции). Поэтому фронтенду не нужна логика «под путём»: вкладки, документы и записи
синхронизации адресуются точным путём одинаково для заметки, папки, перетаскивания и MCP.
Сам механизм переименования со ссылками — `files::rename`, это операция без побочных действий.

## Фронтенд: один обработчик

`useNoteRelocation` в `App` слушает событие и применяет его через `applyRelocation`
(`modules/documents/relocation.ts`):

- **перенос**: открытый документ переезжает на новый путь (`renameDoc` и `writer.adoptPath`), вкладка
  тоже (`handleFileRenamed`), запись синхронизации переносится (`moveSyncRecord`), реплика старого
  пути закрытой заметки удаляется;
- **удаление**: документ и вкладка закрываются, реплика и запись синхронизации удаляются.

У открытой переименованной заметки реплика остаётся подключённой к комнате старого пути, пока документ
жив: IndexedDB не умеет переименовывать базу, а удаление подключённой базы оборвало бы её запись.
`docs` помнит путь, под которым документ подключился (`roomPath`), и удаляет эту комнату при закрытии
документа, если путь с тех пор сменился.

События применяются по одному в очереди. Каждый шаг **идемпотентен**: событие может прийти до или
после того, как интерфейс сделал своё, или прийти дважды, и ничего не испортит. Отсюда два правила:

- `moveSyncRecord` не затирает запись, которая уже есть на новом пути: её мог записать интерфейс
  после переименования открытой заметки, и она свежее перенесённой;
- редуктор вкладок и `handleExternalRename` ничего не делают, если вкладки с таким путём нет, —
  иначе каждое событие о чужой заметке перерисовывало бы вкладки и сохраняло сессию.

Ручные вызовы, которые раньше дублировали это в потоках интерфейса, удалены: `forgetDeletedFile`,
`markdownFilesUnder`, перенос записи синхронизации в `renameWorkspaceFile`, проброс `onFileRenamed`
и `onFileDeleted` через `Sidebar`, `EditorPane` и `Editor`, событие `renamed` моста MCP.

## Инициирование переноса

Перенос с фронтенда идёт через `moveWorkspaceEntry` (`renameWorkspaceFile.ts`). Открытая заметка
переносится через очередь своего `DocumentFileWriter` (`writer.rename`), поэтому ни одно её
сохранение не вклинится между переименованием и сменой пути. Перед переносом папки дожидаются
несохранённого у открытых заметок внутри (`flushDocumentsUnder`). Через `moveWorkspaceEntry` идут
перетаскивание и переименование папки; переименование заметки — через `writer.rename` внутри
`renameWorkspaceFile`.

## Что сломается, если писать мимо шлюза

Любая новая операция с заметками, которая вызовет `write_file_atomic_impl`, `rename_file_impl` или
`move_to_trash_impl` напрямую, снова потеряет что-то из списка выше: поиск не узнает о пути,
вкладка не поедет за заметкой, в IndexedDB останется сирота. История заметки ([[note-history]])
пишется в шлюзе — запись мимо него пропадёт и из истории, а перенос мимо него оставит историю под
старым путём. Внутри шлюза напрямую вызывает
запись только сам механизм переименования (`files::rename`) — это одна атомарная операция с откатом.

Действия в Проводнике и других программах идут мимо Aquilum вовсе. Наблюдатель знает о них только
«что-то изменилось в структуре», поэтому переносы оттуда не видны как переносы. Для них работает
правило синхронизации «файл побеждает»: для пути без записи синхронизации или с репликой, которую не
трогали с последней синхронизации, `resolveSync` берёт текст файла.
