# Жизненный цикл документа Aquilum

Статус: принято к поэтапной реализации, этап 1 завершён 2026-07-15.

## Связанные документы

- [[mcp-and-doc-sync]] — как внешние правки попадают в открытый документ минимальным диффом.
- [[tab-switching]] — что происходит при открытии и переключении вкладок и почему в DOM всегда один редактор.
- [[search-indexing-workspaces-part-1]] — сохранение документа поднимает ревизию индекса, а её читают бэклинки, граф и разрешение вики-ссылок.
- [[conflict-copies]] — что происходит, когда свести файл и документ без потери нельзя, и что копия теперь пишет о причине.

## Прогресс

- [x] Этап 1: файловый фундамент, типизированный gateway и тестовый контур.
- [ ] Этап 2: `DocumentSession`, UUID и локальный baseline store.
- [ ] Этап 3: reconcile внешних изменений.
- [ ] Этап 4: workspace watcher.
- [ ] Этап 5: локальные точки восстановления.

Поведенческая часть этапов 3 и 4 уже работает до появления `DocumentSession`: внешние
изменения файла приходят событием `documents-changed` и вливаются в `Y.Doc` минимальным
диффом (`modules/docSync`), а конфликт записи разрешается перечитыванием диска. Детали и
корнер-кейсы — [[mcp-and-doc-sync]]. Идентификация `Y.Doc` по пути и владение через
mount/unmount остаются нерешёнными и снимаются только `DocumentSession`.

## Состояние после этапа 1

Уже гарантируется:

- атомарная запись Markdown на Windows, Linux и macOS;
- BLAKE3-хеш прочитанного и записанного содержимого;
- отказ от записи при несовпадении ожидаемого хеша;
- последовательный порядок локальных `write` и `rename`;
- создание и переименование без предварительной проверки из React;
- завершение ожидающего подключения IndexedDB при размонтировании;
- отсутствие прямых файловых Tauri-вызовов вне типизированного gateway.

До этапов 2 и 3 намеренно остаются ограничения старого lifecycle:

- `Y.Doc` и IndexedDB всё ещё идентифицируются файловым путём;
- один глобальный provider всё ещё обслуживает активный редактор;
- владение `Y.Doc` всё ещё связано с mount/unmount React-компонента;
- сохранённый `Y.Text` ещё не согласуется с внешне изменённым Markdown при открытии.

Эти ограничения устраняются заменой `useEditorDoc`, `modules/docs` и `modules/sync` на одну `DocumentSession`. Добавлять параллельные обходные механизмы в старые модули запрещено.

Два эффекта в `useEditorDoc` намеренно объявляют неполные зависимости (под `eslint-disable-next-line react-hooks/exhaustive-deps`):

- эффект загрузки зависит только от `ydoc`. Документ живёт по `ydoc`: при переименовании меняется путь, но загружать заново нечего. Если добавить путь в зависимости, переименование вызовет повторную загрузку и `releaseDoc` живого документа;
- обработчик `blur` вешается один раз: writer читается из ref, поэтому пересоздавать подписку при каждом рендере не нужно.

## Цель

Сохранить обычные Markdown-файлы пользовательским форматом хранения и использовать один `Y.Doc` на документ как рабочее состояние редактора. Локальная архитектура должна без переписывания допускать последующее подключение совместной работы.

## Основной контракт

```text
Aquilum закрыт -> Markdown является долговечным представлением документа
Aquilum открыт -> актуальное рабочее состояние находится в Y.Doc
DiskBaseline   -> связывает файл и Y.Doc
```

Локальный путь является изменяемым свойством документа, но не его идентификатором. Документ получает стабильный UUID (`DocumentId`).

## Инварианты

1. На один `DocumentId` существует не более одной активной `DocumentSession`.
2. `Y.Doc`, IndexedDB persistence, `Y.UndoManager`, файловый baseline и очередь операций принадлежат `DocumentSession`.
3. React-компоненты не читают и не записывают документы напрямую. Они работают через сессию или файловый gateway.
4. Открытие редактора происходит только после восстановления persistence и согласования файла с Yjs.
5. Все операции одного документа выполняются последовательно.
6. Любое изменение `Y.Text`, независимо от источника, материализуется в Markdown.
7. Запись файла атомарна и проверяет ожидаемый хеш, чтобы не затереть внешнее изменение.
8. Собственные события watcher отбрасываются по хешу содержимого, а не только по времени изменения.
9. Внешнее изменение применяется точечными `insert`/`delete` в одной Yjs-транзакции. Полная замена `Y.Text` допустима только при первой инициализации или явном восстановлении.
10. Локальные пути, хеши и baseline не хранятся в синхронизируемом `Y.Doc`.
11. `Ctrl+Z` использует один `Y.UndoManager`; отдельная история CodeMirror для текста отключена.
12. Закрытие одной сессии не влияет на другие документы.

## Открытие документа

```text
resolve canonical path and DocumentId
-> read immutable disk snapshot
-> restore Y.Doc from IndexedDB
-> restore DiskBaseline
-> reconcile disk changes
-> attach editor
-> observe Y.Text changes
```

При появлении сетевого provider этап синхронизации добавляется после IndexedDB и перед reconcile. Остальная последовательность не меняется.

### Сбой открытия не оставляет пустой экран

Редактор рисует заметку, когда готовы документ (`useEditorDoc`: файл прочитан, реплика подключена,
сверка с диском прошла) и состояние вида (`viewStateReady`). Пока чего-то нет, на месте заметки
пустой `q-editor-loading`. Раньше любая ошибка на этих шагах уходила только в `console.error`,
которого в установленной версии не видно, и заглушка оставалась навсегда — обращение пользователя
«любая заметка пустая», на скриншоте которого были дерево и вкладка, но не было даже поля заголовка.

**Файл не прочитался — экран ошибки.** Показать нечего, поэтому `useEditorDoc` кладёт ошибку в
`openError`, `Editor` бросает её, и `ErrorBoundary` панели показывает `ErrorReport`: заголовок, путь,
код и детали, «Копировать», «Попробовать снова» (перемонтирует редактор и читает заново). Для
`invalid_utf8` есть ещё «Показать файл в папке» — пересохранить файл может только пользователь.
Тексты — `Editor/noteOpenError.ts`. Граница сбрасывается и при смене заметки в той же вкладке
(`resetKey` — вкладка, `mountKey` и путь), иначе ошибка заметки A оставалась бы на заметке B.

**`ui-state` не работает — заметка всё равно открывается.** `ui-state.sqlite3` хранит только
вкладки, позиции прокрутки и курсора, список баз; сама заметка от неё не зависит. Поэтому любой
сбой этой базы — сессия не открылась, `resolve_ui_document` или `load_ui_document_view` упали — не
экран ошибки, а деградация: `useTabSession` запоминает первую ошибку в `stateError`, перестаёт
обращаться к базе, все заметки считаются готовыми без сохранённого вида (открываются с начала), а
над заметкой одна плашка `EditorNotice`: «Открытые вкладки и позиции в заметках сейчас не
сохраняются: причина». Действие зависит от того, сломана ли база целиком (`stateFailure` в
`modules/ui-state/types.ts`): если сессия не открылась или код `unavailable`/`unsupported_schema` —
«Сбросить и перезапустить» с честным перечнем того, что забудется; если упал отдельный запрос
(например, кратковременная блокировка) — только «Перезапустить». Сброс стирает всю `ui-state`, а не
вкладки одной базы, поэтому предлагать его на единичный сбой нельзя.

Первая версия показывала экран ошибки на каждую вкладку и вела ошибки по ключам вкладок — три ошибки
из ревью были именно оттуда (ошибка переезжала на другую заметку в той же вкладке, не снималась
после повтора), а пользователь вместо заметки видел отказ из-за базы, без которой заметка обходится.

Сброс (`resetSessionState` → `reset_ui_state`) откладывает `-wal`, `-shm` и саму
`ui-state.sqlite3` в `*.broken-<время>` (сначала спутники: иначе новая база могла бы открыться рядом
со старым WAL), открывает чистую, заново регистрирует текущую базу знаний (`resolve_ui_workspace` —
иначе после перезапуска открылся бы экран «нет базы») и перезагружает окно. Теряются вкладки,
позиции, список других баз и выбор домашней страницы; заметки, история и настройки не затронуты.
Помогает при базе от более новой версии (`unsupported_schema` после отката с 0.1.9 на 0.1.8), при
повреждённом файле и при базе, занятой на старте другим процессом. Тесты в `migration_tests.rs`:
база из будущей версии и база, открытая и используемая перед сбросом.

**Не сохраняется на диск — плашка.** Ошибка записи (кроме конфликта, который решает сверка) раньше
уходила в консоль: пользователь писал дальше, а `.md` оставался старым — для MCP, синхронизации и
внешних редакторов. Текст при этом не терялся (он в `Y.Doc` и реплике). Теперь `useEditorDoc`
держит `saveError`, над заметкой `EditorNotice` «Изменения не сохранены на диск: причина. Текст не
потерян…» и «Сохранить ещё раз» (`writer.writeCurrent`). Плашка снимается первой удачной записью:
у запланированной записи есть `onSaved` рядом с `onError` (через `writer.onSynced` нельзя — он
назначается один раз при первом открытии документа и при повторном монтировании остался бы
старым).

**IndexedDB, которая не отвечает, не вешает открытие.** `y-indexeddb` при ошибке открытия базы
просто не присылает `synced`, и ожидание было вечным. `connectDoc` ждёт реплику не дольше 10 секунд,
затем закрывает её и **стирает** (`disconnectDoc` + `clearLocalDoc`), и заметка открывается с диска.
Стирать обязательно: правки этой сессии в реплику не попадут, а запись синхронизации уйдёт вперёд;
в следующий раз ответившая реплика со старым текстом выглядела бы для сверки как свежие правки
документа (`publish-document`) и перезаписала бы файл без копии конфликта. В лог —
`[aquilum:replica] … не ответила`. Цена: если приложение упало в первую секунду после правки
(правка была только в реплике), а при следующем запуске IndexedDB ответила медленнее порога, эта
правка теряется вместе со стёртой репликой. Порог 10 секунд, а не 5, чтобы медленная, но живая
IndexedDB (холодный старт, антивирус) почти никогда его не достигала. Тест `opens the document without the local copy when IndexedDB
never answers`.

**Чего нет и почему.** После чтения файла `setupDoc` упасть нечему: `connectDoc` не бросает,
`diskSync.pull` ловит ошибки сам, поэтому действия «сбросить локальную копию» нет. Переиндексации
тоже нет: открытие заметки индекс не использует. Не закрыто чтение, которое не завершается
(облачный файл «по запросу», зависший сетевой диск): заглушка висит, пока ОС не ответит.

## Согласование файла

`DiskBaseline` содержит последний успешно записанный текст, его BLAKE3-хеш, Yjs state vector и время сохранения.

```text
external patch = diff(baseline text, current disk text)
merged text    = apply(external patch, current Y.Text)
Yjs changes    = diff(current Y.Text, merged text)
```

Итоговые изменения применяются одной транзакцией с origin `filesystem`. Diff вычисляется только при несовпадении хешей и никогда не выполняется на каждый ввод символа.

## Сохранение

Изменения `Y.Text` объединяются debounce-механизмом внутри сессии. Сохранение выполняется через последовательную очередь:

```text
capture current Y.Text
-> compare current disk hash with expected hash
-> atomically replace Markdown file
-> persist new DiskBaseline
```

При несовпадении ожидаемого хеша запись прекращается, файл перечитывается и проходит reconcile. Сессия не имеет права молча перезаписывать неожиданно изменившийся файл.

## Origins и отмена

Минимальный набор источников транзакций:

```text
editor
filesystem
system
remote (в будущем)
```

Локальный `Y.UndoManager` отслеживает ввод редактора и импорт с этого компьютера. Системная гидратация и удалённые транзакции не добавляются в персональный стек отмены.

## Поэтапная миграция

### Этап 1. Файловый фундамент

- тестовый контур TypeScript и Rust;
- `read_file_snapshot`, атомарная запись, проверка существования и переименование;
- типизированный TypeScript gateway;
- зелёные `npm run build`, `npm test` и `cargo test`.

### Этап 2. DocumentSession

- UUID-реестр документов;
- локальный store для baseline;
- persistence на один документ;
- последовательная очередь и lifecycle;
- единый UndoManager.

### Этап 3. Reconcile

- чистый diff/patch-адаптер;
- точечное применение изменений к `Y.Text`;
- миграция текущих IndexedDB-баз без автоматического удаления;
- тесты внешнего редактирования и аварийного перезапуска.

### Этап 4. Workspace watcher

- один watcher на workspace;
- объединение повторных событий;
- маршрутизация событий только в открытые сессии;
- обновление дерева файлов и обработка rename/delete.

### Этап 5. Локальные точки восстановления

- снимок перед внешним импортом или крупным удалением;
- ограниченная политика хранения;
- подготовка данных без обязательного UI истории.

## Миграция существующих данных

Старые IndexedDB-базы не удаляются автоматически. При первом открытии создаётся UUID и новая persistence-база. Если Markdown и старый `Y.Text` различаются, обе версии сохраняются как recovery-снимки, а рабочим долговечным содержимым считается Markdown-файл.

## Критерии готовности локального фундамента

- внешний редактор может изменить файл при закрытом или открытом Aquilum без молчаливой потери данных;
- переименование не меняет `DocumentId`;
- переключение и закрытие вкладки не отключает другой документ;

Механизм переключения вкладок и истории навигации описан в [[tab-switching]].
- после аварийного перезапуска выбирается проверяемое состояние, а не случайный победитель;
- все операции покрыты сценарными тестами с Unicode, CRLF, пустыми файлами и крупными удалениями;
- сохранение не вызывает React-render на каждый введённый символ;
- текущие темы, масштабирование и отображение Markdown не меняются.
