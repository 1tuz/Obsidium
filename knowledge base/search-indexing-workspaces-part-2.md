# Adamic-Adar и BM25F в Aquilum

Первая часть: [[search-indexing-workspaces-part-1]]

## 1. Где это находится

Backend analysis расположен в `src-tauri/src/search/analysis/`:

| Файл | Назначение |
|---|---|
| `models.rs` | `AnalysisMethod` и `AnalysisResult`. |
| `commands.rs` | Tauri-команда `analyze_document`. |
| `service.rs` | Проверка active workspace/status, выбор алгоритма и graph cache. |
| `graph.rs` | Загрузка SQLite graph snapshot и Adamic-Adar. |
| `bm25f.rs` | Поиск похожих заметок по содержимому через Tantivy. |
| `paths.rs` | Канонический graph identity и нормализация пути. |

Frontend получает оба алгоритма из `useDocumentAnalysis`, а показывает их в `BacklinksPanel`. Клик по строке вызывает `App.tsx -> revealFile -> activateFile(path, { disposition })`.

Общий контракт:

```ts
{
  path: string,
  title: string,
  value: number,
  reasons: string[]
}
```

Для Adamic-Adar интерфейс показывает `value.toFixed(2)`. Сортировка выполняется по полному `f64`, поэтому две одинаково выглядящие строки могут иметь разные реальные значения.

## 2. Adamic-Adar: математическая модель

Пусть `a` - открытая заметка, `b` - кандидат, `N(x)` - множество всех соседей. Общие соседи:

```text
N(a) ∩ N(b)
```

Текущая совместимая с Obsidian Graph Analysis формула:

```text
AA(a,b) = sum( 1 / ln(outDegree(z)) )
          z in N(a) ∩ N(b)
```

Чем меньше исходящих ссылок у общего соседа `z`, тем он информативнее. Общий «редкий» сосед дает больший вклад; высоко связанный hub дает маленький вклад.

В графе Aquilum каждое Markdown wiki-link создает ориентированное ребро `source -> target`, но `neighbours` для поиска пересечения симметричен. Поэтому входящие и исходящие связи участвуют в `N(x)`, а вес использует именно число исходящих ребер. Это повторяет код расширения Graph Analysis, где используются `neighbors()` для пересечения и `outNeighbors()` для логарифма.

Пример:

```text
A -> X, A -> Y
B -> X
C -> X, C -> Y

X outDegree = 3, Y outDegree = 2
AA(A,C) = 1/ln(3) + 1/ln(2)
AA(A,B) = 1/ln(3)
```

Важное следствие: если два кандидата имеют ровно одного и того же общего соседа с той же степенью, их score обязан быть одинаковым. Это не ошибка. Расширение при равенстве дополнительно сортирует по числу общих соседей, затем Aquilum использует название как стабильный tie-breaker.

## 3. Как строится graph snapshot

`GraphSnapshot::load` читает из `documents.sqlite3` все `wiki_documents`, строит lookup по `title_key` и `relative_key`, затем читает `wiki_links`.

Этот снимок обслуживает Adamic-Adar. Отдельный снимок для отрисовки графа связей, требования к нему и вывод даты создания заметки описаны в [[graph-view]].

Для каждого link:

1. target разрешается по имени заметки или relative path;
2. при дубликатах выбирается кандидат в той же папке, затем более близкий путь;
3. из source и target строится ключ узла `identity`: слэши, регистр на Windows, без обращения к диску;
4. добавляются symmetric neighbours;
5. source -> target добавляется в outgoing;
6. пути сохраняются для ответа frontend.

Неразрешенные цели в текущем graph analysis не становятся узлами. Самоссылки отбрасываются. Повторные ссылки между той же парой схлопываются через `HashSet`, то есть десять одинаковых `[[Note]]` не усиливают Adamic-Adar.

Результаты включают уже связанные заметки, потому что расширение не фильтрует прямые links. Это link prediction/relatedness, а не только список «чего не хватает».

## 4. Почему раньше был пустой список

Основная причина была не в формуле. В `analysis/service.rs` read-lock graph cache жил слишком долго: ветка empty cache пыталась взять write-lock, пока read guard еще существовал. Adamic-Adar зависал на переходе read -> write. После этого UI видел пустое состояние или старый индекс, а переключение workspace могло заблокироваться тем же lock.

Дополнительные причины были в path representation Windows и в отсутствии проверки `state=ready && updating=false`. Сейчас graph lock scoped, status проверяется до analysis, graph invalidates после индексных изменений, а пути возвращаются в обычном виде без `\\?\`.

## 5. Числовые edge cases Adamic-Adar

В реализации:

- `outDegree = 0` дает нулевой вклад;
- `outDegree = 1` математически дает `Infinity`, после чего результат фильтруется как non-finite, как при настройке `noInfinity` в расширении;
- `outDegree >= 2` дает конечный положительный вклад;
- кандидат без общего соседа не попадает в результат;
- self-result исключается;
- limit backend ограничен 1..100, стандартный limit 50;
- UI округляет только отображение до двух знаков.

Нельзя нормализовать Adamic-Adar делением каждого результата на максимум и называть это процентом: тогда максимум всегда будет `100%`, а при равных сырых scores весь список станет `100%`. Поэтому сейчас показывается raw score, например `0.32`, а не ложная вероятность.

## 6. Как работает BM25F в проекте

Реализация BM25F в Aquilum максимально приближена к академической модели с нормализацией длины полей (`field length normalization`).

`bm25f::analyze`:

1. Читает содержимое и заголовок исходной заметки.
2. Токенизирует их, выявляет термины и подсчитывает частоту.
3. Рассчитывает IDF для каждого термина и отбирает максимум 64 наиболее релевантных (`informative terms`).
4. Для каждого термина создается `Boolean query` по полям `body` и `title`, при этом вес `title` умножается на `TITLE_WEIGHT` (2.5).
5. Получает до 256 кандидатов Tantivy по этому запросу.
6. Выполняет академический подсчет BM25F для каждого кандидата:
   - Рассчитывает нормированную частоту `normalized_tf` отдельно для заголовка (`b_title=0.3`) и для тела (`b_body=0.75`).
   - Использует параметры насыщения `K1=1.2` и `K3=8.0` для итогового расчета Score.
7. Исключает исходную заметку из результатов.
8. Возвращает сырой (`raw`) Score и до трех общих терминов в `reasons` для объяснения в UI.

В UI `BM25F score` больше не нормализуется делением на максимум (победитель больше не равен 100%), а отображается как сырой `raw score`, либо пересчитывается в `confidence` (будущая калибровка).

Tokenizer: lowercase, ASCII folding, удаление токенов длиннее 120 символов. В глобальном поиске query terms дополнительно нормализуются по Unicode и поддерживается prefix matching.

Перед токенизацией текст заметки проходит `sanitize_for_search`, и меняется только то, что уходит в токенизатор: сохранённое в Tantivy тело остаётся нетронутым, поэтому сниппеты и подсветка показывают настоящий текст. Из frontmatter в поиск попадает только значение `author`: `type`, `status`, теги и ссылки одинаковы у сотен заметок и забили бы выдачу шумом. У markdown-ссылки `[подпись](url)` остаётся подпись, а сам URL выбрасывается, как и голые `http://`, `https://`, `www.`. Вики-ссылка `[[Заметка]]` не разбирается и остаётся целиком, иначе имя цели перестало бы токенизироваться как заголовок. Схемы URL сравниваются по байтам ASCII, а не срезами строки: срез `&str` посреди кириллического символа паникует, и одна русская заметка роняла бы индексацию. То, что от URL всё же доходит до токенов (`com`, `html`, `www`…), отсекает список `EXCLUDED_TERMS`. Он обязан оставаться отсортированным, потому что проверка идёт двоичным поиском, и новое слово вписывается по алфавиту, а не в конец. Короткие слова, которые встречаются и в обычном тексте (`de`, `me`, `us`, `co`), в список намеренно не входят, иначе из поиска пропали бы настоящие слова.

Документная частота термина для IDF берётся как сумма `doc_freq` по полям `body` и `title`, ограниченная числом документов. Это верхняя оценка числа заметок, где термин есть хотя бы в одном поле: заметка с термином и в заголовке, и в теле посчитается дважды. Точное объединение потребовало бы отдельного запроса `Count` на каждый термин, а для первичного отбора 64 информативных терминов завышенная частота у заголовочных слов ничего не ломает. Подписи терминов в `reasons` берутся не из основ: `stem_surface_labels` сопоставляет каждой основе самую частую словоформу из самой заметки, поэтому человек видит «книги», а не «книг».

## 7. Разница алгоритмов

| Свойство | Adamic-Adar | Настоящий BM25F |
|---|---|---|
| Источник | `wiki_links` в SQLite | body/title в Tantivy и чтение body |
| Что ищет | структурно близкие узлы графа | лексически похожие заметки |
| Причина | общие соседи | общие informative terms |
| Score | raw AA, может быть меньше/больше 1 | raw BM25F (абсолютный score) |
| Реакция на новую ссылку | требует обновления graph cache | почти не меняется без изменения текста |
| Реакция на общие слова | никак | сильная, с IDF |
| Прямые links | включаются | кандидат может быть найден как похожий |
| Основное ограничение | качество и полнота wiki graph | качество tokenizer и term selection |

Практически полезно использовать оба режима: Adamic-Adar отвечает «что связано через структуру заметок», BM25F отвечает «что похоже по содержанию».

## 8. Путь запроса от UI до результата

```text
BacklinksPanel
  -> useDocumentAnalysis(method, workspace, document, revision)
  -> invoke("analyze_document")
  -> spawn_blocking
  -> SearchService::analyze_document
  -> active root/status/workspace validation
  -> AdamicAdar(GraphSnapshot) OR Bm25f(Tantivy)
  -> AnalysisResult[]
  -> row with score and tooltip reasons
  -> App::revealFile
  -> tab state -> document UUID -> CodeMirror
```

Analysis не выполняется, пока link index не `ready` и не завершает обновление. При смене заметки, метода или revision старый async result игнорируется через request key/current flag.

## 9. Производительность

Пусть `V` - число Markdown-документов, `E` - число уникальных wiki edges, `L` - суммарный размер текста.

Первый scan: примерно `O(L + V + E)` плюс filesystem traversal и Tantivy indexing. Инкрементальная запись одной заметки: `O(size(file) + links(file))`, затем commit/reload.

Загрузка graph snapshot: `O(V + E)` времени и `O(V + E)` памяти. Запрос Adamic-Adar не перебирает все пары документов: он проходит соседей текущего узла и соседей этих соседей. Стоимость примерно `O(sum(degree(z)) для z in N(a))`; hub с тысячами связей может быть дорогим.

BM25F анализ ограничивает query 64 terms и candidate pool 256. Это удерживает latency, но длинная заметка все равно требует term frequency и нескольких Tantivy doc reads. `reasons` дополнительно токенизирует тело кандидатов.

Для текущего масштаба в сотни/тысячи заметок схема подходит. Для 100k заметок и миллионов edges потребуется benchmark на реальных данных, graph adjacency storage в более компактном формате, incremental graph updates и ограничение hub expansion. Полезно измерять p50/p95/p99 для scan, incremental write, global search, AA и BM25F отдельно.

Главный скрытый расход - не SQL query, а in-memory `HashMap<String, HashSet<String>>`: повторение абсолютных строк путей и hash-set overhead может быть значительно больше самих ссылок.

**Пути из индекса не канонизируются повторно.** Раньше `GraphSnapshot::load` на каждую ссылку звал `canonical_path` для источника и цели, а `identity` внутри канонизировала их ещё раз — четыре `fs::canonicalize` на ссылку. На Windows каждый вызов открывает дескриптор файла, около 30 мкс. На базе zombie voxel (247 заметок, 1627 ссылок) построение снимка стоило 196 мс, и почти всё это время уходило на канонизацию путей, которые индекс и так хранит в каноническом виде: их даёт обход канонического корня. Теперь `identity` — чистая функция над строкой, а канонизируется только внешний ввод на границе (`analyze_document` канонизирует документ сам). Снимок строится за 2,6 мс (NeuroNet, 836 заметок и 1859 ссылок: 188 → 6 мс), подсчёт хабов для `list_notes sort=links` — 8 → 0,1 мс, BM25F — 15 → 8,6 мс, потому что его кандидаты тоже проходили через `identity`.

Если в `identity` снова понадобится канонизация, значит, в неё пришёл сырой внешний путь: его надо канонизировать там, где он вошёл, а не внутри горячего цикла.

Замеры снимаются стендом `search/benches/link_pipeline.rs` на синтетической или реальной базе (`AQUILUM_BENCH_VAULT=<папка>`, база только читается), в release-сборке: dev-сборка на строковой работе в 10–20 раз медленнее и искажает картину.

## 10. Подходит ли это для multiplayer

В текущем виде - для локального single-user да, для полноценного multiplayer нет.

Почему база хорошо подготовлена:

- Markdown остается переносимым источником данных;
- document/workspace identity уже отделены UUID от path;
- Yjs выбран как CRDT-слой;
- поисковый индекс является производным и может быть пересобран на каждом клиенте;
- SQLite WAL и Tantivy подходят для локального read-heavy cache.

Что пока мешает multiplayer:

- сетевого провайдера синхронизации нет: `modules/sync` держит только локальную IndexedDB-реплику
  (`connectDoc`/`disconnectDoc`), пустая заглушка `WebSocketSyncProvider` удалена;
- текущий `DocumentFileWriter` защищает local sequence, но не заменяет серверную конфликтную модель;
- expected hash при записи превращает одновременную запись разных клиентов в conflict, а не в merge;
- индекс строится из локальной файловой системы и не имеет remote revision/ack;
- watcher может увидеть несколько промежуточных файловых состояний;
- абсолютный path нельзя использовать как глобальный identity между машинами;
- нет серверных permissions, tenancy и контроля доступа к workspace;
- события `links-changed` не содержат workspace/revision.

Правильная multiplayer-модель: сервер синхронизирует Yjs document или versioned Markdown, каждый клиент materializes локальный файл, индексирует только подтвержденную локальную ревизию и связывает cache с `(workspaceId, contentRevision)`. Результаты поиска должны иметь revision, чтобы UI не показывал результат от старого состояния.

## 11. Приоритетный roadmap

### P0: Корректность (✅ Завершено)

Все критичные ошибки жизненного цикла и конкурентности устранены:
- Graph cache привязан к `(canonicalWorkspace, indexGeneration, revision)`.
- Добавлен `generation` в `prepare_search_index`.
- Lock активного состояния больше не удерживается во время долгого join worker-а.
- Добавлена гибридная проверка `content_hash` (BLAKE3) вместо только mtime+size.
- `links-changed` передает workspace key и revision.

### P1: UX и эксплуатация

1. Показать workspace name/path, `scanned/indexed`, `queued`, `last successful scan`.
2. Дать команду «пересобрать индекс этого хранилища» и «очистить cache этого хранилища».
3. Добавить LRU/TTL/size quota для cache старых workspace.
4. Передавать в `links-changed` workspace key и revision, не только пустой event payload.
5. Добавить кнопку/диагностику: active root, cache path, document count, wiki links count, last error.

### P2: масштабирование

1. Поддержать incremental graph mutation без полной загрузки SQLite в память.
2. Интернировать path IDs и хранить adjacency по integer IDs.
3. Вынести scoring AA в bounded traversal с hub cap и optional sampling.
4. Профилировать BM25F и добавить configurable candidate pool/term limit.
5. Ввести background compaction и controlled Tantivy commit policy.

### P3: multiplayer

1. Реализовать настоящий WebSocket provider.
2. Ввести server revision и content snapshot protocol.
3. Отделить stable document ID от локального absolute path во всех search records.
4. Индексировать Yjs/materialized revision асинхронно и показывать revision lag.
5. Добавить access control и безопасную синхронизацию workspace.

## 12. Диагностика

Если поиск или analysis снова пусты:

1. Проверить active workspace path и отсутствие `InvalidWorkspace`.
2. Дождаться `state=ready` и `updating=false`.
3. Проверить `indexedDocuments` против числа Markdown-файлов.
4. Проверить существование cache directory для BLAKE3 root.
5. Проверить SQLite counts:

```sql
SELECT COUNT(*) FROM documents;
SELECT COUNT(*) FROM wiki_documents;
SELECT COUNT(*) FROM wiki_links;
```

6. Проверить, что target действительно разрешается: title/path key, регистр, duplicate names и папка.
7. Для AA проверить, что у текущей заметки есть resolved links и есть кандидат через общего соседа.
8. Для BM25F проверить, что заметка содержит terms длиной минимум два символа и terms не отфильтрованы как слишком распространенные.
9. При смене хранилища проверить, что новый запрос передает новый `workspacePath`, а старый async result не применился.

## 13. Итоговая оценка

Текущая архитектура разумна для local-first приложения: файлы просты и переносимы, SQL хорошо обслуживает связи и metadata, Tantivy отвечает за полнотекстовый поиск, а graph analysis изолирован от редактора. Основные прежние сбои были lifecycle/path/lock проблемами, а не необходимостью удалить всю систему.

Adamic-Adar теперь работает как структурный ranking с raw score и стабильной сортировкой; одинаковые scores в случае одинаковой topology нормальны. BM25F-подобный режим дает независимый content ranking и относительный процент.

До production multiplayer нужно прежде всего ввести generation/revision model, сделать cache consistency проверяемой и убрать зависимость search identity от absolute path. До этого система надежна как локальный single-user индекс, который можно безопасно пересобрать из Markdown.
