## Где считается выборка

Выборка `.base` считается в Rust и приходит в webview готовым результатом:

| Слой | Файл | Роль |
| --- | --- | --- |
| Парсер `.base` | `src/modules/bases/baseFormat.ts` | YAML → `BaseDefinition` (`views`, `filters`, `formulas`, `summaries`, `propertyLabels`, `relationProperties`, `unsupportedKeys`) |
| Движок | `core/src/search/bases/mod.rs` | фильтры, сортировка, `groupBy`, `limit`, колонки, `unsupported`, `errors` |
| Формулы | `core/src/search/bases/formulas.rs` | `formulas:` считается вычислителем `dataview` и подставляется в строку как `formula.<имя>` |
| Сводки | `core/src/search/bases/rollups.rs` | агрегаты `summaries` по связанным заметкам |
| Сервис | `core/src/search/bases/service.rs` | `SearchService::query_base` — берёт строки из `base_rows` и передаёт их движку |
| IPC | `src-tauri/src/search/commands.rs::query_base` | `query_base(workspacePath, query)` |
| Шлюз | `src/modules/bases/gateway.ts::queryBase` | типизированный вызов из UI |
| UI | `src/components/Bases/BaseView.tsx` | рисует `rows`, `groups`, `columns`, `unsupported`, `errors` |
| Редактор | `src/components/Bases/BaseEditorPanel.tsx` | правит `views[i]`: `name`, `limit`, `groupBy`, `sort`, `filters`, `order` (см. «Редактор представления») |
| Блок в заметке | `src/components/Editor/extensions/baseFence/` | тот же `queryBase` для огороженного блока `base` в live preview |

Запрос: `BaseQuery { definition, viewIndex, sort }`.
Ответ: `BaseEvaluation { rows, groups, columns, unsupported, errors }`.
Парсер `.base` остаётся в TypeScript — движок не разбирает YAML повторно.

## Почему не в webview

`get_base_rows` отдаёт весь vault: на 10 000 заметок это десятки мегабайт JSON и полный проход
фильтрации в JavaScript на каждый перерендер. Теперь через IPC идут только строки результата:
типичная таблица на 50–200 заметок вместо всего vault. `get_base_rows` остался только для
потребителей, которым нужен полный список путей (`src/modules/canvas/recentNotes.ts`).

Сортировка, фильтрация, группировка и формулы больше не дублируются: в TypeScript остались только
`parseBase` (разбор файла) и `src/modules/bases/properties.ts::baseProperty` (показ значения в
ячейке). Логику выборки меняем в одном месте — `core/src/search/bases/mod.rs`, а выражения формул
считает общий с `dataview` вычислитель (`core/src/search/bases/formulas.rs`).

Исключение — раскладка доски: `modules/bases/kanban.ts::buildKanbanColumns` строит колонки из уже
отобранных строк, потому что доске нужны и пустые колонки из `groupOrder`. Это раскладка, а не
отбор: какие строки попали в выборку и в каком они порядке, решает Rust.

## Семантика

- Фильтры: `==`, `!=`, `>`, `>=`, `<`, `<=`, `and` / `or` / `not`, вложенные конструкции.
- Значения: массивы сравниваются по вхождению (`==`) и по «ни одному из» (`!=`), затем склеиваются
  в строку; строки сравниваются без учёта регистра; числовой литерал включает числовое сравнение.
- Вычисляемые свойства: `file.name`, `file.path`, `file.ext`, `file.folder`, `file.hasTag(...)`,
  `file.inFolder(...)`, `property.contains(...)`; префикс `note.` отбрасывается.
- Сортировка: числовые значения сравниваются как числа, остальные — как строки с натуральным
  порядком (`note 2` раньше `note 10`); направление `DESC` разворачивает сравнение, при равенстве
  порядок добивается путём.
- Группы: `groupOrder` задаёт первые группы в указанном порядке, остальные сортируются по метке
  (направление из `groupBy.direction`); `rows` возвращаются уже разложенными по группам, а
  `groups` содержат диапазоны `start`/`end`.
- Колонки: `view.order`, иначе `file.name` плюс первые 7 свойств из первых 50 строк результата.
- Формулы: `formulas.<имя>` считается на каждую строку и подставляется в неё как `formula.<имя>` —
  дальше это обычное свойство, см. «Формулы».
- `limit` применяется после сортировки.

`unsupported: true` означает, что выборка неполная: встретился неизвестный ключ `.base` или
неразобранное выражение фильтра. Строки в этом случае остаются видимыми — как и раньше, — но UI
показывает предупреждение, чтобы неполный результат не выглядел точным. Сломанная формула сюда не
относится: она даёт `null` в своей колонке и запись в `errors` (см. «Формулы»).

## Свойства-связи

Ключ frontmatter объявляется связью в `properties` того же `.base` файла:

```yaml
properties:
  mentor:
    type: relation
    displayName: Наставник
```

`type: relation` — единственный тип, который понимает интерфейс; остальные значения `type` читаются и
переносятся без изменений, но ничего не меняют. `displayName` продолжает работать как раньше.

**Хранение не меняется.** Отдельного формата нет: объявление — это те же ключи `properties.<key>`,
что и раньше. Значения свойства остаются во frontmatter заметок как есть — `[[Заметка]]`, несколько
ссылок списком или путь (`People/Ada.md`); писатель заметок ничего не переписывает и ссылки не
добавляет.

Разбор: `parseBase` собирает ключи с `type: relation` в `BaseDefinition.relationProperties`
(сравнение без учёта регистра, `"RELATION"` тоже подходит). `serializeBase` пишет `properties` из
`extra.properties`, поэтому `type: relation`, `displayName` и незнакомые ключи записи переживают
цикл «разбор → правка → сериализация». Переключает объявление `setRelationProperties`
(`src/modules/bases/baseFormat.ts`): она ставит или снимает только `type`, остальные ключи записи
остаются, а опустевшая запись удаляется.

**Интерфейс.** В панели представления (`BaseEditorPanel`) у каждого свойства колонки есть
переключатель типа с двумя значениями — «Обычное» и «Связь»; другого типа панель не предлагает.
Сохранение идёт тем же `writeView` в `BaseView.tsx` (чтение файла → `parseBase` → правка →
`serializeBase` → `writeFileAtomic` с хешем), второго писателя `.base` нет.

В таблице и карточках значение свойства-связи показывается ссылкой, а не текстом:

- несколько значений (`mentor: [Ada, Grace]`) рисуются по порядку через запятую;
- `[[Цель|подпись]]`, `[Цель]` и голый путь разрешаются тем же `resolveWikiLinks`, что и ссылки в
  редакторе; щелчок открывает заметку через `onOpenNote`;
- неразрешённое значение остаётся видимым текстом — оно не исчезает и не превращается в битую
  ссылку. Поэтому `mentor: Кто-то` без заметки `Кто-то` видно в ячейке как «Кто-то».

Двойной клик по ячейке по-прежнему открывает ввод: значение можно поправить как текст, и это
единственный способ записать связь — отдельного выбора заметки в таблице нет.

Связи попадают в граф: см. [[graph-view]], раздел «Объявленные свойства-связи».

## Редактор представления

Кнопка с ползунками в шапке `BaseView` открывает панель
`src/components/Bases/BaseEditorPanel.tsx` — компактный диалог для текущего представления:

| Поле | Что пишется в `.base` |
| --- | --- |
| Название | `views[i].name` |
| Ограничение строк | `views[i].limit`; пустое поле убирает ключ |
| Группировка | `views[i].groupBy.property` и `groupBy.direction`; «без группировки» убирает `groupBy` |
| Сортировка | `views[i].sort` — список `property` + `direction`; поля добавляются и удаляются, направление переключается в панели |
| Фильтры | `views[i].filters` — плоский список условий; одно условие пишется строкой, несколько — группой `and` или `or` |
| Порядок колонок | `views[i].order` — панель двигает колонки вверх/вниз и пишет весь массив |
| Тип свойства | `properties.<key>.type` — «Связь» ставит `type: relation`, «Обычное» снимает только этот ключ (см. «Свойства-связи») |

**Фильтры.** Условие — это ровно та строка-выражение, которую понимает движок
(`evaluate_filter` в `core/src/search/bases/mod.rs`). Панель предлагает все поддерживаемые формы и
сама собирает строку:

- сравнение — `property == value`, `!=`, `>`, `>=`, `<`, `<=`;
- подстрока — `property.contains(value)`;
- тег — `file.hasTag(tag)`;
- папка — `file.inFolder(folder)`.

Значение-число и `true`/`false` пишутся без кавычек, остальные значения — в кавычках: так их
разбирает `literal()` в движке. Одно условие сохраняется как строка (`filters: status == "todo"`),
несколько — как `{ and: [...] }` или `{ or: [...] }`; переключатель «Все условия» / «Любое условие»
появляется, когда условий больше одного.

Вложенные группы панель не строит: `not`, `and` внутри `or` и `unsupported` правятся только в самом
`.base`. Если в файле уже лежит такая группа, панель показывает пометку и сохраняет `filters` без
изменений — незнакомая конструкция не переписывается и не теряется. То есть UI умеет плоский список
с одним уровнем `and`/`or`, а вложенные отрицания остаются ручной правкой файла.

**Порядок колонок.** Панель показывает текущий `views[i].order`, а если ключа нет — колонки
выборки, и двигает строки вверх/вниз; сохранение пишет весь массив `order`. Пока порядок не
трогали, ключ не появляется: пустой `order` по-прежнему означает «колонки в том порядке, в каком их
нашёл движок».

`groupOrder` панель не редактирует, но и не теряет: запись идёт через `parseBase` → правку одной
ветки → `serializeBase`, а сериализатор отдаёт `groupOrder`, `properties`, `formulas`, `summaries` и
неизвестные ключи (верхнего уровня и самого представления) без изменений.

Запись одна на все правки — `writeView` в `BaseView.tsx`:

```
readFileSnapshot(path) → parseBase(content) → mutate views[i] → serializeBase → writeFileAtomic(path, next, snapshot.hash)
```

Это тот же шлюз и тот же хеш, что у `addView`; второго писателя у `.base` файла нет. Записи
выстраиваются в очередь (`viewWriteQueue`), чтобы два быстрых клика не читали один и тот же `hash`.
Ошибка хеша или ввода-вывода не глотается: текст ошибки уходит в существующий `actionError` над
таблицей, панель остаётся открытой. После успешной записи `BaseView` заново разбирает
сериализованный текст (`parseBase(next)`) и кладёт его в состояние — вкладка, шапка и выборка видят
ровно то, что лежит в файле.

**Что остаётся в памяти.** Только выбранное представление (`activeView`) — оно живёт в ui-state
(`loadBaseView`/`saveBaseView`), а не в `.base`. Сортировка по клику на заголовок колонки больше не
держится отдельным состоянием: клик пишет `views[i].sort` тем же `writeView`, а `queryBase` получает
`sort` из разобранного файла. Теневого оверрайда нет — источник правды один, `views[].sort`.

## Формулы

`formulas:` — отображение `имя: выражение` на верхнем уровне `.base`. Разбор остаётся в
TypeScript (`parseBase` → `BaseDefinition.formulas`), а значения считает Rust в
`core/src/search/bases/formulas.rs`:

```yaml
formulas:
  risk: 'if(priority == "high", 1, 0)'
```

Выражение разбирает `parser::parse_expression` и вычисляет `eval::evaluate` — тот же вычислитель,
что у `dataview`. Второго языка выражений нет: операторы, функции, приведение типов и правила
истинности у `.base` и запросов одни и те же, поэтому новая функция добавляется один раз и сразу
доступна в обоих местах. Два вычислителя разошлись бы в мелочах — в приоритете операторов, в том,
что считать пустой строкой и числом, — и одна и та же формула отвечала бы по-разному в таблице и в
блоке запроса.

Результат подставляется в поля строки под ключом `formula.<имя>`: формула `risk` становится полем
`formula.risk`. Дальше работает обычный `property()` — без особых случаев для формул. Поэтому
`filters`, `views[].sort`, `groupBy`, `columns` и `view.order` пишут `formula.risk` как любое
другое свойство: фильтр и сортировка по `formula.*` поддержаны.

```yaml
filters:
  and:
    - 'status != "готово"'
    - 'formula.risk > 0'
views:
  - type: table
    name: Риски
    order: [file.name, formula.risk]
    sort:
      - property: formula.risk
        direction: DESC
```

**Синтаксис.** Арифметика `+ - * / %`, сравнения `== != > >= < <=`, логика `and` / `or` / `not`,
`if(условие, да, нет)`. Ветка `if` вычисляется лениво: считается только выбранная, поэтому ошибка в
невыбранной (например, неизвестная функция) формулу не ломает. Строки: `lower`, `upper`, `length`,
`contains`, `startswith`, `endswith`, `substring`, `replace`, `split`, `join`, `truncate`,
`padleft`, `padright`. Числа: `round`, `floor`, `ceil`, `trunc`, `abs`, `sum`, `product`,
`average`, `min`, `max`, `number`, `string`. Списки: `list`, `filter`, `map`, `any`, `all`, `sort`,
`unique`, `flat`, `slice`, `firstvalue`, `lastvalue`, `nonnull`. Значения и даты: `default`,
`choice`, `typeof`, `date`, `dateformat`, `dur`, `today`, `now`. Полные подписи и поведение каждой
функции — в [[dataview-queries]], здесь они не дублируются.

**Поля.** Голое имя (`priority`) читает свойство frontmatter или инлайн-поле заметки; `file.name`,
`file.path`, `file.folder` и `file.tags` считаются полями файла. Отсутствующее свойство даёт `null`,
а не ошибку, поэтому `default(priority, "нет")` — обычный способ подставить значение. Индекс строк
Bases не хранит `file.ctime`, `file.mtime` и `file.size`, поэтому в формуле они читаются как ноль
или пустая строка, а не как дата и размер заметки.

**Ограничения.**

- Формула не видит другие формулы. Все выражения считаются по исходным полям заметки, а
  результаты подставляются в строку уже после. Поэтому `formula.x` внутри формулы — `null`, а
  голое `x` означает поле frontmatter `x`, а не одноимённую формулу. Порядок объявления в
  `formulas:` ни на что не влияет.
- Сломанное выражение не прячет строку: значение колонки — `null`, строка остаётся в выборке,
  `unsupported` не поднимается.
- Даты, длительности и ссылки возвращаются текстом для показа в ячейке: `date("2024-10-07")` в
  колонке — подпись даты, а не значение, по которому можно считать дальше.

**Ошибки.** Ответ несёт `errors: Vec<BaseFormulaError>` — по записи на сломанную формулу:

| Поле | Что содержит |
| --- | --- |
| `formula` | имя из `formulas:` |
| `path` | путь заметки, на которой случилась ошибка; у ошибки разбора пустой |
| `message` | текст ошибки парсера или вычислителя |

Выражение разбирается один раз, поэтому ошибка синтаксиса записывается один раз с пустым `path`;
ошибка времени вычисления запоминает первую строку, где она случилась. Записи схлопываются по паре
`formula` + `message`: одна и та же ошибка на сотне заметок — одна запись, а не сотня.

## Summaries (агрегаты по связанным заметкам)

Блок `summaries` в корне `.base` добавляет в строку значения, посчитанные по связанным заметкам:

```yaml
summaries:
  - name: total
    source: file.links
    property: price
    formula: sum
    filter: 'genre == "sci"'
```

Поля: `name` — ключ колонки, значение попадает в поля строки как `summary.<name>`; `source` — откуда
берутся связанные заметки; `property` — свойство связанной заметки; `formula` — `sum`, `avg`, `min`,
`max`, `count`, `list` или `unique`; необязательный `filter` — выражение того же синтаксиса, что
фильтры view, применяется к связанным заметкам.

`source`:

- `file.links` — исходящие wiki- и markdown-ссылки из тела заметки по индексу ссылок;
- `file.backlinks` — заметки, которые ссылаются на эту;
- любое другое значение — свойство frontmatter, строковое или массив строк со значениями `[[Target]]`
  либо именами заметок.

Сводки считаются до общих и view-фильтров, сортировки и `limit`, поэтому `summary.<name>` работает в
`filter`, `sort`, `groupBy` и `order`. Связанные заметки дедуплицируются по пути, порядок — порядок
ссылок; битые ссылки молча пропускаются. Свойства связанных заметок читаются из тех же строк
field-index, что уже получил `evaluate`: отдельного прохода по диску нет, разрешение ссылок и поиск
свойств кэшируются в пределах одного `evaluate`.

Формулы:

- `sum`, `avg`, `min`, `max` — только числовые значения (`finite_number`); нечисловые значения и
  массивы игнорируются;
- `count` — число связанных заметок после фильтра, `property` не учитывается;
- `list` — массив значений свойства в представлении field-index: скаляры приходят строками, списки —
  массивом строк;
- `unique` — то же, что `list`, но без повторов: порядок — первого появления значения;

Пустые случаи: связанных заметок нет — `count` = 0, `list` = `[]`, `sum`/`avg`/`min`/`max` = `null`.
Свойство отсутствует у всех связанных заметок — `sum`/`avg`/`min`/`max` = `null`, `list` = `[]`,
`count` по-прежнему считает заметки.

Неизвестная или пустая `formula` даёт `summary.<name> = null` и `BaseEvaluation.unsupported = true` —
это единственная новая причина для `unsupported`. Неразобранное выражение в `filter` сводки
оставляет связанную заметку и `unsupported` не ставит.

Разбор: `summaries` — YAML-последовательность отображений; записи без `name` или `source`
отбрасываются; `formula` приводится к нижнему регистру, но не проверяется в TS, чтобы неизвестную
формулу отметил Rust. `summaries` входит в поддерживаемые ключи верхнего уровня и не попадает в
`unsupportedKeys`.

Ограничения:

- только одно звено связи: сводка по сводке или по связанным второго уровня не выражается;
- `count` игнорирует `property`;
- значения связанных заметок должны быть в field-index: заметка без индексируемых полей ничего не
  добавляет;
- массивы для числовых формул не разворачиваются;
- `summary.*` — не подпись: заголовок колонки показывает `name` без префикса (`summary.total` →
  `total`), переопределить можно через `properties.summary.total.displayName`; колонка только для
  чтения, двойной клик не пишет `summary.*` во frontmatter;
- списки связей для агрегатов не обрезаются, но `file.backlinks` идёт через тот же запрос бэклинков,
  который ограничен 200 только для списка в UI.

## Блок `base` в заметке

Тот же движок работает внутри обычной заметки — огороженный блок с языком `base` рисует результат
выборки прямо в live preview:

````markdown
```base
Projects/Roadmap.base План
```
````

Первая строка блока — путь к `.base` файлу и, необязательно, имя представления:

- путь считается от корня vault (`Projects/Roadmap.base`), корневой слэш и абсолютный путь внутри
  vault (`/vault/Projects/Roadmap.base`) дают тот же файл; `..` за пределы vault и путь не с `.base`
  блок не рисуют — остаётся исходный текст;
- второе слово — имя представления (`views[].name`, без учёта регистра); без него берётся первое
  представление; неизвестное имя даёт строку с сообщением, а не исключение;
- остальные строки блока игнорируются: это не запрос, а ссылка на файл.

Движок тот же: блок читает файл (`readFileSnapshot`), разбирает его `parseBase` и вызывает
`queryBase` — второго пути вычисления нет. Рисуется компактная таблица по `BaseEvaluation`
(`rows`, `groups`, `columns`, `unsupported`, `errors`) теми же классами `q-base-*`, что и страница
базы; `unsupported` и ошибки формул показываются строками над таблицей.

Кэш: `src/components/Editor/extensions/baseFence/store.ts` держит результат по ключу
(заметка, путь `.base`, имя представления) и номеру ревизии индекса. Событие `links-changed`
(его слушает `PrefetchScheduler`) поднимает ревизию — все блоки в открытых заметках пересчитываются,
устаревшие записи по ключу больше не отдаются. Блоки, которых в заметке уже нет, выкидываются из
кэша.

Чего блок не делает: не пишет в заметки и `.base` файл (ячейки только для чтения), не переключает
представления и не сохраняет выбранное представление в ui-state, не показывает kanban, cards и
calendar — только таблицу, не создаёт карточки. Для записи и переключения представлений открывайте
`.base` как отдельную страницу.

## Паритет

Кейсы прежнего `src/modules/bases/filter.test.ts` (файл стал `properties.test.ts`) перенесены в
`core/src/search/bases/tests.rs`: рекурсивные фильтры с `file.*`, неизвестные выражения,
числовая сортировка, массивы, `and`/`or`/`not`, группы, колонки, `limit`, вычисляемые свойства.
Формулы проверяются там же: арифметика, `if`, строковые функции, отсутствующее свойство,
сломанное выражение, сортировка и фильтр по `formula.*`.
TS-тесты остались на форматирование и разбор: `properties.test.ts` проверяет `baseProperty`
(подписи `file.*` и префикс `note.`), `baseFormat.test.ts` — `parseBase`/`serializeBase`,
`cardCreation.test.ts` — содержимое создаваемой заметки.

Проверка:

```bash
cd obsidium-app/core && cargo test bases
cd obsidium-app && npx vitest run src/modules/bases
cd obsidium-app && npx vitest run src/components/Editor/extensions/baseFence
```

Любое изменение семантики делается в Rust-движке и в `tests.rs`; если меняется разбор `.base`,
дополняется `baseFormat.test.ts`.
