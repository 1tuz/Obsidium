## Пять workflow и их зоны ответственности

| Файл | Когда запускается | Что делает |
| --- | --- | --- |
| `ci.yml` | push в любую ветку кроме `main`, pull request в `main` из форка, `workflow_dispatch` | Роутинг по изменённым файлам, статический анализ, `tsc`, связанные тесты, `cargo test` изменённых крейтов, автомерж ветки владельца |
| `nightly-tests.yml` | Расписание `23:00 UTC`, `workflow_dispatch` | Полный `npm test`, сборка фронта, `cargo test --workspace`, тесты установщиков, бюджет производительности, компиляция под macOS и Windows |
| `release.yml` | push тега `v*`, `workflow_dispatch` (только существующий тег) | Preflight-проверки, сборка Windows/macOS/Ubuntu, подпись обновлений, публикация релиза |
| `build-macos-app.yml` | `workflow_dispatch` | Быстрый артефакт `.app` для проверки без релиза |
| `sync-upstream.yml` | Расписание `06:23 UTC`, `workflow_dispatch` | Перенос ядра из upstream, PR при успехе, задача при конфликте ([[upstream-sync]]) |

Дублирующих конвейеров нет: `release.yml` не повторяет проверки `ci.yml`, он делает только то, чего
в push-прогоне быть не может — проверку релизного контракта, подпись и публикацию.

## Почему pull_request только для форков

Ветка владельца уже проверяется на push, и автомерж открывает PR ровно из этого прогона. Второй
прогон на `pull_request` был бы тем же самым набором проверок за те же минуты. У форка своего push
в репозиторий нет, поэтому его PR — единственная возможность что-то проверить. Отсюда условие на
job `route`: `github.event_name != 'pull_request' || github.event.pull_request.head.repo.fork`.
Если job `route` пропущен, остальные тоже пропускаются, и workflow честно показывает «skipped».

## Роутинг изменённых областей

`scripts/ci-routing.mjs` отвечает только на вопрос «запускать ли проверки». Что именно проверять,
решает `dorny/paths-filter` по фильтрам `.github/filters.yml`:

| Флаг | Область | Что запускает |
| --- | --- | --- |
| `frontend_types` | TS/TSX, конфиги, скрипты | `npx tsc --noEmit` |
| `frontend_related` | изменённые `.ts/.tsx/.js/.jsx` | `scripts/run-related-vitest.mjs` — только связанные тесты |
| `frontend_full` | манифест, конфиги Vite/TS, CSS/JSON, `src/styles/**` | полный `npm test` |
| `rust_core` / `rust_app` / `rust_cli` | соответствующие каталоги | `cargo test -p <крейт>` |
| `rust_workspace` | `Cargo.toml`, `Cargo.lock`, toolchain | `cargo test --workspace` |
| `workflow` | `.github/**`, скрипты роутинга | проверка YAML (строгий парсер, ловит дубли ключей), `actionlint`, тесты роутинга |
| `release_contract`, `installer_scripts` | контракт релиза, установщики | адресные тесты |

Ручной запуск `workflow_dispatch` включает все лёгкие флаги разом, поэтому полную проверку можно
получить без тега.

## Что добавлено 22.10.2026

- **PR-проверки для форков** (см. выше) — раньше PR из форка не проверялся вообще.
- **Job `performance`** в nightly: `benchmark_search_pipeline` и `benchmark_indexing` на 1000 и
  10000 заметках, потолок через `OBSIDIUM_BENCH_BUDGET_MS` (заведомо щедрый: цель — поймать
  случайный квадратичный проход, а не шум раннера), логи замеров уходят артефактом.
- **Job `compile`** в nightly: `cargo check --workspace --all-targets` под `aarch64-apple-darwin` и
  `x86_64-pc-windows-msvc`. Это ловит ошибки в `cfg`-ветках, которые ubuntu-тесты не видят, и стоит
  дешевле полной сборки.

## Правила, которые нельзя нарушать

- Проверку не отключают ради зелёного статуса; красный тест чинится.
- Устаревшие запуски одной ветки/PR отменяются через `concurrency`, кроме релиза и nightly
  (`cancel-in-progress: false` там, где прогон дорогой и не должен обрываться).
- Кэш зависимостей — только в Actions (`Swatinem/rust-cache`, `setup-node` с `cache: npm`).
- Локально не запускаются полные `cargo test --workspace`, `npm test` и ресурсоёмкие сборки: это
  работа ночного прогона. Локально допустимы `cargo check -p aquilum-core`, `npx tsc --noEmit` и
  тесты затронутого модуля.
- Перед коммитом с изменениями workflow: `ruby scripts/check-workflow-yaml.rb` (отклоняет дубли
  ключей) и `actionlint`.

## Когда красное

1. Открыть журнал конкретного job, а не сводку workflow.
2. Найти первое упавшее задание: дальше по цепочке ошибки обычно следствие.
3. Починить причину, перезапустить только нужный job (`gh run rerun --job <id>` локально не
   требуется — достаточно push в ветку, `concurrency` отменит устаревший прогон).
4. Если проверку получить не удалось (нет сети, лимит минут, падение раннера), в отчёте и в
   [[Что осталось сделать]] состояние пишется как «не проверено», а не «готово».
