# Канбан-представление Bases

## Связанные документы

- [[bases-engine]] — где считаются фильтры, сортировка и группы.
- [[dataview-queries]] — запросы и поля заметок.
- [[frontmatter-field-index]] — индексируемые поля frontmatter.
- [[notes-gate]] — запись через общий шлюз.

Канбан — один из типов представления в `.base`. Поле `groupBy.property` задаёт колонки, а
`groupOrder` задаёт их порядок и сохраняет пустые колонки. Если `groupBy` отсутствует, используется
`status`; значения, которых нет в `groupOrder`, сортируются по алфавиту с учётом чисел, направление
берётся из `groupBy.direction`.

Моделью остаётся `.md` и файл `.base`; отдельная база данных для доски не создаётся.

Неизвестное выражение или оператор фильтра оставляет строки видимыми и показывает предупреждение, чтобы
не выдать неполную выборку за точный результат. Формулы, summaries и неизвестные типы view сохраняются
в исходном `.base`, но не исполняются как в Obsidian.

## Перетаскивание карточек

Перетаскивание меняет значение свойства заметки во frontmatter (`groupBy.property`), а не текст
заметки. Доска работает на нативном HTML5 drag-and-drop: карточка помечена `draggable`, колонка —
`data-kanban-column`, события `dragstart`, `dragover`, `drop` и `dragend` заменили pointer capture.
Перед перемещением срабатывают те же ограничения: свойства `file.*` и `formula.*` только для чтения,
массивы не перетаскиваются, конфликт членства в доске отклоняется. Запись идёт через
`writeFileAtomic` с хэшем снимка, перечитанного перед изменением, поэтому конфликт с внешним
изменением не перезаписывает файл.

### Почему оптимистичное обновление с откатом

Карточка переезжает в локальной карте переопределений сразу, не дожидаясь `onCommit`: доска должна
реагировать за один кадр, иначе перетаскивание выглядит сломанным. После успешной записи
переопределение снимается — оценка `.base` уже содержит новое значение. При ошибке переопределение
удаляется, карточка возвращается в исходную колонку, а причина показывается через
`bases.kanbanMoveError`: интерфейс не должен показывать колонку, которой нет на диске. `<select>`
на карточке остаётся альтернативой для клавиатуры. Порядок колонок по-прежнему задаёт `groupOrder`,
неизвестные значения дописываются в конец, пустые колонки сохраняются, карточки без значения
остаются в «Не распределено».

## Статусы markdown-задач

Чекбоксы в тексте заметки — отдельная модель: их разбирает и меняет модуль `core/src/search/tasks/`,
а не доска.

| Статус | Маркер |
| --- | --- |
| `todo` | `[ ]` |
| `doing` | `[/]` |
| `done` | `[x]` |

Разбор считает закрытой любую задачу с непробельным маркером, включая `[-]` (отменённую).

`taskId` — первые 16 hex-символов blake3 от текста задачи без пробелов по краям плюс `:` и номер
вхождения среди одинаковых текстов. Поэтому id переживает правки в других местах заметки и меняется
только вместе с текстом самой задачи.

`update_task_status(path, task_id, new_status)` в `core/src/search/tasks/status.rs` читает заметку
через `read_file_snapshot_impl` (нормализованный текст и хэш исходных байт) и переписывает только
символ маркера через `edit::set_status`; отступ, маркер списка (`-`, `1.`, `1)`), остальной markdown
и CRLF остаются байт в байт. Если маркер уже в нужном статусе, функция возвращает `Ok(false)` и файл
не пишет. Иначе вызывается `write_file_atomic_impl(path, content, Some(hash))`: атомарная замена с
проверкой ожидаемого хэша, поэтому параллельное внешнее изменение даёт `FileCommandError::Conflict`,
а не потерю чужой правки. Неизвестный `taskId` возвращает `FileCommandError::Task` с текстом
«Задача не найдена: …», неизвестное имя статуса отклоняется с «допустимо todo, doing или done».

Tauri-команда `update_task_status(path, taskId, newStatus)` в `src-tauri/src/search/commands.rs`
вызывает это ядро через `run_blocking` и возвращает признак изменения.

Граница между моделями: карточка доски — это заметка, и перетаскивание пишет свойство frontmatter.
Статус чекбокса меняется только через API задач. Смешивать их нельзя: маркер `[ ]` во frontmatter
или frontmatter в строке задачи испортит файл.

## Boards в интерфейсе

Раздел Boards в левом Sidebar показывает Kanban-представления из всех `.base` текущего vault и
сохраняет вложенность папок. Сканирование начинается только при открытии раздела; сведения о
прочитанных `.base` кэшируются в памяти по хэшу файла. Пока Boards открыт, `workspace-changed`
обновляет список после создания, удаления, переименования или изменения `.base`; после закрытого
изменения список перечитывается при следующем открытии. Закрытая панель не сканирует vault и не
держит отдельный индекс.

У каждой доски есть меню переименования и удаления. Переименование проходит через общий файловый
шлюз и сохраняет защиту от конфликтов имён; вместе с именем `.base` меняется имя первой Kanban-вкладки,
а остальные представления сохраняют свои имена. Удаление отправляет `.base` в корзину после подтверждения.
Меню доски расположено в строке первого представления, чтобы не отделяться от названия Kanban-вкладки.
Карточки без значения `groupBy.property` остаются в колонке «Не распределено», чтобы их можно было
переместить в колонку со значением.

Выбор представления открывает исходный `.base` сразу на выбранном view. Обычное открытие возвращает
к последнему view, сохранённому по workspace и относительному пути в общей `ui-state.sqlite3`.
Изменение списка views ограничивает сохранённый индекс последним существующим view.

Создание доски пишет обычный `.base` с `filters`, `views`, `type: kanban`, `groupBy` и `groupOrder`;
значения группы задают и пустые стартовые колонки. Доска не получает собственную схему или хранилище.

Новая доска по умолчанию ограничена тегом `board/<имя-доски>`; пользователь может задать другой тег.
Если файл с таким именем уже есть, тег строится по фактическому свободному имени файла. После создания
открывается первая вкладка доски. Переименование обновляет путь и имя первой Kanban-вкладки в списке
сразу, а затем повторно сверяет данные с диском; активный редактор получает переименование через
общий callback файлового дерева.

В macOS нативная тема окна повторяет настройку внешнего вида: для `system` WebView выбирает тему
операционной системы, а для `light` и `dark` кнопки заголовка окна переключаются вместе с интерфейсом.

Add to board автоматически меняет только один точно распознанный фильтр `property == "value"` или
`file.hasTag("tag")`. Запись перечитывает заметку и использует её хэш, а изменение frontmatter
затрагивает только membership-свойство или список тегов и пустое свойство колонок. Существующие
конфликтующие значения, массивы в несовместимых полях, folder-фильтр, весь vault и составные,
отрицательные или неподдерживаемые фильтры не переписываются автоматически; интерфейс показывает
причину. Remove from board удаляет только точное значение membership-свойства или тег этой доски и
его потомков, если они входят в её иерархический фильтр. Остальные теги и metadata остаются на месте.
