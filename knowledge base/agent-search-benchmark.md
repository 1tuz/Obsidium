# Бенчмарк поиска для агента

Статус: актуально на 2026-10-23, замер на коммите `b6a1a60` (`b6a1a6078851a8ded74d3ac185157e1dd3115160`). Корпус — 180 синтетических заметок, вопросов — 50. Числа ниже получены одним прогоном `node scripts/agent-bench.mjs --strategies rg,context,mcp --warm 2`; отчёт сгенерирован тем же прогоном через `--report`, а не переписан руками.

Документ отвечает на один вопрос: что дешевле и точнее для внешнего агента — искать строку через `ripgrep` и читать файлы целиком, пользоваться прежними инструментами MCP (`search` плюс `note read`) или звать `context search`, который возвращает готовые фрагменты. Замер не доказывает превосходство одного способа. Он показывает цену каждого: сколько вызовов, сколько байт контекста, сколько времени и насколько часто ожидаемая строка действительно попадает в ответ.

## Что измеряется

Три стратегии повторяют три реальных сценария работы агента:

| Стратегия | Что делает | Вызовы |
| --- | --- | --- |
| `rg` | `ripgrep --json` по словам запроса, затем чтение каждого найденного файла целиком | 1 поиск + 1 чтение на файл |
| `mcp` | `search` по индексу, затем `note read` для трёх верхних результатов | 1 + до 3 |
| `context` | один `context search` с настройками по умолчанию; для вопросов про граф — ещё `context connections` | 1 или 2 |

Для точных строк `rg` ищет запрос целиком как фиксированную строку. Для остальных вопросов запрос режется на слова, служебные слова выбрасываются, и `rg` ищет любое из слов. Это не идеальный агент, а агент, каким он был до `context search`: он ищет ключевые слова и читает найденное.

Метрики считаются по одному вопросу, затем усредняются:

- **Recall@5 и Recall@10** — доля ожидаемых заметок, попавших в первые 5 или 10 путей. Для вопроса с пустым эталоном recall равен 1, только если стратегия не вернула ничего.
- **MRR** — обратный ранг первой ожидаемой заметки. Единица означает, что ответ стоял первым; ноль — что ожидаемого пути не было вовсе.
- **supported** — самая строгая метрика: попала ли в выданный контекст именно ожидаемая строка. Для `context` проверяется, что `lineStart`/`lineEnd` фрагмента накрывают ожидаемый диапазон. Для `mcp` — что прочитанный текст содержит ожидаемую строку: у `search` нет номеров строк, поэтому диапазон проверить нечем. Для `rg` — что она есть в прочитанном файле. Для вопроса с пустым эталоном `supported` равен 1, если ничего не найдено.
- **calls** — среднее число вызовов инструмента на вопрос. Это цена в круглых поездках, а не в токенах.
- **bytes и ~tokens** — средний объём выдачи инструментов, которую получает модель: JSON плюс прочитанные файлы. Токены приблизительные: `bytes / 4`, как и написано в отчёте. Для кириллицы эта оценка завышает число токенов, потому что один символ занимает два байта UTF-8.
- **p50/p95 latency** — время одного ответа стратегии, включая запуск процесса CLI. «Холодный» замер для `context` и `mcp` идёт на пустом `OBSIDIUM_DATA_DIR`: в него входит построение индекса. «Тёплый» — на уже построенном индексе, после прогрева. У `rg` индекса нет, поэтому холодный и тёплый замеры совпадают.
- **false positives** — вопросы с пустым эталоном, на которые стратегия всё-таки что-то вернула.
- **mustNotInclude** — пути, которых в верхней пятёрке быть не должно. Это ловушки near-duplicate и устаревших данных: архивная копия не должна выдаваться за актуальную заметку.

## Как устроен корпус

Корпус собирает `scripts/agent-bench-corpus.mjs`. Генератор детерминированный: seed `20261023`, никакого `Math.random`, поэтому два прогона на одной машине дают одинаковые 180 заметок. Папки: `Kubernetes/`, `Jenkins/`, `Ingress/`, `TLS/`, `Databases/`, `Проекты/`, `Архив/`. У каждой заметки есть frontmatter с `type`, `status`, `tags` и `updated`.

В корпусе намеренно заложены свойства, на которых поиск ломается:

- хабы (`Обзор Kubernetes`, `Обзор Jenkins`, `Обзор Ingress`, `Обзор TLS`, `Обзор баз данных`, `Обзор проектов`), на которые ссылается большинство заметок раздела;
- цепочка из двух шагов `Пайплайн деплоя` → `Мост Jenkins и Ingress` → `Ingress для деплоя`;
- 23 заметки-сироты без входящих и исходящих ссылок;
- markdown-задачи в части заметок;
- кириллические имена файлов и кириллический текст;
- три заметки больше 20 КБ (25 049, 25 004 и 25 067 байт);
- шесть пар near-duplicate с перекрытием 80–90 %: архивная копия отличается одной строкой (порт, версия, путь, число сервисов);
- пять противоречий: версии cert-manager, Java, PostgreSQL, Kubernetes и таймаут ingress-nginx;
- четыре заметки с битыми wiki-ссылками;
- восемь заметок с упоминанием существующего заголовка без `[[...]]`.

Вопросы лежат в `scripts/agent-bench-questions.json`. Их 50, и они покрывают точную строку, русский и английский запросы, перефраз, синтез по нескольким заметкам, обход графа, near-duplicate, противоречия, устаревшие данные, большие заметки и три вопроса с пустым эталоном. Эталон собран из плана генератора: пути и строки-маркеры заданы там же, а `lineStart`/`lineEnd` вычисляются по готовому файлу, а не проставляются руками. Поэтому номера строк в JSON соответствуют реальному корпусу. При изменении корпуса вопросы надо перегенерировать той же командой.

## Где что выигрывает

**`rg` выигрывает там, где ответ — точная строка в одном файле.** На exact-вопросах у него Recall@5 100 %, MRR 1,000, два вызова и 1,3 КиБ контекста: один `rg`, одно чтение. На больших заметках он тоже силён по попаданию: 100 % Recall@5 и 100 % supported, потому что читает файл целиком. Но за это платит 25,5 КиБ на вопрос и не различает архивную копию: на near-duplicate его Recall@5 падает до 66,7 %, а четыре архивных пути попадают в верхнюю пятёрку.

**`rg` проигрывает на естественном языке и на графе.** Русская морфология рассыпается: запрос «как откатить деплой» даёт 40 % Recall@5 и 22 вызова, потому что `rg` тянет все файлы со словом «деплой». На graph-вопросах он делает 45,6 вызова и отдаёт 70,6 КиБ — это худший результат по объёму контекста, хотя ожидаемая строка в итоге находится. `rg` не понимает ссылок, поэтому «два шага от Jenkins» для него не существует.

**`context search` выигрывает на больших заметках и на графе.** На large-вопросах он даёт 100 % Recall@5 и 100 % supported при одном вызове и 2,0 КиБ: вместо всего файла приходит фрагмент вокруг нужной строки. На graph-вопросах Recall@10 — 90 %, supported — 80 %, два вызова и 20,4 КиБ; это лучший Recall@10 среди трёх стратегий. На synthesis supported 40 % против 20 % у `mcp`: фрагменты из двух заметок попадают в один ответ чаще, чем три прочитанные заметки. На exact-вопросах `context` тоже держит 100 % Recall@5, но стоит 7,1 КиБ и одного вызова.

**`context search` проигрывает в общем Recall и в русских запросах.** Общий Recall@5 — 73 % против 89 % у `mcp`. Русский запрос «настройка агентов Jenkins» не находит `Агенты и метки` вовсе: графовые и теговые сигналы поднимают соседей раздела выше точного текстового совпадения. На противоречиях — 60 % против 100 % у `mcp`. Из шести near-duplicate-ловушек архивная копия попадает в верхнюю пятёрку в трёх случаях (`q31`, `q32`, `q35`), и во всех трёх актуальная заметка стоит выше копии. Это следствие штрафа за путь под `Архив/`: до него копия оказывалась рядом или впереди. Штраф не убирает копию из выдачи совсем — она по-прежнему содержит те же слова, — но перестаёт выдавать её за ответ.

**`mcp` выигрывает в «найти правильную заметку».** Общий Recall@5 89 %, Recall@10 91 %, русские запросы 100 %, противоречия 100 %. Это по-прежнему лучший способ получить список кандидатов. Но за это платит 3,7 вызова, 299,0 мс тёплого ответа и 653,1 мс холодного. И `note read` по умолчанию отдаёт 8000 символов, поэтому на всех трёх заметках больше 20 КБ ожидаемая строка в прочитанный текст не попадает: supported 0 % при Recall@5 100 %. Это не артефакт бенчмарка, а реальное ограничение инструмента.

**Ни одна стратегия не выигрывает везде.** Если нужна точная команда или строка — `rg` дешевле и точнее по рангу, но контекст надо ограничивать. Если нужен ответ из нескольких заметок или обход ссылок — `context search` даёт компактные фрагменты и лучший Recall@10 на графе. Если нужно сначала найти заметку, а потом решать, что с ней делать — `mcp search` даёт лучший Recall. Идеальный агент, вероятно, комбинирует: `context search` для фрагментов, `search` для списка кандидатов, `rg` для точных строк и чтение файла только после того, как стало ясно, что он нужен.

Вопросы, которые провалились заметнее всего:

- `context`: `q08-ru-key-rotation`, `q10-ru-jenkins-agents`, `q12-en-502`, `q14-en-parallel`, `q17-paraphrase-extend-cert`, `q20-paraphrase-slow-queries`, `q21`, `q22`, `q25`, `q27`, `q29`, `q38`, `q39`, `q41`; плюс нарушения `mustNotInclude` на `q04`, `q31`–`q36`, `q42` и `q43`.
- `mcp`: `q14-en-parallel` и `q19-paraphrase-memory-limit` (ожидаемая заметка есть в выдаче, но не в первых трёх прочитанных), `q21`–`q25` (синтез), `q27`–`q30` (граф), `q45`–`q47` (большие заметки), плюс нарушения `mustNotInclude` на `q04`, near-duplicate и stale.
- `rg`: `q06`–`q08` (русская морфология), `q12`, `q14`, `q34`, `q36`, `q38`, `q39`; на `q21`–`q25` и `q27` он находит ожидаемое, но платит десятками вызовов и десятками килобайт.

## Ограничения

**Токены приблизительные.** `bytes / 4` — грубая оценка. Для русского текста в UTF-8 байтов вдвое больше, чем символов, поэтому «токены» в таблице скорее завышены, чем занижены. Сравнивать стратегии по этой колонке можно, воспринимать её как счёт за токены — нельзя.

**Корпус синтетический.** Это не рабочая база на 800 заметок и не книги. Запросы и эталонные строки писались вместе с корпусом, поэтому формулировки местами слишком удобны для одной из стратегий. На реальной базе с шумом, опечатками и другими формулировками абсолютные числа будут ниже у всех.

**Одна машина, один прогон.** Замер снят на macOS, arm64, с прогретым кэшем файловой системы. Время включает запуск процесса CLI и не включает сеть. Холодный замер для `context` и `mcp` строит индекс заново на каждый вопрос: 448 мс и 653 мс в медиане. На другой машине и другом диске числа сдвинутся, особенно холодные. Порядок результатов при равных score тоже может меняться от прогона к прогону: на том же корпусе и коммите `context` давал Recall@5 71,0 % и 73,0 % в двух запусках. Разница в пределах двух процентных пунктов — это шум ранжирования, а не изменение кода.

**Ранжирование — часть методики.** `rg` сортирует файлы по числу совпадений, `context` добавляет узлы графа после результатов поиска, `mcp` читает ровно три верхних результата. Если поменять эти правила, изменятся Recall@5 и supported. `mustNotInclude` проверяется только по верхней пятёрке; более длинный хвост не наказывается.

**`context` работает с настройками по умолчанию.** Лимит 8 заметок, 12 000 символов, глубина графа 1. С `--limit 20` или `--graph-depth 0` числа будут другими. Бенчмарк измеряет именно дефолт, потому что агент по умолчанию ничего не настраивает.

**`mcp` не читает большие заметки целиком.** `note read` обрезает ответ до 8000 символов, поэтому supported на large-вопросах равен нулю. Это ограничение инструмента, а не ошибка подсчёта. Если агенту нужна строка в конце большой заметки, ему придётся передать `--limit` или `--offset`.

**`rg` может отсутствовать.** Если бинарника нет, стратегия помечается `skipped`, и числа для неё не выдумываются. В таблице отчёта она остаётся строкой «пропущен».

## Как повторить

Собрать корпус и вопросы заново:

```bash
node scripts/agent-bench-corpus.mjs --out /tmp/obsidium-bench \
  --questions scripts/agent-bench-questions.json \
  --manifest /tmp/obsidium-bench-manifest.json
```

Прогнать все стратегии и получить Markdown-отчёт:

```bash
node scripts/agent-bench.mjs --strategies rg,context,mcp --warm 2 \
  --report /tmp/agent-bench-report.md --json > /tmp/agent-bench-result.json
```

Проверить только `context` и `mcp`, как в приёмке:

```bash
node scripts/agent-bench.mjs --strategies context,mcp
```

Раннер сам собирает временный корпус, проверяет JSON вопросов (не меньше 40, все `expected` и `mustNotInclude` существуют в корпусе, покрыты все типы, есть три пустых эталона) и по умолчанию удаляет временную папку. `--keep` оставляет её для разбора, `--root DIR` задаёт место, `--seed N` меняет seed. Бинарник берётся из `OBSIDIUM_BIN` или из `obsidium-app/src-tauri/target/debug/obsidium`.

Если менялся корпус, вопросы надо перегенерировать: номера строк в JSON привязаны к конкретному тексту. Если менялся только код поиска, достаточно перезапустить раннер на прежнем JSON.
