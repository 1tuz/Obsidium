# Открытие заметки: из чего складывается время

Заметка фиксирует замеры пути открытия и то, что из них следует. Числа сняты в dev-сборке на рабочей машине владельца, база — 821 заметка. Разброс между открытиями одной и той же заметки доходил до двух раз, поэтому одиночному замеру верить нельзя: сравнивать нужно медиану из нескольких.

## Связанные документы

- [[render-performance-pass]] — бюджет парсинга и разбор прежнего круга оптимизаций.
- [[editor-viewport-decorations]] — почему семь сборщиков декораций делают семь обходов документа.
- [[book-widget-sync]] — как собираются данные книжных строк.
- [[editor-book-callout]] — ширина блочного виджета и measure-цикл.
- [[tab-switching]] — что происходит при возврате на вкладку.

## Чем меряем

`modules/perf/openTrace.ts` и `bootTrace.ts` поверх общего `trace.ts`. Отсчёт открытия начинается в `openNote`, то есть от щелчка пользователя; отсчёт запуска — от начала загрузки страницы. След печатается сам через 700 мс тишины простым текстом, одним `console.log`: таблицу из консоли нельзя выделить и скопировать, а замеры нужны в переписке.

Разметка живёт только в dev (`import.meta.env.DEV`), в релизе все вызовы возвращаются на первой строке. Это сознательно: мерить надо настоящие IPC и настоящий диск, а не синтетический стенд.

## Запуск

| Этап | мс |
| --- | --- |
| модули загружены и выполнены | 1340–1465 |
| React получил дерево | +0,5 |
| первый кадр приложения | +65…87 |

| база знаний известна | +116 |
| сессия вкладок загружена | +95 |

**Белый экран — это Vite, а не приложение.** 83% запуска уходит на отдачу и выполнение неупакованного графа модулей: CodeMirror собран из нескольких десятков пакетов, плюс yjs, плюс шрифты. В релизной сборке это один бандл, и числа там другие — сравнивать dev с релизом нельзя.

Единственная контролируемая часть графа — то, что попало в него зря. Читалка (`BookReader` → `ReaderEngine` → foliate) грузилась при каждом старте, хотя нужна только у книг: `useEditorReader` статически импортировал из неё `prefetchFoliate`. После перевода обоих на динамический импорт этап «модули» упал с 1551 до 1340–1465 мс.

## Открытие заметки

| Этап | Холодное открытие | Тёплый возврат |
| --- | --- | --- |
| React дошёл до запроса файла | 19–37 | — |
| файл прочитан с диска | +22…31 | — |
| реплика IndexedDB подключена | +5…27 | — |
| текст документа готов | +0,5 | 21–33 |
| редактор смонтирован | +20…46 | +25…56 |
| прокрутка восстановлена | +22…52 | +26…52 |
| **итого** | **100–197** | **80–105** |

Три вывода, которые меняли план по ходу.

**Реплика IndexedDB дешёвая.** Гипотеза, что она стоит 50–60 мс, не подтвердилась: 5–27 мс. Отказываться от durable-реплики ради скорости незачем.

**Тёплое переключение вкладки — 80–105 мс без единого обращения к диску.** Документ уже в памяти, файл не читается. Всё это время уходит на React (21–33 мс), создание CodeMirror (25–56) и восстановление прокрутки (26–52). Причина структурная: `App` рисует `EditorPane` только для активной вкладки, поэтому переключение уничтожает редактор и строит новый — со всеми декорациями и восстановлением позиции. Вкладка графа при этом остаётся смонтированной и просто прячется; к заметкам тот же приём не применён.

**Круг Tauri IPC за чтением файла — 22–31 мс.** Для маленького markdown-файла это цена самого круга, а не чтения. В JS её не сократить; сократить можно только число кругов.

## Что было исправлено по этим замерам

**Двойное монтирование редактора.** Ключ `EditorPane` содержал `documentId`, а тот приезжает асинхронно: редактор монтировался с ключом по пути, строил все декорации и через ~50 мс выбрасывался, когда ключ менялся. В следе это было видно как две отметки «текст документа» подряд. Теперь ключ по пути, а контроллер состояния подключается отдельным эффектом, когда `documentId` появляется.

Первая попытка была неверной: гейт «не рисовать редактор без `documentId`» уронил тест `creates a fresh editor instance when a sidebar selection replaces the active file`. Тест был прав — в его окружении `documentId` не разрешается вовсе, и гейт превратил бы это в вечно пустой экран вместо работающего редактора без сохранённой позиции.

**Два гейта на одну страницу.** Обложка показывалась по `isReady`, тело по `ready`, между ними был кадр с обложкой без текста. Теперь одно условие на всю страницу.

**Measure loop.** CodeMirror ругался «Measure loop restarted more than 5 times»: каждая группа книжных строк вешала свой `ResizeObserver` и писала `root.style.width`, а запись во время measure-цикла запускала его заново. Ширину теперь считает один `blockWidth.ts` на редактор — см. [[editor-book-callout]]. Предупреждение исчезло; время монтажа при этом заметно не изменилось, разброс между открытиями больше самой разницы.

**Блок dataview достраивался после открытия.** Префетчер запускал первый расчёт через дебаунс 250 мс, то есть уже после того, как прокрутка восстановлена и снят флаг `restoring`: блок вырастал, страница сдвигалась, и в сохранённую позицию писалась смещённая камера. После правки этап `dataview` укладывается в 27–30 мс и завершается **раньше** восстановления прокрутки (54–68 мс), а сам расчёт вынесен ещё выше — в момент, когда файл только что прочитан с диска. Разбор — [[dataview-queries]], раздел «Отрисовка блока».

## Что осталось и чего это стоит

- **Живые вкладки** — держать 2–3 последних редактора смонтированными и скрытыми, как уже сделано для графа. Убирает разом создание CodeMirror, восстановление прокрутки и повторный резолв ссылок при переключении: 80–105 мс превращаются почти в ноль. Самая крупная из оставшихся правок и единственная, меняющая модель вкладок.
- **Двойной резолв вики-ссылок.** У заметки со списком книг ссылки резолвились дважды: 154,6 и 294,5 мс. Восстановление прокрутки меняет видимую область, там находятся новые цели, уходит второй круг — 140 мс, половина времени открытия этой заметки. Уйдёт, если прокрутка встаёт до первой сборки декораций.
- **Прокрутка восстанавливается после кадра** (`requestMeasure`), поэтому страница рисуется сверху и прыгает. 22–52 мс и видимый рывок.
- **Данные книжных строк приезжают после монтажа**, потому что проход живёт в `ViewPlugin`, а его конструктор запускается только при создании редактора. Заготовка строки видна ~70–120 мс. Данные зависят только от текста заметки, который известен до создания редактора. Для dataview это уже сделано прогревом из `useEditorDoc` — приём переносится сюда один в один.
- **`Forced reflow` 30–40 мс остаётся и принадлежит CodeMirror.** Все три наших места чтения раскладки проверены обёрткой-детектором и исключены: книжные строки и картинки не дали ни одной отметки, таблица дала 5–7 мс. Оставшееся — measure-цикл самого CodeMirror, которому приходится мерить блочные виджеты, чтобы построить карту высот. Уменьшается только объявлением высот виджетов, а не правкой нашего кода.

## Как этим пользоваться дальше

Открыть заметку в dev-сборке и прочитать след в консоли. С третьего открытия одной и той же заметки в первой строке появляется медиана и разброс — сравнивать правки нужно по ней, а не по одиночному числу.
