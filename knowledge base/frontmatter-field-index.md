# Индекс полей frontmatter

Поля frontmatter лежат в поисковом индексе типизированными строками таблицы `note_fields` и заполняются тем же инкрементальным проходом, который строит wiki-граф. До этого структурированного хранилища полей не было вовсе: `strip_frontmatter` выбрасывал блок из полнотекстового индекса, оставляя один `author`, а всё, что хотело прочитать метаданные чужой заметки, открывало её файл.

Это первый слой под язык запросов: исполнять `WHERE type = "book"` не на чем, пока поля не лежат в индексе. Язык поверх него уже есть — [[dataview-queries]], — но слой окупается и сам по себе.

## Что это дало

Две горячие дороги перестали открывать файлы.

**Книжные виджеты.** Каждая строка `[!book]` со вики-ссылкой делала два круга через IPC: разрешала ссылку и **читала связанный файл целиком** через `readFileSnapshot`, чтобы разобрать его frontmatter в TypeScript. Двадцать строк на странице — двадцать полных чтений файлов и двадцать разборов. Теперь данные всей страницы собираются одним проходом за два круга: `resolve_wiki_links` списком целей и `get_note_fields` списком путей, файлы не открываются. Подробности прохода и почему строка без данных рисуется пустой заготовкой — в [[book-widget-sync]].

**Выборка по полям.** `find_notes` обходил всю базу и читал первые 8 КБ каждого файла: по замеру в [[mcp-agent-ergonomics]] это 47 мс сверх круга на 821 заметке, и почти всё время уходило на 821 открытие файла. Теперь пути сужаются запросом по индексу `note_fields_lookup`, а поля кандидатов читаются одним `SELECT ... WHERE path IN (...)`.

Замер новой дороги не снят — его нужно делать после пересборки приложения тем же круговым вызовом по HTTP, что и прежний, иначе числа несравнимы.

## Инвариант: индекс отвечает за чужие заметки, буфер — за открытую

**Открытая заметка разбирается в памяти, а не через индекс.** `useEditorBookPage` парсит текущий текст редактора на каждое нажатие клавиши: обложка, тип страницы и прогресс обязаны меняться в том же кадре, что и YAML. Индекс всегда отстаёт от буфера — он обновляется после записи файла и прохода воркера, — поэтому подменять им живой разбор нельзя ни при каких условиях. Индекс отвечает только на вопрос «что во frontmatter *другой* заметки».

Из этого следует, что парсеров frontmatter в проекте два, и это не дубль по недосмотру: `modules/docs/frontmatter.ts` читает несохранённый текст в браузере, `search/fields/parse.rs` — сохранённый на диске. Свести их в один нельзя, не заплатив круг IPC за каждое нажатие.

Ценой этого решения идёт риск расхождения семантики. Сейчас она различается так:

| Конструкция | TypeScript, живой буфер | Rust, индекс |
| --- | --- | --- |
| `key: value` | да | да |
| `key value` без двоеточия | да, делит по первому пробелу | нет, строка пропускается |
| `[a, b]` | массив | массив |
| Список с дефисами под ключом | нет | да |
| Блочное значение `\|` и `>` | нет | да |
| Комментарий `#` | нет | да, строка пропускается |

Практического расхождения для книжных виджетов нет: все книжные поля пишет само приложение через `setFrontmatterField`, всегда в форме `ключ: значение`. Но если руками написать `tags:` со списком через дефисы, живой редактор тегов не увидит, а индекс увидит.

## Модель значения

`Field` — исходное написание ключа, тип, каноничный текст и элементы списка:

| Тип | Когда | Текст |
| --- | --- | --- |
| `Text` | всё остальное | как в файле, без кавычек |
| `Number` | значение начинается с цифры или знака и разбирается как `f64` | как в файле |
| `Bool` | `true` или `false` в любом регистре | как в файле |
| `List` | `[a, b]` или список с дефисами | элементы через запятую |

Проверка «начинается с цифры или знака» стоит перед `parse::<f64>()` намеренно: без неё `author: Infinity` и `author: NaN` становились бы числами. А `pages: 0/0` и `created: 31-08-2026` числами не становятся — на это есть тесты, потому что обе строки реально встречаются в базе.

Текст поля-списка — это его элементы через запятую, поэтому `tags: []` даёт **пустой текст**. Отсюда изменение поведения: раньше `pairs` возвращал для этого поля строку `"[]"`, и `find_notes` с условием `has: ["tags"]` считал поле заполненным. Теперь пустой список — незаполненное поле, что и правильно, но заметки из шаблона содержат `tags: []`, так что разница видна сразу.

## Схема и миграция

```sql
CREATE TABLE note_fields (
  path TEXT NOT NULL,
  ordinal INTEGER NOT NULL,   -- порядок в файле, восстанавливает исходную последовательность
  key TEXT NOT NULL,          -- исходное написание
  key_lower TEXT NOT NULL,    -- ключ для поиска
  kind INTEGER NOT NULL,
  text TEXT NOT NULL,
  text_lower TEXT NOT NULL,   -- значение для поиска
  items TEXT,                 -- JSON-массив, заполнен только у списков
  PRIMARY KEY(path, ordinal)
) WITHOUT ROWID;
CREATE INDEX note_fields_lookup ON note_fields(key_lower, text_lower);
```

Отдельные колонки `key_lower` и `text_lower` нужны потому, что `lower()` в SQLite работает только с ASCII, а ключи здесь кириллические: `Путь к файлу` обязан находиться в любом написании. Регистр снимает Rust через `to_lowercase()`, и результат кладётся рядом с исходным значением. Элементы списка хранятся JSON-массивом в той же строке, а не отдельной таблицей: разбирать `text` обратно по запятой было бы потерей данных на элементе с запятой внутри, а вторая таблица не нужна, пока по элементам не ищут.

Версия схемы поднята до `user_version = 12`, и миграция **сбрасывает `analyzer_version` в ноль для всех строк**. Иначе новых полей не появилось бы ни у одной существующей заметки: `probe` пропускает файл, у которого совпали отпечаток и версия анализатора, поэтому без сброса `note_fields` осталась бы пустой до первой правки каждого файла. Сброс `analyzer_version` выбран вместо подъёма `ANALYZER_VERSION`: последний меняет имя каталога Tantivy и начинает полнотекстовый индекс с нуля, то есть на время миграции поиск ничего не находит. Сброс версии в строках переиндексирует те же файлы в существующем каталоге, и поиск продолжает работать всю миграцию.

**Ловушка в лестнице миграций.** До этой правки `ADD_CREATED_COLUMNS` выполнялся в ветке `version < SCHEMA_VERSION` без своей проверки версии. Пока `SCHEMA_VERSION` равнялась 11, это было безвредно, потому что в ветку попадали только базы версий 9 и 10. С подъёмом до 12 в ту же ветку попала база версии 11, и повторный `ALTER TABLE` упал бы на «duplicate column name», а вместе с ним — открытие индекса целиком. Каждый шаг лестницы теперь закрыт своей проверкой `if version < N`.

## Запасные дороги

У обоих потребителей есть путь на случай, когда индекса ещё нет, и оба сужены до одного явного условия.

`get_note_fields` читает **начало файла** (8 КБ, frontmatter стоит в начале) для тех путей, которых нет в `note_fields`. Это случай только что созданной заметки: воркер до неё ещё не дошёл, а виджет уже рисуется. Без этой дороги новая страница книги показывалась бы пустой до конца индексации.

Ответ этой команды идёт **в порядке запроса и той же длины**: путь за пределами базы занимает своё место с пустыми полями, а не выпадает из ответа. Иначе пакетный вызов нельзя было бы сопоставить с запросом по индексу, а сопоставление по строке пути ненадёжно — Rust отдаёт канонизированный путь, который может отличаться от присланного регистром.

`find_notes` спрашивает у сервиса `note_fields_for_filter`, и тот возвращает `None`, пока индекс не в состоянии `Ready` или обновляется. На `None` инструмент обходит диск, как раньше. Причина в том, что выборка обязана быть полной: неполный индекс молча вернул бы часть заметок, и агент принял бы это за ответ. Логика отбора при этом одна и та же — `matches` и `value_of` получают одинаковые пары ключ-значение независимо от источника.

## Что осталось за границей

- **Вложенность.** Строка с отступом и двоеточием читается как самостоятельное поле верхнего уровня, а не как вложенный объект. Так же вело себя прежнее чтение. Из-за этого в запросах не работает `book.author` — см. границы в [[dataview-queries]].
- **Поиск по элементам списка.** `match` в `find_notes` сравнивает значение целиком, поэтому «все заметки с тегом `fiction`» не выражается: элементы в индексе есть, но условие по ним не построено. Это самое очевидное следующее улучшение.
- **Типизированная сортировка.** `sort` в `find_notes` по-прежнему сравнивает значения как строки, поэтому `rating: 10` встаёт перед `rating: 5`. Тип поля в индексе уже лежит, так что починка дешёвая, но она меняет поведение существующего инструмента.
