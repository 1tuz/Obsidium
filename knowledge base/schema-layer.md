# Слой схемы объектов

Статус: актуально на 2026-10-25.

Схема описывает типы объектов vault (книга, человек, проект) и их свойства. Она отвечает на два
вопроса: «что за тип у этой заметки» и «соответствует ли заметка своему типу». Markdown остаётся
источником истины: тип живёт в frontmatter, а `schema.json` — только описание допустимых типов.

## Где лежит файл

`<vault>/.obsidium/schema.json`. Файла нет — реестр пустой, и это нормальное состояние: старые vault
открываются без миграций.

```json
{
  "version": 1,
  "types": [
    {
      "name": "Book",
      "icon": "book",
      "color": "#c0a",
      "extends": "Entry",
      "properties": [
        { "name": "author", "kind": "text", "required": true },
        { "name": "status", "kind": "select", "options": ["reading", "done"], "default": "reading" },
        { "name": "published", "kind": "date", "format": "DD.MM.YYYY" }
      ]
    }
  ]
}
```

Поля типа: `name`, `icon?`, `color?`, `extends?`, `properties`. Поля свойства: `name`, `kind`,
`options`, `required`, `default?`, `format?`. `kind` — одно из `text`, `number`, `date`, `tags`,
`select`, `multiSelect`, `checkbox`, `url`, `phone`, `email`. В JSON всё в camelCase
(`multiSelect`), лишние поля и неизвестные значения `kind` отвергаются при разборе: опечатка должна
быть ошибкой, а не молча потерянным полем.

## Почему заметка без `type:` — это `Note`

`type:` читается из frontmatter как строка или массив строк (`type: [Book, Entry]`). Если ключа нет,
заметка получает встроенный тип `Note` без свойств: проверять нечего, нарушений нет.

Если `schema.json` нет или в нём пустой `types`, `type:` игнорируется целиком: `type: book` в старом
vault — это всё ещё `Note`, а не «неизвестный тип». Поэтому любой старый vault и любая заметка,
созданная до появления схемы, валидны по определению; неизвестный тип становится ошибкой только
после того, как в схеме появился хотя бы один тип.

`Note` встроенный: его нельзя описать в `schema.json` (валидация вернёт ошибку), и его свойства
нельзя переопределить. Иначе пользователь мог бы сделать `Note` обязательным и сломать весь vault
одной правкой схемы.

## Наследование `extends`

`extends` ссылается на имя другого типа. Эффективный тип — свойства родителя, затем свойства
ребёнка; свойство с тем же именем (регистр не важен) заменяется описанием ребёнка. Поэтому
`required: true` у родителя действует на все дочерние типы, пока ребёнок явно не снимет его.

Ошибкой схемы считаются: неизвестный родитель, наследование самого себя, цикл (`A → B → A`),
дубликат имени типа или свойства, `select`/`multiSelect` без `options`, `options` у другого вида,
`default`, не соответствующий `kind` (в том числе значение вне `options`).

`SchemaRegistry::type_of` возвращает уже развёрнутые типы: с наследованием, но без записи в заметку.
`type: [A, B]` проверяется по обоим типам; одинаковые нарушения не дублируются.

## Проверка заметки

`validate_note` возвращает `Vec<Violation>`; у нарушения есть `property` и `reason`. Проверяются:

- `required` — ключ есть и значение непустое;
- `kind` — число, дата, boolean, список тегов, одно значение или несколько из `options`;
- `options` — значение `select`/`multiSelect` должно быть в списке;
- ссылка на тип, которого нет в схеме, — нарушение с `property: "type"`.

Лишние поля frontmatter не ошибка: схема описывает известные свойства, но не запрещает остальные.
`default` в заметку не записывается — он проверяется только при сохранении схемы.

Дата без `format` принимает общую грамматику проекта (`2026-10-25`, `25.10.2026`, время через `T`
или пробел) — та же, что у календаря Bases, см. [[bases-calendar]]. Если `format` задан, значение
сверяется с шаблоном из токенов `YYYY`, `YY`, `MM`, `DD`, `HH`, `mm`, `ss`; остальные символы
считаются литералами.

## Кэш, запись и ошибки

`SchemaStore` в `Core` держит один `SchemaRegistry` на корень vault. Кэш сравнивает `(mtime, size)`
файла: правка снаружи подхватывается без перезапуска, а отсутствие файла — такое же состояние кэша,
как пустая схема.

`save` сначала валидирует схему и только потом пишет: каталог `.obsidium` создаётся при
необходимости, файл пишется временным файлом и переименовывается (`write_file_atomic_impl`).
Невалидная схема не оставляет после себя ни файла, ни полузаписанного JSON. Ошибки чтения и
валидации — `SchemaError` с кодом `io` или `invalid`; паники и «молча пустого» реестра нет.

## Tauri

Команды лежат в `src-tauri/src/schema/commands.rs` и зарегистрированы в `src-tauri/src/lib.rs`:

| Команда | Что делает |
| --- | --- |
| `get_schema(workspacePath)` | читает `schema.json` (или пустую схему) |
| `save_schema(workspacePath, schema)` | валидирует, пишет и возвращает сохранённое |
| `validate_note(workspacePath, path)` | читает заметку по пути и возвращает нарушения |

## Почему файл, а не SQLite

Схема — часть vault, а не состояние приложения. Файл в `.obsidium` копируется вместе с vault,
попадает в git и синхронизацию, его можно открыть и поправить руками, а конфликт двух правок
разрешается как обычный текстовый конфликт.

Запись в SQLite (например, в `documents.sqlite3` в app data) ломает всё это сразу: схема перестаёт
переезжать вместе с vault, её не видно в diff и нельзя отредактировать вне приложения; при потере
или повреждении базы типы исчезают вместе с ней, а два устройства правят одну и ту же схему без
возможности merge. Плюс схема читается редко и стоит копейки — кэша по `(mtime, size)` достаточно,
отдельная таблица с миграциями не даёт ничего.

## Ключевые файлы

- `core/src/schema/model.rs` — модель, `PropertyKind`, встроенный `Note`.
- `core/src/schema/registry.rs` — чтение/запись, кэш, `SchemaStore`.
- `core/src/schema/validate.rs` — валидация файла, наследование, нарушения заметки.
- `core/src/schema/mod.rs` — публичный API и `SchemaError`.
- `src-tauri/src/schema/commands.rs` — Tauri-команды.

## Границы среза

Редактор схемы в интерфейсе и применение `default` к новым заметкам в этот срез не входят. Схема не
индексируется поиском и не участвует в запросах Bases: `type:` по-прежнему обычное поле frontmatter,
см. [[frontmatter-field-index]] и [[dataview-queries]].
