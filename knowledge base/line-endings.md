# Переводы строк: везде LF

Каноническая форма текста в проекте и в базах знаний — LF (`\n`). CRLF (`\r\n`) может прийти
только снаружи: из git с `core.autocrlf=true` на Windows, из внешнего редактора, из чужой базы.
Приложение его не распространяет: читает как LF и пишет LF.

## Связанные документы

- [[document-lifecycle]] — снимок файла: текст, хэш файла и хэш текста.
- [[mcp-and-doc-sync]] — внешние правки и сверка хэшей при записи.
- [[links-and-backlinks]] — смещения ссылок, по которым редактор прыгает к месту ссылки.
- [[mcp-guest-workspace]] — MCP-агент в чужой базе, где CRLF встречается чаще всего.

## Два правила

**Git.** В корне репозитория лежит `.gitattributes`:

```
* text=auto eol=lf
*.bat text eol=crlf
*.cmd text eol=crlf
```

Этот файл сильнее личной настройки `core.autocrlf` на любой машине. Git хранит LF и отдаёт LF в
рабочую папку, поэтому предупреждения «LF will be replaced by CRLF» и дифы из одних переводов строк
исчезают. `text=auto` сам узнаёт бинарники (иконки, картинки) и не трогает их. Пакетным файлам нужен
CRLF: `cmd.exe` с LF путает метки и переходы.

**Приложение.** Весь текст заметки читается одной функцией `files::document::read_text` (или
`read_file_snapshot_impl`, когда нужен ещё и хэш), обе нормализуют через `normalize_line_endings`.
Записывается всегда LF, так что файл с CRLF переезжает на LF при первой же правке.

## Почему именно так

**Два хэша, а не один.** Проверка «файл не изменился под нами» перед записью сравнивает хэш **сырых
байтов** на диске: это единственный честный ответ на вопрос, тот ли это файл. Сравнение с документом
в редакторе идёт по хэшу **нормализованного** текста (`text_hash`). Если бы проверка записи шла по
нормализованному тексту, два файла, отличающиеся только переводами строк, считались бы одним. Если бы
сравнение с редактором шло по сырым байтам, каждый CRLF-файл выглядел бы изменённым снаружи, и
приложение бесконечно подтягивало бы диск.

**Переименование со ссылками.** `wiki/rename.rs` ищет и переписывает ссылки в нормализованном тексте,
а хэш для проверки записи и исходник для отката берёт от сырого файла. Если нормализовать и хэш,
запись упрётся в конфликт: на диске лежат другие байты. Откат после сбоя возвращает файл байт в байт.

**Смещения ссылок в индексе.** Раньше индексатор (`index_document::prepare_file`) читал файл сырым.
В CRLF-заметке смещение ссылки считалось по тексту с `\r`, а редактор живёт в тексте без `\r`. Прыжок
к обратной ссылке промахивался на столько символов, сколько строк было выше ссылки. Поэтому формат
индекса поднят до версии 9: при следующем открытии каждая база один раз перестраивает индекс, и
смещения становятся верными.

**Старые версии индекса удаляются.** Индекс лежит в папке `index-v<версия>` рядом с
`documents.sqlite3`. Раньше при смене версии прежняя папка оставалась на диске навсегда: в
реальной базе лежали `index-v6`, `index-v7` и `index-v8` одновременно. Теперь `open_index` удаляет
все `index-v*`, кроме текущей. Если старую папку держит открытой другая сборка (релиз рядом с dev),
удаление не проходит и пишется в журнал; повторится при следующем открытии.

**Файлы пользователя массово не переписываются.** Приложение не переводит базу на LF само: это была
бы правка сотен файлов, которых пользователь не трогал. У всех поменялась бы дата изменения, в
git-репозитории баз пришёл бы огромный дифф на ровном месте, OneDrive пересинхронизировал бы базу
заново. Нормализация при чтении делает это ненужным.

## Перевод рабочей папки, если CRLF уже там

`.gitattributes` не переписывает то, что уже лежит в рабочей папке. Если файлы были выписаны с CRLF
до его появления, их нужно один раз перевести. В истории от этого не меняется ни одной строки, если
в индексе git уже LF (`git ls-files --eol` показывает `i/lf w/crlf`).

Ловушка при переводе: git кэширует размер файла и после перевода по несовпадению размера помечает
файл изменённым, не сравнивая содержимое. `git diff` при этом пустой. Кэш обновляется через
`git add` именно этих файлов: содержимое совпадает с HEAD, поэтому в стейдже ничего не появляется.
Пути с кириллицей надо брать из `git ls-files -z`: без `-z` git отдаёт их в кавычках с экранированием.

Так переведены Aquilum (222 файла) и zombie voxel (299 файлов, `.gitattributes` там уже был, но
рабочая папка осталась от времени до него).
