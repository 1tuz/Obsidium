# Запросы к базе в блоке ```dataview

Блок ```` ```dataview ```` считается целиком в Rust и отдаёт редактору готовые ячейки. Синтаксис снаружи повторяет DQL из Obsidian, чтобы запросы переносились без переписывания, но внутри устройство своё и заметно проще: у значений закрытый список типов, у функций нет ни лямбд, ни отложенных вычислений, а даты — обычные наносекунды от эпохи, без библиотеки календарей.

Отправная точка — [[frontmatter-field-index]]: исполнять `WHERE type = "book"` было не на чем, пока поля frontmatter не легли в индекс.

## Что умеет

```dataview
TABLE WITHOUT ID
link(file.link, title) AS "Ссылающиеся заметки"
FROM [[📖 5 пороков команды]]
SORT file.ctime DESC
```

| Часть | Формы |
| --- | --- |
| Заголовок | `TABLE [WITHOUT ID] [колонка [AS "имя"], …]`, `LIST [WITHOUT ID] [значение]`, `TASK [WITHOUT ID]` |
| Источник | `FROM "Папка"`, `FROM #тег`, `FROM [[Заметка]]` (кто ссылается), `FROM outgoing([[Заметка]])`, `FROM once` (ни одной заметки, одна пустая строка), и их сочетания через `and`, `or`, `not`, скобки |
| Условия | `WHERE выражение`, `SORT выражение [ASC/DESC], …`, `LIMIT число`, `GROUP BY выражение [AS имя]`, `FLATTEN выражение [AS имя]` |
| Обновление | `EVERY 30s` — блок пересчитывает себя сам с этим шагом (`5 minutes`, `1 hour`) |
| Подпись | `TITLE "Невыполненные задачи"` — название над выдачей, пишется в любом месте запроса |
| Поля файла | `file.link`, `file.path`, `file.name`, `file.folder`, `file.ctime`, `file.mtime`, `file.size`, `file.tags` |
| Поля заметки | любое имя из frontmatter **и из текста** (`Оценка:: 8`), включая кириллические |
| Поля задачи | `text`, `completed`, `line` — только в запросе `TASK` |
| Функции | `link`, `default`, `list`, `length`, `contains`, `containsword`, `choice`, `object`, `typeof` |
| Текст | `lower`, `upper`, `join`, `split`, `replace`, `substring`, `startswith`, `endswith`, `padleft`, `padright`, `truncate` |
| Числа | `number`, `string`, `round`, `floor`, `ceil`, `trunc`, `abs`, `sum`, `product`, `average`, `min`, `max` |
| Списки | `reverse`, `sort`, `unique`, `flat`, `slice`, `firstvalue`, `lastvalue`, `nonnull` |
| Даты | `date("2024-10-07")`, `date(today)`, `now`, `dur(1 week)`, `dateformat(значение, "d MMM")`, `striptime`, арифметика `дата ± длительность` и `дата - дата` |
| Периоды | `day`, `week`, `month`, `season`, `year`, `season_name`, `span(начало, конец)`, а по ним — `bar`, `percent`, `remaining`, `within`, `count`, `previous`, `delta` |
| Стрелочные функции | `filter(список, (x) => …)`, и так же `map`, `any`, `all` |
| Свойства даты | `.year`, `.month`, `.day`, `.weekday` (1 — понедельник) |
| Операторы | `+ - * / %`, `= != < <= > >=`, `and or not` (и `&& || !`), индексы `a[0]`, свойства `a.b` |

## Счёт по периоду

Четыре функции работают не со значением заметки, а с отрезком времени, и вместе дают сводку «сколько сделано за отрезок и больше ли это, чем за прошлый»:

| Функция | Что считает |
| --- | --- |
| `within(дата, период)` | попала ли дата в отрезок; конец отрезка не включается |
| `count(список[, период])` | сколько элементов в списке (1 аргумент) или сколько дат попало в отрезок (2 аргумента); если период `null`, возвращает `null` |
| `previous(период)` | предыдущий отрезок той же длины; для `ever` («за всё время») и пустых отрезков возвращает `null` |
| `delta(стало, было[, прочерк])` | разница со знаком (`+N`, `-N`), при нулевом изменении — `0` (или заданный 3-й аргумент), а при отсутствии базы сравнения (`null`) — прочерк «—» |

```dataview
TABLE WITHOUT ID
    count(file.ctime, week) AS "За неделю",
    delta(count(file.ctime, week), count(file.ctime, previous(week))) AS "Динамика"
FROM #заметки
```

`count` — это `length(filter(…))`, написанное одним словом: счёт по периоду — то, ради чего сводные таблицы пишут. При вызове с одним аргументом `count(список)` функция возвращает общее количество непустых элементов в списке.

`delta` отдаёт текст, а не число: в колонке «динамика» читают направление, и знак важнее значения:
- Рост выводится со знаком плюс (`+N`), спад — со знаком минус (`-N`).
- Нулевое изменение выводится числом `0` (а не голым прочерком `—`, который в числовых колонках путают с минусом). Если автор запроса явно передаёт 3-й аргумент `delta(стало, было, "—")`, ноль будет напечатан этим текстом.
- Для периода за всё время (`ever`) предыстории не существует: `previous(ever)` возвращает `null`, `count(..., previous(ever))` даёт `null`, и `delta(всего, null)` выводит стандартный прочерк `—` (или текст из 3-го аргумента), исключая ложный прирост `+всего`.

## Название над выдачей

`TITLE "Невыполненные задачи"` рисует подпись шапкой таблицы: текст и разделитель под ним. У `TASK` и `LIST` колонок нет вовсе, поэтому назвать выдачу через `AS` было нечем — `AS` именует колонку, а не запрос.

**`TITLE` не стало ключевым словом.** Поле `title` во frontmatter — одно из самых частых, и попади это слово в `KEYWORDS`, запрос `TABLE title` перестал бы читать поле и вернул бы ошибку. Частью запроса слово делает только идущая следом строка в кавычках: `at_title` смотрит на два токена сразу. Ничего другого `TITLE "…"` значить не может, поэтому разбор однозначен, а старые запросы не меняют смысла.

## Поля прямо в тексте

Поле заметки пишется не только в шапке. Строка `Оценка:: 8` где угодно в тексте — такое же поле, как `Оценка: 8` во frontmatter, и попадает в тот же индекс. Форм две, обе из dataview: строка целиком (в том числе внутри пункта списка или цитаты) и вставка в скобках посреди предложения — `Прочитал за вечер [Оценка:: 9], понравилось`.

**Шапка важнее текста.** При совпадении ключа побеждает frontmatter: иначе строка в середине заметки молча переопределяла бы то, что автор написал в шапке.

**Двойное двоеточие — ещё не поле.** `note_date::parse` в тексте полем не становится: после разделителя обязателен пробел или конец строки. Плюс не читаются блоки кода и код в обратных кавычках целиком, а ключ ограничен 64 символами — иначе обычное предложение с «::» превратилось бы в поле с ключом на пол-абзаца.

Разбор живёт в `fields/inline.rs` и работает **только на индексацию**: `note_fields` по-прежнему возвращает чистый frontmatter, потому что MCP-инструменты правят именно шапку и не должны видеть в ней строки из текста.

## Задачи

```dataview
TASK WHERE !completed and contains(text, "позвонить")
```

`TASK` меняет само понятие строки: это не заметка, а чекбокс в ней. Поэтому условия применяются к задачам — `WHERE !completed` отсеивает выполненные задачи, а не заметки, где нет невыполненных. Задача знает свой `text`, `completed`, `line` и всю свою заметку через `file.*`.

Чекбоксы лежат в своей таблице `note_tasks` и пишутся тем же проходом индексации, что поля и ссылки (`tasks/`). Дочитываются они **только для формы `TASK`** — остальным запросам они не нужны, а лишний запрос к базе на каждую заметку стоил бы дороже самой выборки.

Сделанной задача считается по любому непробельному знаку в скобках: Obsidian ставит туда и `x`, и `/`, и `-`, и все они значат «не открыта». Чекбокс в блоке кода задачей не считается — это пример разметки, а не дело.

**Чекбокс в выдаче нажимается.** Щелчок переключает задачу в самой заметке (`toggleTaskInFile`), номер строки для этого и едет в ячейке. Два пути, вызовы по одному файлу идут друг за другом через `PathQueue`:

- **Заметка открыта и у неё уже есть writer.** Знак меняется в `Y.Doc` минимальным диффом (`DIRECT_WRITE_ORIGIN`, обычное отложенное сохранение не планируется), а на диск пишет writer методом `writeCurrent`: текст читается из `Y.Doc` в момент, когда запись дошла до очереди writer'а, а не заранее. Раньше на диск писался `next`, посчитанный до ожидания `writer.idle()`; если пока шла предыдущая запись пользователь печатал и его сохранение вставало в очередь раньше, файл перезаписывался текстом без этих символов и оставался устаревшим до следующей правки — MCP и внешние редакторы видели старый текст. Тест `writes what the document holds when the write runs, not when the toggle started`.
- **Заметка закрыта или writer ещё не подключён** (документ только открывается). Файл читается, знак меняется, запись атомарная с проверкой хэша; открытый документ подхватит правку как внешнюю. Раньше при открытом документе без writer правка попадала только в `Y.Doc`, а на диск — никогда.

**Ссылкой служит сам текст задачи.** Название заметки рядом с делом отъедало половину ширины строки, а иконка в конце строки читалась как отдельная кнопка, которой она не является. Поэтому ячейка задачи — чекбокс плюс **ссылка с текстом самого дела**, ведущая в заметку, где это дело записано. Особой разметки для этого не нужно: ссылка в ячейке обычная, такая же, как в любой таблице.

Само переключение — общая функция `modules/documents/taskCheckbox`: она же отвечает за чекбоксы в тексте заметки (см. [[editor-outline]]), поэтому «что считать задачей» и «что значит закрыта» описано в одном месте. Пункт списка она не разбирает сама, а берёт у `matchOutlineItem` из `outline/constructs.ts`: задача — это `[ ]` сразу после префикса `- `, `N. ` или `N) `. Звёздочка и плюс списком в Aquilum не являются, значит и задачи там нет. Разбор задач в индексе (`search/tasks/parse.rs`) обязан принимать ровно тот же набор префиксов: если индекс найдёт задачу, которую фронтенд не признаёт, щелчок по её чекбоксу в выдаче ничего не переключит.

В Rust правило живёт в одной функции `list_item_body` (`search/markdown.rs`, рядом с `lines_outside_fences` — общим пропуском блоков кода): `- `, `N. `, `N) `, и больше ничего. Ею пользуются и задачи (`search/tasks/parse.rs`), и инлайн-поля (`search/fields/inline.rs`), которые снимают маркер пункта и чекбокс перед `Ключ:: значение`. До 2026-10-06 индекс принимал `* [ ]` и `+ [ ]` и не принимал `1) [ ]` — ровно расхождение, которое ломало щелчок. Тесты: `a_task_follows_the_list_markers_of_the_editor`, `only_dash_and_numbered_markers_start_a_list_item`, `a_field_in_a_task_or_a_bracket_numbered_item_is_read_and_a_star_is_not_a_marker`.

`FROM #тег` смотрит **теги из frontmatter**, а не решётки в тексте заметки: в индексе лежат только первые. Вложенный тег находится по родителю — `#книги` даёт и `книги/фантастика`.

Элементы списка `tags` лежат в `note_fields` JSON-массивом, поэтому совпадение тега проверяет Rust после разбора массива, а SQL лишь сужает выборку до заметок, у которых поле `tags` вообще заполнено. Сравнение внутри SQL пришлось бы делать по тексту JSON, и `#книги` совпадало бы с `книгиX` или не находило бы `книги/фантастика`.

## Таблица, которая не о заметках

Запрос умеет считать и то, что к базе отношения не имеет, — например, сколько прошло от периода:

```dataview
TABLE WITHOUT ID
    item.name AS "Период", bar(item.span) AS "Прогресс",
    percent(item.span) + "%" AS "Процент", remaining(item.span) AS "Осталось"
FROM once
FLATTEN date("2001-05-17") AS birth
FLATTEN list(
    object("name", "День", "span", day),
    object("name", season_name, "span", season),
    object("name", "Жизнь", "span", span(birth, birth + dur(80 years)))
) AS item
```

Держится это на трёх вещах, и ни одна из них не является отдельным механизмом: `FROM once` даёт ровно одну пустую строку, `FLATTEN list(object(…))` разворачивает её в нужное число строк, а период — обычный объект с полями `start` и `end`, который умеет построить и `span(…)`, и встроенные имена `day`/`week`/`month`/`season`/`year`.

**Полоса — часть ячейки, а не разметка.** `bar(…)` возвращает долю, а виджет рисует её двумя блоками с шириной в процентах. HTML из запроса не исполняется нигде и никогда: иначе блок в общей заметке стал бы способом протащить чужую разметку в приложение — а заметки в проекте вскоре станут общими.

**Встроенные имена проверяются после полей заметки.** Поле `year` во frontmatter важнее встроенного периода `year`, иначе добавление имени в язык молча ломало бы чужие запросы.

## Три сознательных отличия от dataview

**Условия применяются в том порядке, в каком написаны.** `LIMIT 10 SORT rating DESC` действительно обрежет до сортировки и вернёт десять случайных заметок, а не десять лучших. Это выглядит строже, зато запрос читается сверху вниз и не требует помнить приоритет частей.

**Пустое значение всегда внизу, при любом направлении сортировки.** `SORT rating DESC` не начинается с заметок, где оценки нет вовсе, — иначе полезная часть выдачи оказывалась бы под экраном. В dataview пустое считается наименьшим и при `DESC` всплывает наверх.

**Группы идут в порядке первого появления ключа.** `GROUP BY` не сортирует — по тому же правилу, что и остальные части: что написано раньше, то раньше и считается. Нужен другой порядок — ставьте `SORT` после группировки.

**Время считается по часам того, кто смотрит.** Внутри всё хранится моментом в UTC — так лежат `ctime` и `mtime` в индексе, — а гражданский вид (какое сегодня число, когда началась неделя, сколько осталось до конца дня) считается со сдвигом часового пояса. Сдвиг приходит от системы вместе с каждым запросом (`-new Date().getTimezoneOffset()`), отдельной настройки нет и быть не должно: пояс знает система, и переход на летнее время она учитывает сама.

Без этого «Осталось» в блоке периодов показывало остаток до полуночи по Гринвичу: в восемь утра по UTC+7 выходило 23 часа вместо шестнадцати. Сдвиг применяется в одном месте — в `note_date`, при переводе момента в гражданский вид и обратно, — поэтому его видят и периоды, и `dateformat`, и разбор дат из frontmatter.

**Текст, который читается как дата, становится датой.** Поле `created: 07.10.2024` сравнивается с `created: 2024-11-01` как даты, а не как строки, потому что индекс уже знает тип поля, а `note_date::parse` понимает оба порядка. Без этого `SORT created DESC` давал бы бессмыслицу на реальной базе.

## Как это устроено

```text
текст блока
  -> lexer.rs      плоский список лексем, границы в исходном тексте
  -> parser/       выражения по приоритетам + разбор частей запроса -> Query
  -> source.rs     Source -> множество путей (SQL по wiki_links, note_fields, documents)
  -> rows.rs       пути -> Row: поля файла из documents, frontmatter из note_fields
  -> eval.rs       Expr + Scope -> Value
  -> execute.rs    WHERE/SORT/LIMIT/GROUP BY/FLATTEN, затем Value -> ячейки
  -> duration.rs   длительности из dur(...) и календарный сдвиг даты
  -> dateformat.rs шаблон Luxon -> подпись даты по-русски
```

Встроенные функции лежат в `functions/`, по модулю на род значения: `text.rs`, `numbers.rs`, `lists.rs`, `dates.rs`, `periods.rs` и `values.rs` — ссылки, `default`, `choice`, `object`, `typeof`. В `functions/mod.rs` остаётся только таблица имён: по ней видно весь язык разом, и именно она отвечает на вопрос «а такая функция есть?» текстом ошибки.

**Синонимов в языке нет.** `array` убран в пользу `list`, `icontains` — в пользу `contains` (тот и так не различает регистр), `if`, `avg` и `duration` — в пользу `choice`, `average` и `dur`, а `ascending`/`descending` — в пользу `asc`/`desc`. Два имени у одного действия заставляют пользователя гадать, чем они отличаются, а разница была только в написании. Литерал списка `[a, b]` разбирается в вызов `list`, поэтому у квадратных скобок и функции по-прежнему один механизм.

**Строка выдачи шире, чем заметка.** До `GROUP BY` строка — это заметка; после — группа, у которой заметки нет вовсе, зато есть ключ и список `rows`. Поэтому `execute.rs` считает не `Row`, а `Entry`: необязательная заметка под `Rc` плюс имена, выданные `GROUP BY` и `FLATTEN`. `Rc` здесь не про экономию памяти вообще, а про `FLATTEN`: он размножает строку на каждый элемент списка, и копировать вместе с ней весь frontmatter было бы бессмысленно.

**Элемент `rows` — заметка, ставшая значением.** Поля файла лежат в нём под `file`, поэтому `rows.file.ctime` разбирается тем же путём, что и `file.ctime` у обычной строки. Свойство списка берётся у каждого элемента — это и превращает такую запись в столбец дат.

**Стрелочная функция вычисляется в `eval.rs`, а не в `functions.rs`.** Только у вычислителя есть область видимости, в которой параметру можно дать значение. Область — цепочка ссылок `Local`, а не словарь: вложенность мелкая, а копировать словарь на каждый элемент списка дороже самого вычисления. Значением лямбда не бывает — её принимают ровно `filter`, `map`, `any` и `all`, и попытка написать её где-то ещё объясняет это словами.

**`and` и `or` не считают правую часть без надобности.** Если левая часть уже решила результат, правая не вычисляется. Это не только про скорость: правая часть может быть дорогой или вовсе ошибочной на этой строке, например обращаться к полю, которого у заметки нет, и короткое замыкание позволяет защитить её условием слева. Ключи сортировки по той же логике цены считаются один раз на строку до сортировки, а не внутри сравнения: сравнение вызывается O(n log n) раз, и пересчёт выражения в каждом вызове стоил бы дороже самой сортировки.

**Календарь свой, библиотеки дат в проекте нет.** Месяцы и годы в длительности хранятся отдельно от наносекунд, потому что они календарные: «плюс месяц» от 31 января — это 28 февраля. Сравниваются длительности по приближению (средний месяц), а складываются с датой — точно, через `note_date`.

**Закрытый список типов и короткий список функций — одно решение.** У значения запроса фиксированный набор типов, а встроенных функций сознательно немного: каждая функция обязана вести себя понятно на значении любого типа, и каждый новый тип или новая функция добавляет правило, которое приходится держать в голове всем остальным. Отсюда и устройство сравнения. Равенство сравнивает числа с числами, а всё прочее — по строковому виду, поэтому `status = "read"` срабатывает независимо от того, каким типом это значение оказалось в индексе. Порядок между разными типами при сортировке закреплён: иначе результат зависел бы от того, какая строка попалась первой. Целое число печатается без дробной части, чтобы `rating: 5` осталось в таблице пятёркой, а не `5.0`. Поля `object(...)` хранятся в порядке перечисления, и таблица печатает их в том же порядке.

**Разбор запроса.** Переводы строк для лексера значения не имеют: границы частей запроса задают ключевые слова, поэтому запрос пишется и в одну строку, и в несколько. Из этого следует правило для выражений: слово, с которого начинается часть запроса, обязано выражение закончить. Иначе `TABLE FROM "Книги"` прочиталось бы как колонка с именем `FROM`. Забытая запятая между колонками выглядит ровно так: список колонок кончился, а текст остался. Поэтому парсер говорит об этом прямо, а не молча обрезает запрос. Сравнение неассоциативно: `a < b < c` — это описка, а не выражение, и парсер о ней сообщает. Стрелочная функция разбирается пробно: круглая скобка чаще открывает обычное выражение, а лямбду выдаёт только стрелка после закрывающей скобки, поэтому при первом несовпадении курсор возвращается на отметку. Аргумент `dur(…)` берётся исходным текстом между скобками, а не выражением: иначе `week` в `dur(1 week)` пришлось бы объявлять именем языка. `LIMIT` принимает только число: вычисляемый предел никому не нужен, а ошибку в нём не видно. `GROUP BY` и `FLATTEN` называют своё значение так же, как колонка: по `AS`, а без него — собственным исходным текстом.

Модуль лежит в `src-tauri/src/search/dataview/` — рядом с `fields/`, `graph/` и `wiki/`, потому что он надстройка над тем же индексом и пользуется их данными, а не своими.

**Ссылки остаются ссылками до самого DOM.** Ячейка — это последовательность частей `text` и `link`, а не готовая строка. Иначе `link(file.link, title)` пришлось бы отдавать разметкой и разбирать её обратно на фронтенде, а щёлкать было бы не по чему.

**Границы лексем нужны для заголовков.** Колонка без `AS` называется своим же исходным текстом (`file.ctime`, `rating * 2`), поэтому каждая лексема помнит своё место в запросе, и заголовок берётся срезом исходной строки.

**Функции вызываются только по имени.** `expr(...)` в языке нет: конструкция никому не нужна, а без неё разбор постфиксов проще и ошибки понятнее.

**Вычислитель не знает о базе.** `eval.rs` получает готовую `Row` и ничего не читает сам. Поэтому весь язык проверяется юнит-тестами на сочинённых строках, без SQLite: сквозные тесты в `dataview/tests.rs` прогоняют текст запроса до ячеек.

**Текстовые функции считают символы, а не байты.** Границы `substring` и длина в `truncate` меряются в символах: срез по байтам рвал бы кириллическую букву пополам. Многоточие у обрезанного `truncate` текста входит в заданную длину, поэтому колонка не становится шире заказанного. `containsword` ищет слово целиком, а не подстроку: «мысль» найдётся в «мысль дня», но не в «замысел». `flat` раскрывает ровно один уровень вложенности: список списков становится списком значений. `TABLE` без единой колонки показывает только колонку заметок, потому что больше показывать нечего. `FROM ""` (пустой путь папки) означает всю базу.

## Отрисовка блока

Виджет живёт в `extensions/dataview/` и следует тому же правилу, что книжные строки ([[book-widget-sync]]): **блок появляется сразу с таблицей, а не достраивается.** Результат считается заранее, складывается в хранилище и только потом эффектом `dataviewDataReady` пересобирает декорации. Пока результата нет, на месте блока стоит заготовка фиксированной высоты.

Считают его два места, и это не дублирование, а разные моменты жизни заметки.

**Прогрев `run.ts` — до создания редактора.** Префетчер живёт в `ViewPlugin`, поэтому его конструктор запускается только когда CodeMirror уже построен: при холодном открытии блок неизбежно достраивался после первого кадра. Прогрев уходит раньше — сразу после того, как файл прочитан с диска, прямо по сырому тексту заметки. По замерам это около шестидесяти миллисекунд форы до монтажа, чего хватает на круг IPC.

Текст на этом этапе разбирает `dataviewQueriesInText`, а не обход дерева: синтаксического дерева до создания состояния ещё не существует. Это отдельный вопрос — «какие запросы есть в тексте», — а не второй способ находить блоки: позиции для декораций по-прежнему берутся только из дерева. Чтобы два пути не разошлись молча, тест сверяет их результаты на восьми формах блока.

**Префетчер `prefetch.ts` — пока редактор живёт.** Он пересчитывает запросы на правку документа и на новую ревизию индекса. Исполнение у обоих общее: `evaluateDataviewQuery` держит карту запросов в полёте, поэтому прогрев и префетчер, спросив одно и то же, ждут один промис вместо двух кругов IPC.

**Результаты переживают переход между заметками.** Чистка хранилища ограничена запросами текущей заметки, поэтому возврат на вкладку рисует таблицу из кеша в первом же кадре, а не считает заново.

Хранилище разложено по заметкам, и вытесняется заметка целиком — восемь последних по обращению. Плоский список из 64 результатов с вытеснением самого старого этого не умел: `Map.set` по уже существующему ключу не меняет порядок вставки, поэтому часы, переписывающие свой результат каждую секунду, так и оставались самой старой записью и вылетали первыми — прямо из открытой заметки. Блок после этого рисовался заготовкой в 96 пикселей, а его таймер не находил шага и больше не взводился. Открытая заметка теперь последняя в порядке обращения по построению, а не по удаче.

**Блок, зависящий от времени, обновляется сам.** Ничего писать для этого не нужно: если при счёте запрос спросил текущий момент — через `now`, `today` или период вроде `day`, — выдача стареет сама по себе, и блок заводит пересчёт. Признак берётся с самих часов: вычислитель отмечает обращение к ним, поэтому список «временных» функций нигде не дублируется и не разъедется с кодом.

**Отметка об обращении к часам принадлежит потоку, а не процессу.** Команда уходит в `spawn_blocking`, то есть два блока считаются одновременно на разных потоках пула. Пока отметка была `static AtomicBool`, запрос, финишировавший первым, забирал чужую: блок с `now` получал пустой шаг и вставал насовсем — до перезагрузки страницы, — а соседняя сводка наоборот получала лишний пересчёт раз в минуту. Встреча при этом не случайна, а регулярна: блок с шагом в секунду и блок с шагом в минуту стреляют в одну и ту же миллисекунду каждую минуту. Тот же общий флаг делал нестабильным и тест `a_block_that_asks_the_clock_keeps_itself_fresh_without_every`, потому что `cargo test` гоняет тесты параллельно. Внутри запроса потоков нет, поэтому `thread_local!` — ровно та область жизни, которая нужна, и никакой синхронизации она не требует.

Шаг у такого блока два: **секунда**, если запрос считает своё и в базу не ходит (`FROM once` — часы, прогресс периодов), и **минута**, когда за каждой строкой стоит обход базы. Разница не в важности, а в цене пересчёта.

**`EVERY 30s` задаёт шаг вручную и отменяет автоматический.** Пишут его, когда нужно реже — например, блок с `now` в заметке, открытой весь день. Слово становится частью запроса только когда следом идёт число: поле `every` у заметки от этого не страдает, как и `title`.

Шаг `EVERY` не бывает меньше секунды (`MIN_REFRESH_SECONDS`): за каждым пересчётом стоит запрос в базу, а разницу между пересчётом раз в секунду и чаще глазом всё равно не поймать.

**Тик у каждого блока свой.** Часы с шагом в секунду и сводка по базе с шагом в минуту живут в одной заметке, не мешая друг другу: таймер заводится на запрос, а не на документ. Общий шаг на всю заметку заставлял бы самый частый блок тянуть за собой самый тяжёлый.

**Взведённый таймер переживает прогоны префетчера.** Шаг — свойство самого запроса, поэтому префетчер его не переназначает: он заводит таймеры новым блокам и гасит те, чьих блоков в заметке больше нет. Прежняя редакция гасила и взводила заново всё сразу на каждом прогоне, то есть на каждой правке текста, и часы, пока в заметке печатают, не шли вовсе. Хуже того, список блоков брался из лениво разобранного дерева без проверки `syntaxTreeAvailable`: блок ниже границы разбора в список не попадал, и его таймер гасился навсегда. Теперь чистка таймеров стоит под той же проверкой полного дерева, что и чистка хранилища.

Прежде рядом с таймером помнился и сам шаг — на случай разовой неудачи запроса: результат со статусом `failed` шага не несёт, и без памяти о прежнем цепочка тиков обрывалась на первой же ошибке. Эта подпорка убрана вместе с причиной. Запрос больше не падает от того, что индекс не открыт (ниже), поэтому `failed` теперь означает настоящую ошибку — разбор запроса, которому нечего ждать. Гасить тики такого блока правильно: он не починится сам, сколько его ни пересчитывай.

Заводила прогонов у блока запроса **общий с книжной строкой** — `extensions/prefetchScheduler.ts`. Подписка на ревизию индекса с фильтром по рабочей папке, дебаунс, очередь прогонов и уборка в `destroy` у обоих совпадали дословно, и пока это было написано дважды, копии успели разойтись: гонку прогонов починили только в одной из них. Своё каждый оставил себе — блок запроса таймеры пересчёта, книжная строка прогрев обложек ([[book-widget-sync]]).

Первый прогон тоже принадлежит заводиле и делается после того, как подписка на ревизию встала. Надёжность здесь даёт порядок, а не проверка: ревизию, пришедшую до подписки, терять не страшно, потому что прогон после неё всё равно читает текущее состояние. Раньше первый прогон заводил каждый вызывающий сам, прямо в конструкторе, и между ним и подпиской оставалась щель.

Сами прогоны выстроены в очередь одним промисом, а не тремя флагами «идёт», «устарело», «устарело по ревизии». Пачка событий ревизии больше не разворачивается в несколько одновременных обходов, а повторной работы это не добавляет: `evaluateDataviewQuery` и так держит один запрос в полёте на пару «заметка и запрос».

**Готовности индекса ждать больше не нужно.** Блок, спросивший базу до того, как индекс открылся, получал «Index is not ready». Сначала это чинили событием: открытие индекса шлёт ту же ревизию, что и обычные изменения, и слушатели пересчитываются. Подпорка оказалась ненадёжной — при открытии ревизия приходит ровно один раз, а подписка на события оформляется асинхронно, и это единственное событие можно не застать. Тогда ошибка оставалась на экране навсегда: правки документа блок не пересчитывали, потому что неудача лежала в кэше как готовый ответ, а тик ему не заводился, потому что шага у неудачи нет.

Теперь причина убрана в Rust. `active_paths` сам открывает индекс, если тот ещё не открыт: `prepare` идемпотентен и для уже открытой базы выходит на первой же проверке. Любая надстройка над индексом — запросы, обратные ссылки, поля frontmatter, подсказки ссылок — получает его готовым вместо ошибки. «Index is not ready» из этой дороги исчез совсем, а проверка на чужую рабочую папку перестала быть отдельной веткой и слилась с разбором `Option`.

**Запрос `FROM once` до индекса вообще не доходит.** Он считает себя по часам, и ни корень базы, ни соединение с SQLite ему не нужны. Раньше `run_dataview_query` брал и то и другое до того, как посмотреть на источник запроса, — поэтому таймер на домашней странице зависел от индекса, который ему не требовался, а каждый его тик, то есть раз в секунду, открывал соединение с базой впустую. Теперь строки заметок грузит отдельный `note_rows`, и зовётся он только для запросов по базе. Регрессия на это — `a_query_from_once_is_answered_without_an_index`: служба без единого открытого индекса считает такой запрос и отдаёт ответ.

Пересчёт идёт на правку документа (с задержкой 250 мс — правки внутри запроса набираются посимвольно) и на новую ревизию индекса — **эта без задержки**: ревизия уже пришла пачкой, дебаунсить её второй раз значит просто добавить четверть секунды к ожиданию. Разные поводы — разные задержки.

**Щелчок по чекбоксу задачи откликается мгновенно (0 мс) и оптимистично.** Вся цепочка конвейера (запись на диск, индексация в SQLite/Tantivy на бэкенде, отправка события `LINKS_CHANGED_EVENT` и пересчёт запроса) занимает от 100 до 300 мс. Чтобы исключить даже минимальную задержку:
- Виджет `DataviewWidget` в момент щелчка мгновенно меняет класс чекбокса (`q-task-check--done`) в DOM.
- `toggleCachedDataviewTask` синхронно обновляет кэш `store.ts`: если запрос фильтрует невыполненные задачи (`WHERE !completed` или `completed = false`), выполненная задача сразу удаляется из строк выдачи, а счетчики `total` и `truncated` пересчитываются. Если фильтра по завершённости нет, у задачи меняется статус `done`.
- Обновляется подпись результата `signature` и немедленно отправляется эффект `dataviewDataReady`, пересобирающий декорации в том же тике событий без ожидания ответа бэкенда.
- В фоне `toggleTaskInFile` применяет изменение: если заметка уже открыта в редакторе (`getOpenDoc`), правка вносится напрямую в `Y.Doc` через `applyDocumentText(..., DIRECT_WRITE_ORIGIN)` и сбрасывается писателем `writer.write(..., EDIT_WRITE)`. Если закрыта — атомарно на диск. Серия быстрых кликов по одной заметке сериализуется общей очередью путей `PathQueue` (`modules/pathQueue.ts`, ключ — `comparablePath`), исключая конфликты хэшей.
- Приходящее следом событие `LINKS_CHANGED_EVENT` фильтруется строго через `samePath` (сравнение `event.payload.workspacePath` в каноническом виде ОС исключает потерю событий из-за различий в слэшах `/` и `\`) и обновляет блоки данными из SQLite, подтверждая оптимистичный результат без мигания и повторных отрисовок.

**Подпись принадлежит запросу, а не приложению.** `WidgetType.eq` решает, оставить ли CodeMirror прежний DOM блока. Сравнивать там общий на приложение счётчик поколений нельзя: часы с шагом в секунду меняли его каждую секунду, и неравными разом становились **все** блоки заметки. CodeMirror сносил и строил заново DOM каждой таблички, а вместе с ним заново мерил её высоту в `HeightMap`; во время прокрутки такой перемер двигает содержимое над окном просмотра, и страница дёргается. Поэтому виджет запоминает подпись своей собственной выдачи: тик часов меняет подпись часов и ничью больше.

По той же причине из виджета убрана позиция блока. Раньше она входила в сравнение, и набранный выше символ сдвигал `from` у всех блоков ниже — снова полный пересбор DOM на каждое нажатие клавиши. Позиция для каретки берётся теперь в момент щелчка, через `view.posAtDOM(root)`: для блочного виджета это начало заменённого диапазона, и устареть ей негде.

### Высота блока называется заранее

`WidgetType.estimatedHeight` — то, чем блочный виджет сообщает CodeMirror свою высоту **до** отрисовки. Пока его у блока запроса не было, карта высот держала оценку по числу строк самого запроса — 32 пикселя на трёхстрочный запрос, — а настоящая табличка занимала от двухсот до трёхсот сорока пяти. Замер в живом приложении на домашней странице дал на пяти блоках такую последовательность: `14 → 96 → 32 → 104 / 345 / 224 / 264 / 207`. Каждый въезд таблички в окно просмотра давал поправку в 175–313 пикселей, и всё содержимое под ней скачком уезжало. Это и были рывки прокрутки, которые шесть раз искали не там.

Хуже того, блок с часами скакал `104 ↔ 32` дважды в секунду **при полном покое страницы**: его выдача честно новая каждую секунду, виджет законно пересоздаётся, и карта высот на один кадр откатывалась к оценке. Страница дёргалась на 72 пикселя, даже когда её никто не трогал. Подпись результата этот случай не закрывает и закрывать не должна — данные у часов действительно другие.

Поэтому виджет помнит измеренную высоту и называет её. Существенны три вещи:

- **Геттер, а не метод.** CM6 кладёт значение прямо в карту высот, а функция роняет `HeightLeaf.lineInner`. То же правило записано у виджета таблицы.
- **Память о высоте переживает смену выдачи.** Она лежит рядом с результатом, но `rememberDataviewResult` её не трогает: у тикающего блока содержимое новое каждую секунду, а размер тот же. Сбрасывать её вместе с результатом значило бы вернуть ровно ту поправку, ради которой всё и делалось.
- **Заготовка встаёт в ту же высоту.** Пока результата нет, блок рисуется карточкой `--pending`, и её `min-height` берётся из запомненной высоты, а не из жёстких 96 пикселей. Иначе виджет называл бы карте 345, а рисовал 96 — прыжок просто сменил бы знак.

Высота живёт в памяти сессии и вытесняется вместе с заметкой. При первом открытии заметки её ещё никто не мерил, поэтому одна установочная поправка на блок неизбежна: данных до первой отрисовки просто нет.

Три блочных виджета редактора объявляют `estimatedHeight`, но считают высоту принципиально по-разному — картинка по соотношению сторон, таблица по модели строк, запрос по разу измеренному DOM. Общее у них только правило «геттер и слегка с запасом»; сводить разные расчёты в одну функцию смысла нет, и это не тот дубль, который надо убирать.

### Дерево при монтаже разобрано не до конца

Парсер markdown успевает разобрать около трёх килобайт к моменту создания состояния: на заметке в 6335 символов дерево обрывается на 3027, и блок ниже этой границы не находит **ни** префетчер, **ни** сборщик декораций. Дерево дорастает в фоне, но раньше на это никто не реагировал, и блок оставался пустой рамкой до первой правки текста — при каретке внутри блока не оставалось даже рамки.

Поэтому и префетчер, и `livePreviewWidgetField` реагируют на `treeChanged` — тем же сравнением `syntaxTree(state) !== syntaxTree(startState)`, что `codeBlock`, `links/flow` и `livePreviewPlugin` (см. [[editor-viewport-decorations]]). По той же причине чистка хранилища ждёт полного дерева: иначе она стирала результаты блоков, которые ещё не найдены.

Следствие для чтения замеров: метка `запросы dataview` в следе открытия означает **конец последнего прохода префетчера**, а не момент появления блока. На длинной заметке дерево дорастает несколькими порциями, каждая планирует проход с задержкой 250 мс, и метка уезжает на несколько сотен миллисекунд, хотя таблица уже нарисована из прогрева.

Ошибка запроса рисуется в самом блоке текстом, а не всплывашкой: сообщения парсера на русском и говорят, что ожидалось вместо найденного («Ожидается закрывающая «)», а не «FROM»»). Ошибка вычисления делает то же: `file.автор` отвечает списком полей, которые у файла есть.

Щелчок по ссылке в ячейке открывает заметку, щелчок мимо ставит каретку в начало блока — иначе запрос нельзя было бы править.

**Вертикальный отступ блока — padding на корне виджета, никогда margin.** Это тот же инвариант, что у таблицы ([[editor-table-layout]]): HeightMap CodeMirror меряет border-box без margin, поэтому внешний отступ сдвигает строки под блоком относительно их зон попадания — каретка ставится не туда, куда целишься, а пустая строка между двумя блоками перестаёт нажиматься. Поэтому корень `.q-md-dataview` несёт только `paddingBlock`, а рамка, фон и внутренние поля живут на вложенной карточке `.q-md-dataview-card`.

Фон, обводка, скругление и поля карточки — общие токены блоков `--q-block-*`, те же, что у блока кода и виджета книги ([[design-tokens]]). Ошибка запроса красится `--q-text-danger`. Раньше там стоял несуществующий `--q-danger` с хардкодом-фолбэком, и цвет брался из литерала мимо темы. Геометрия (`--q-block-padding`, `--q-block-radius`) общая с блоком кода, а внешний отступ — тем же, что у виджета таблицы (`--q-space-12`). Одинаковая геометрия нужна не ради вида: когда блоки стоят подряд, промежуток между ними везде одной высоты, и целиться в него не приходится.

**Шрифт задаётся один раз — на карточке, шрифтом редактора.** Таблица, список, задачи и сообщения его наследуют, своих размеров не задаёт никто: раньше каждый из них называл свой токен, и сообщение «Запрос ничего не нашёл» оказывалось вдвое мельче текста заметки. Единственное исключение — галочка задачи, и она задана в `em`, то есть тоже следует за шрифтом заметки.

### Обратный отсчёт секунд и завершение «конец»

Длительности меньше одной минуты (`duration.rs`) не замирают на статической надписи «меньше минуты»:
- В диапазоне от 59 до 1 секунды отображается обратный отсчёт (`59 сек.`, `58 сек.`, ..., `1 сек.`).
- Когда до конца остаётся менее одной секунды (> 0 наносекунд), отображается `0 сек.`.
- При наступлении окончания отрезка (ноль наносекунд) выводится максимально компактная надпись `конец`, которая не растягивает ячейку таблицы.
- Блоки `FROM once` пересчитываются каждую секунду (`OWN_SECONDS = 1`), благодаря чему отсчёт тикает непрерывно.

### Быстродействие и индексный отбор (TD-15)

Запросы не сканируют всю базу документов при наличии фильтров:
- **Изолированные источники:** `Source::Tag`, `LinksTo`, `LinksFrom` и их комбинации через `AND` в `source.rs` больше не вызывают полный `all_paths` из таблицы `documents`, а обращаются напрямую к профильным индексам и связям.
- **Отбор задач:** в запросах `TASK` кандидаты заметок сужаются до выгрузки строк через индекс `note_tasks_open` (`WHERE done = 0` при `!completed`, `WHERE done = 1` при `completed` или `note_tasks` вообще). Заметки без задач отсекаются за доли миллисекунды.
- **Отбор по полям frontmatter:** условия равенства `WHERE key = "value"` отбирают подходящие пути заметок через `fields::candidates` по индексу `(key_lower, text_lower)` до вызова `rows::load`.
- **Параллельный опрос в UI:** `warmDataviewResults` и `refreshBlocks` выполняют запросы через `Promise.all`, исключая последовательные задержки IPC.

### Константы модуля вынесены в отдельные файлы

Все настраиваемые параметры, селекторы, тайминги и строковые литералы вынесены из кода логики в профильные файлы констант:

**Фронтенд (`extensions/dataview/constants.ts`):**
- `DATAVIEW_LANGUAGE = 'dataview'` — идентификатор языка кодового блока.
- `MAX_CACHED_NOTES = 8` — размер LRU-кэша разобранных блоков для соседних заметок.
- `UNKNOWN_HEIGHT = -1` — маркер блока до первого замера в DOM.
- `PENDING_HEIGHT = '96px'` — минимальная высота карточки во время первого ожидания.
- `DEFAULT_DASH = '—'`, `DEFAULT_ZERO_DELTA = '0'` — значения по умолчанию для динамики и отсутствующих данных.
- `DATAVIEW_PREFETCH_DELAYS` — задержки пересчета: 250 мс на посимвольный ввод, 0 мс на ревизию индекса.
- `DATAVIEW_CLASSES` — словарь CSS-классов DOM-структуры (`root`, `card`, `pending`, `failed`, `title`, `table`, `tasks`, `list`, `link`, `cellBar`, `bar`, `barFill`, `message`).
- `DATAVIEW_SELECTORS` — селекторы элементов карточки (`card`).
- `DATAVIEW_MESSAGES` — системные сообщения виджета (`empty`, `truncated`).

**Бэкенд (`search/dataview/constants.rs`):**
- `NANOS_PER_*` — шкалы наносекунд (`NANOS_PER_SECOND`, `NANOS_PER_MINUTE`, `NANOS_PER_HOUR`, `NANOS_PER_DAY`, `NANOS_PER_MONTH`, `NANOS_PER_YEAR`).
- `DURATION_FINISHED = "конец"`, `DURATION_ZERO_SECONDS = "0 сек."`, `DURATION_UNITS` — склонения единиц длительности.
- `OWN_SECONDS = 1`, `OVER_NOTES_SECONDS = 60` — интервалы автоматического пересчета.
- `MAX_OUTPUT_ROWS = 500` — предельный размер выдачи.
- `CHUNK_PATHS = 400` — размер пачки параметров `IN (?)` для SQLite.
- `NOTE_COLUMN = "Заметка"`, `ROWS_IDENTIFIER = "rows"`, `TASK_*` — константы колонок и полей задач.
- `DEFAULT_DASH = "—"`, `DEFAULT_ZERO_DELTA = "0"` — константы прочерка и нулевой динамики.
- `SPAN_START = "start"`, `SPAN_END = "end"`, `FILE_IDENTIFIER = "file"` — ключевые строковые идентификаторы моделей.

Централизация констант исключает дублирование строковых литералов, предотвращает рассинхронизацию селекторов и делает калибровку параметров прозрачной.

## Справка для агента

Агент по MCP не видит эту заметку и не читает исходники, поэтому синтаксис лежит в самом приложении: инструмент `dataview_syntax` без аргументов отдаёт справку — формы, части запроса, поля и полный список функций, — а с аргументом `query` разбирает запрос и отвечает, верен ли он. Список функций в справке берётся из того же кода, что и сообщение об ошибке, поэтому справка не расходится со сборкой.

## Границы

- **Ячейка — текст и ссылки, а не разметка.** Колонка вида `"<div style='text-align:right'>" + …` напечатает эти символы как есть: HTML из запроса не исполняется, иначе блок стал бы способом выполнить чужую разметку в приложении.
- **Нет `dataviewjs` и встроенных выражений `$=`.** Это исполнение произвольного JavaScript; в приложении, которое читает чужие заметки, такой блок — не функция, а способ выполнить код.
- **Шаблон даты — подмножество Luxon.** `dateformat` знает `y M L d H h m s E c` в обычных сочетаниях и русские названия месяцев и дней; локалей нет, шаблон всегда читается по-русски. Без шаблона дата печатается как `ГГГГ-ММ-ДД`. Подмножество выбрано по тому, чем подписывают дату в таблице, а буквы шаблона те же, что у Luxon в dataview, поэтому шаблоны переносятся без переписывания. Текст в одинарных кавычках печатается как есть. Месяц склоняется по месту: рядом с числом он стоит в родительном падеже («7 октября»), а сам по себе — в именительном («октябрь»).
- **Нет `CALENDAR`.** Месячная сетка — отдельная форма вывода со своей разметкой, а не таблица.
- **Нет вложенных полей frontmatter.** Строка с отступом читается индексом как самостоятельное поле верхнего уровня, поэтому `book.author` не работает — см. [[frontmatter-field-index]].
- **Потолок выдачи — 500 строк.** Сверх него блок сообщает, сколько всего нашлось, а не молча обрезает.
- **Источник `csv()` не поддержан.** Данные берутся только из базы заметок.
