# Инструкции и правила проекта для AI-агента

Obsidium — локальный (local-first) Tauri v2 редактор базы знаний, форк Freaction/Aquilum. Rust-бэкенд (`aquilum-app/src-tauri`),
React + TypeScript фронтенд (`aquilum-app/src`), редактор на CodeMirror 6, документ — Yjs `Y.Doc`,
источник правды на диске — обычный `.md`. Данные приложения (настройки, `ui-state.sqlite3`, индекс
поиска, состояние окна) лежат в `%APPDATA%\com.dmitriy.aquilum-app`.

## Сборки (критично)

Dev ≠ Release: `.artifacts/cargo-dev/` vs `.artifacts/cargo-release/`. Работа всегда в DEV.

Локально: `npm run tauri dev`, `npm run dev`, `npm test`, `cargo test`. Пакеты для Windows, Apple
Silicon macOS и Ubuntu 24 собираются GitHub Actions на push; tag `v*` создаёт черновик релиза.
`npm run release:local` оставлен только как необязательная локальная Windows-сборка.

Механика: `scripts/tauri.ps1` делает junction `src-tauri/target` → `cargo-dev` (dev) или
`cargo-release` (build). Не ставить отдельный `CARGO_TARGET_DIR` — Tauri ACL ломается. Не
использовать: `npx tauri …`, голый `tauri`, `npm run tauri build` без wrapper. Служебные `build` /
`tauri:build` пользователю не предлагать. Детали: `knowledge base/build-artifacts-separation.md`.
Публикация релиза и автообновление: `knowledge base/release-and-updates.md`
(fork `1tuz/Obsidium`; upstream для синхронизации — `Freaction/Aquilum`).

## Проверки перед тем, как сказать «готово»

Из `quantum-app/`: `npx tsc --noEmit`, `npm test`, `npm run check:colors`; если менялся Rust —
`cargo test` из `quantum-app/src-tauri`. Красный тест чинится, а не обходится и не удаляется. Если
тест устарел вместе с поведением — переписать тест под новое поведение и сказать об этом явно.
Не сообщать об успехе, не прогнав проверки.

## Комментарии: в коде только код

Комментариев в коде нет. Ни поясняющих «что делает», ни «почему так» — всё объяснение живёт в
`knowledge base/`. Понятность даёт код: имена переменных, функций, типов и выделение шага в
отдельную функцию с говорящим названием. Найденные комментарии удаляются вместе с правкой файла.

Единственное исключение — директивы инструментов, которые влияют на сборку и линтеры:
`// eslint-disable-next-line`, `// @ts-expect-error`, `#![cfg_attr(...)]` и подобное.

Если решение действительно неочевидно и без объяснения его сломают — объяснение пишется в
профильный документ `knowledge base/`, а не в исходник.

## База знаний

`knowledge base/` — память проекта: архитектура, инварианты, причины принятых решений. Любое
изменение поведения или архитектуры сопровождается правкой профильного документа в том же заходе.
Документ описывает не только «как сделано», но и «почему так» и «что сломается, если сделать иначе».
Новый сквозной механизм — новый документ со ссылками на смежные.

## Архитектура и размер файлов

Ориентир — 200 строк на файл с логикой, но это ориентир, а не догма: критерий модульности —
единственная ответственность файла или класса, а не количество строк. Файлы с чистыми данными,
константами, дизайн-токенами, иконками и текстами не обязаны укладываться в лимит, их дробление
вредит навигации. Файлы-фасады, где длина набрана короткими делегирующими методами, тоже допустимы.
Не создавай искусственные файлы ради формального прохождения лимита.

Дубли и мёртвый код запрещены: перед новым хелпером ищи существующий (`modules/paths.ts` для путей,
`modules/documents/fileGateway.ts` для файловых команд и так далее). Удаляй неиспользуемые файлы,
функции и экспорты; `export` ставится только на то, что импортируют снаружи файла.

Один диапазон — один владелец: два модуля не могут одновременно управлять одним и тем же участком
документа, декорацией или транзакцией.

## Производительность как философия продукта

Приложение обязано работать максимально быстро, не расходовать лишнюю оперативную память и занимать
минимум места на диске. Практические следствия: предпочитать минимальные зависимости толстым
фреймворкам, не поднимать фоновые службы, пока пользователь их не включил, ограничивать размеры
ответов и кэшей, переиспользовать существующие сервисы вместо вторых копий индексов и состояний.
Новая зависимость требует явного обоснования.

## Состояние и хранилища

- Общее для dev и релиза состояние живёт только в `app_data_dir` (`settings.json`,
  `ui-state.sqlite3`). `localStorage` привязан к origin WebView, а он у сборок разный
  (`http://127.0.0.1:1420` против `http://tauri.localhost`), поэтому там допустим только кэш,
  авторитет которого лежит в backend-хранилище. Детали: `knowledge base/workspace-switching.md`.
- Мультиплеер запланирован: любое изменение документа применяется минимальным диффом в `Y.Doc`.
  Перезапись документа целиком запрещена — она уничтожает параллельные правки и ломает CRDT-слияние.
  Конфликт записи в файл разрешается сравнением хэшей.
- Редактор обязан подтягивать изменения, сделанные снаружи (MCP-агент, другой пользователь, внешний
  редактор), а не показывать устаревший текст. Локальная реплика `Y.Doc` в IndexedDB — часть
  архитектуры, а не лишний слой; удалять её нельзя.

## Компоненты, токены и темы

Интерфейс строится строго на дизайн-токенах и переиспользуемых компонентах, повторяющиеся элементы
выносятся в компоненты. Светлая и тёмная темы обязательны для всех элементов, включая проверку
контраста текста на фоне в обеих темах. Хардкод цветов запрещён: `npm run check:colors`. Сырые
значения допустимы только в `styles/tokens/**`, `styles/themes/**` и декоративных SVG обложек.

Figma-токены: единственный источник — `quantum-app/variables.json`; синхронизация
`npm run tokens:sync`, проверка цветов `npm run tokens:diff`, проверка имён и дублей
`npm run check:figma-names`.

## Ошибки и асинхронность

Пустой `catch` допустим только для ожидаемых гонок с внешним API, когда объект мог исчезнуть между
операциями, и это очевидно из контекста вызова. Любая операция, которая асинхронно мутирует общее
состояние в ответ на внешние события, обязана быть защищена от повторного параллельного запуска
идемпотентностью, блокировкой или дедупликацией по ключу, а не полагаться на порядок событий.

## Границы изменений

Не редактируй сгенерированные и сборочные файлы, только исходники. Не меняй версии внешних API и
зависимостей без явной необходимости и явного запроса. Не расширяй задачу за пределы просьбы: нашёл
смежную проблему — почини по запросу или вынеси её отдельным пунктом в отчёт.

## Мышление и отчёт

Перед реализацией нетривиального решения сформулируй гипотезу, назови минимум два корнер-кейса,
которые её ломают, опиши решение для них и определи, в какой существующий модуль это встраивается,
не создавая дублирующих сущностей. Чини причину, а не симптом: если формулируешь про собственное
решение «это страховка на случай» или «потом переделаем нормально» — решение неверное, нужно либо
чинить причину, либо вынести выбор владельцу до того, как костыль написан.

В отчёте: что сделано, чем проверено, что осталось за рамками. Не выдавать непроверенное за
проверенное; если что-то смотрел только по коду и не запускал — сказать об этом.

## Сквозные инварианты

Markdown-списки: полные префиксы `- `, `N. `, `N) ` равноправны и сразу начинают список (в том числе
под абзацем и с пустым пунктом), без Setext. `1.` и `1)` — один тип, суффикс сохраняется. Единый
модуль конструкций: `quantum-app/src/components/Editor/extensions/outline/constructs.ts`. Детали:
`knowledge base/editor-outline.md`.

Live preview: маркер сырой тогда и только тогда, когда каретка стоит на строке владельца и внутри
его диапазона; правило одно на все конструкции. Детали:
`knowledge base/editor-markdown-live-preview.md`.

Таблицы: размеры треков для интерфейса берутся из DOM, модель задаёт запрос. Детали:
`knowledge base/editor-table-structure.md`.

Пиши код так, как писал бы топовый сеньор в big tech: надёжно, просто, без избыточности.
